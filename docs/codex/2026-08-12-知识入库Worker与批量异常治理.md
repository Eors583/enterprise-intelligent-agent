# 知识入库 Worker 与批量异常治理

日期：2026-08-12

## 部署位置

`KnowledgeIngestionWorker` 当前运行在 NestJS 后端 API 进程中。管理后台只轮询公共知识 API 并展示文件、文件夹进度，不执行安全扫描、解析、切片、Embedding 或向量索引。

开发环境采用同进程 Worker 便于一键启动；生产环境应将同一 Worker 代码作为独立进程或容器部署，以便与业务 API 分别扩缩容、限流和故障隔离。知识访问仍通过知识边界内部 Gateway/仓储完成，不能让前端或其他业务模块直接访问 Qdrant、对象存储或知识表。

## 现场状态

知识库 `咨询圈文库资料1` 共 583 份文档。2026-08-12 09:07 的快照：

- 362 份 `SUCCEEDED/READY`；
- 41,667 个知识切片；
- 217 份处于自动退避重试；
- 3 份超过 100MB，属于永久输入异常；
- 1 份曾被标记 `DOCUMENT_PARSE_FAILED`。

217 份重试任务不是最终失败。主要暂时错误为 Docling 无效响应、Docling 不可用、基础设施瞬时错误、Embedding 超时和 ClamAV 暂时不可用。

## 新定位的根因

Docling 在并发解析复杂 PPT/PDF 时反复自行退出并由 Docker `unless-stopped` 拉起。现场重启计数在两分钟内从 25 增长到 27；容器没有被标记为 OOMKilled，但服务重启会中断正在返回的响应，产生 404、截断响应和连接不可用。

对唯一被标记为文件解析失败的 PDF 重新校验：对象大小 9,781,947 字节，SHA-256 与账本记录一致。使用同一原始对象调用 Docling 时返回 HTTP 404：`Task result not found. Please wait for a completion status.`。这代表解析服务内部结果暂未就绪，并不能证明源文件损坏。

## 修复与运行策略

- Docling HTTP 404 改为 `DOCUMENT_PARSER_UNAVAILABLE`，进入有界退避重试，不再误报文件损坏。
- 为 404 分类增加适配器测试。
- 通过正式知识重试 API 将误判 PDF 重新排队，没有直接改写知识表。
- 本机 `KNOWLEDGE_INGESTION_BATCH_SIZE` 从 2 降为 1。调整后观察期内 Docling 重启计数保持 27，健康检查通过，内存约 2.2GB。
- 保留最大 5 次真实失败限制；不使用无限重试。

## 扩容建议

单实例提并发不是可靠提速方式。生产环境应独立部署 Worker，并按 `Worker 实例数 <= 健康 Docling 实例数` 控制解析并发；每个 Docling 实例设置独立 CPU/内存限制与就绪探针，通过队列水平扩容。Embedding 和向量写入也应分别设置批量大小、限流和指标。只有完成容量压测后才提高并发。
