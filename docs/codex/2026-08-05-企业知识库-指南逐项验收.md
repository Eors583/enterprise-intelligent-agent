## 最终结论

不能把指南中的全部内容认定为已经完成。

当前已经完成并真实跑通的是“初版企业文件 RAG + 结构化表格查询 + 关系增强 + 管理界面”闭环：原文件进入 MinIO，业务事实和权限元数据进入 PostgreSQL，Dense/Sparse 向量进入 Qdrant，Docling 生成统一结构化文档，系统建立父子块和相邻块，执行词法、向量、关系、SQL 路由和重排，返回可打开的原文来源；无可靠证据时返回无答案。PDF、DOCX、XLSX、PPTX、PNG、Markdown 六类真实文件和前端界面均已验收。

尚不能认定完成的是指南中的生产知识中台目标：当前 200 道题是从已发布资料切片生成并由双人治理流程发布的“来源绑定技术基线”，不是业务部门提交的员工真实问题；通用 HTTPS Manifest 增量连接器已完成本地真实验收，但具体网盘厂商 OAuth/服务账号、权限投影和定时调度尚未生产接线。真实业务 API 执行通道、生产 SSO/ACL/KMS/DLP、复杂扫描件专项基准、Qdrant/MinIO 高可用与联合灾备、容量压测和真实告警投递也没有完成生产验收。

因此准确口径是：

> 初版功能闭环已经跑通，且小白用户可在前端完成上传、预览、检索和来源查看；指南要求的生产化与持续运营部分仍需下一阶段建设。

这套设计没有把大文件放进 PostgreSQL，也没有让 PostgreSQL 承担主向量库。PostgreSQL 保存需要事务、外键、权限和审计的数据；MinIO 保存大对象；Qdrant 承担高维向量近邻检索。这样能降低业务库的 I/O、膨胀、备份和索引压力。

## 检索和关系是怎样建立的

### 文档检索链路

1. 用户上传文件，服务先校验文件类型、大小、签名和 SHA-256，并通过 ClamAV 扫描。
2. 原文件以不可覆盖对象写入 MinIO；数据库创建文档和版本账本。
3. PDF、DOCX、XLSX、PPTX、图片交给 Docling；Markdown/Text 使用本地解析器。解析结果以统一结构化 JSON 另存到 MinIO。
4. 解析结果按文档结构生成父块和较短子块，同时保存标题路径、页码/工作表/章节定位、前后相邻块和解析器信息。
5. 子块生成 Dense 向量和 Sparse 表征写入 Qdrant；正文和业务元数据仍由 PostgreSQL 掌握。
6. 查询先识别 DOCUMENT、SQL、RELATIONSHIP 或 BUSINESS_API 意图。普通文档问题并行取得词法、Dense、Sparse 和关系候选；结构化 Excel 计算进入 SQL 通道。
7. 外部索引只返回候选 ID 和分数。系统回到 PostgreSQL 复核租户、当前发布版本、文档状态和资源范围，再读取正文。
8. 候选经过融合、Cross Encoder 或加权回退、单文档限额、关系贡献和证据阈值判断。
9. 证据不足返回 `noAnswer=true`；证据充分时返回来源文件、版本、章节/页码/工作表、原文片段和可打开原文件的引用。

### 父子块和相邻关系

- 父块代表完整章节、页面、条款组或表格上下文。
- 子块用于精确召回。
- 每个子块记录 `parent_chunk_id`、`previous_chunk_id`、`next_chunk_id`，并保持文档、版本和知识库复合身份一致。
- 检索先命中子块，再展示父块及前后文，避免只给用户一个脱离语境的句子。

### 实体关系

- 入库后从文档切片抽取实体、别名和关系，并把每条关系绑定到原文证据。
- 关系查询从授权候选中的实体出发，执行一至两跳扩展，并把路径、方向、置信度和来源切片作为检索证据。
- 当前实现是 PostgreSQL 中的证据型关系图，不是 Neo4j，也不是全量 GraphRAG。这样适合初版验证，同时避免先引入独立图数据库的运维复杂度。
- 本地验收知识库已发布本体，由资料负责人提交、另一位管理员独立批准。增量资料引入新关系类型后又完成一次异人本体审核和关系修正治理；当前 224 条活动关系全部受治理、开放冲突为 0，221 条关系进入已发布可检索读模型。真实问题“Payment Service 的负责人是谁？”走关系检索，首条证据指向 `service-ownership-handbook` 中的 Finance Platform Team，且能展开一至两跳路径。这证明证据型关系治理闭环可用，但仍不等于已建设面向高频多跳推理的 Neo4j/KAG 企业图谱。

### Excel 双通道

- 说明、字段含义和少量记录继续走 RAG。
- 求和、平均、最大/最小、计数、同比和环比走参数化 SQL。
- 当前真实问题“Identity API 第二季度比第一季度的可用率环比提高多少？”走 SQL，结果为当前 99.9%、上期 99.7%、提高 0.2 个百分点，约 90 ms。
- 当前 SQLite 通道面向单个已授权工作簿，不等同于企业数仓；跨工作簿、复杂公式和实时业务数据仍需正式分析引擎或业务 API。

## 非技术用户实际流程

### 1. 进入“企业知识库”

管理员从业务概览进入企业知识库。主页优先显示知识库、资料数、可用状态和需要处理的异常，不要求用户理解向量库。

证据：`.data/audits/2026-08-05-knowledge-novice-final/01-overview.png`、`02-knowledge-home.png`。

### 2. 给当前知识库添加资料

点击“上传文件”，选择 PDF、Word、Excel、PPT、图片或 Markdown。系统在真正上传前计算哈希：

- 完全相同：明确提示重复并阻止再次导入；
- 同名但内容不同：让用户选择“作为新版本”或“作为独立资料”；
- 新资料：直接进入处理队列。

证据：`03-upload-duplicate.png`。

### 3. 等待处理并查看内容

用户只需要看“处理中、可用、失败”及失败原因。打开资料后能看到可读章节、表格、页码/工作表和父子块上下文；Token、哈希、模型 ID 等放在高级详情。

证据：`04-chunk-lineage.png`、`07-structured-table-after.png`。

对于企业文档源，管理员也可以在同一知识库创建 HTTPS Manifest 连接器并点击“立即同步”。第二次同步会按稳定远端 ID、SHA-256/ETag 和游标识别新增、更新、删除与无需处理的条目；删除不会物理抹除历史，而是归档当前文档并使其退出检索。

### 4. 提问和查看来源

普通模式先显示回答，再显示支持回答的来源。分数、候选数、阶段代码和内部 ID 收进“查看诊断”。Excel 计算问题显示精确结果，用户无需理解 SQL；来源可打开原文件。

证据：`08-retrieval-answer-after.png`。

### 5. 没有答案时明确停止

当证据不够，页面第一屏直接显示“未找到达到阈值且当前用户有权访问的内容”，并说明不会拼接无依据回复，不让用户在大量工程日志之后才看到结论。

证据：`10-no-answer.png`。

### 6. 设置保持简单

普通管理员默认只看到检索模式和是否精排；TopK、阈值、权重和切分 Token 放在高级设置。当前仍应继续补充“按业务场景选择推荐配置”和“一键恢复推荐值”。

证据：`09-settings-simplified.png`。

### 7. 评测不是默认显示假成功

评测页已经用真实前端走通“创建检索专用版本 → 导入 200 题 → 形成 200 份证据标注 → 资料负责人提交 → 另一位管理员审核 → 发布 → 逐题真实检索 → 查看指标与失败 → 修复后复测”。运行过程中每 2 秒读取服务端持久化进度，最终页面显示 Recall@5、MRR、nDCG@10、来源支撑率、无答案准确率均为 100%，ACL 泄漏 0，P95 2496 ms 和“通过”。页面同时明确标注这批题是来源生成技术基线，不冒充员工真实提问。

证据：`06-evaluation-dashboard.png`。

### 8. 员工端

Electron 员工端已真实打开并加载通讯录、会话和员工智能体。历史回答生成于反馈功能上线前时，按钮禁用并显示“这条历史回答生成于反馈功能启用前，暂不支持评价”，不再暴露英文 404 技术错误。新消息对应的回答已经真实提交“没帮助/缺少关键知识”反馈，管理端完成坏例归因、加入回归数据集、创建关联用例和标注；这条链路不依赖静态假数据。

## 仍建议优化的使用体验

### P0：下一次试用前

1. 把“上传资料”和“新建知识库并导入”做成明确不同的入口，避免资料放错库。
2. 在原文件打开后提供应用内 PDF/Office 预览，才能稳定实现页码和工作表一键定位；依赖外部阅读器只能保证打开原件。
3. 给检索设置增加“制度合同、项目资料、表格数据”业务预设和恢复推荐值。
4. 给每个处理中的文件显示阶段化进度：安全检查、解析、切分、索引、可用；失败时提供业务化原因和重试按钮。

### P1：形成真实质量闭环

1. 请业务部门用员工真实问题替换或补充现有 200 道来源生成基线，继续覆盖正确证据、允许角色、无答案、计算题和多文档题。
