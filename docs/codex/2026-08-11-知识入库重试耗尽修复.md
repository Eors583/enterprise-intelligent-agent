# 知识入库重试耗尽修复记录

日期：2026-08-11

## 现象

企业批量上传后，大量文档显示 `KNOWLEDGE_INGESTION_ATTEMPTS_EXHAUSTED`。现场统计共发现 284 个此类历史失败任务，其中绝大多数停留在 `UPLOADED`，并未进入文档解析阶段；文件类型主要为 PPTX，其次为 PDF。

## 根因

旧队列用同一个 `attempts` 字段同时表示两类完全不同的事件：

1. Worker 真正执行文档处理后失败；
2. API/Worker 重启、租约过期或任务被另一个 Worker 回收。

每次任务领取和租约回收都会增加 `attempts`。因此，批量任务在服务重启或长时间处理时，即使尚未解析文件，也可能达到默认上限 5，随后被统一改写为 `KNOWLEDGE_INGESTION_ATTEMPTS_EXHAUSTED`。这既错误拒绝了可处理文档，也覆盖了真实失败原因。

此外，Docling 在批量并发下偶发返回无效或截断响应。对其中一份失败 PPTX 使用同一源文件和同一 Docling 实例单独复现时，服务在约 2 秒内成功返回 61,254 字符 Markdown，说明该错误是瞬时解析服务响应异常，不是源文件永久不可解析。

## 修复

- 新增 `knowledge_ingestion_jobs.failure_attempts`，仅在一次真实、可重试的处理失败后递增。
- `attempts` 继续记录领取/执行次数，供审计和租约诊断使用，但不再作为文档失败上限。
- Worker 回收过期租约时不会消耗真实失败预算，也不会在执行前将文档判为失败。
- 达到真实失败上限时保留最后一次真实错误码，例如 Embedding 不可用或解析超时，不再统一覆盖为 `KNOWLEDGE_INGESTION_ATTEMPTS_EXHAUSTED`。
- `DOCUMENT_PARSER_INVALID_RESPONSE` 改为可退避重试；永久性错误（不支持的格式、文件签名错误、对象超过限制、完整性错误等）仍立即停止，避免无意义死循环。
- 队列优先处理真实失败次数较少的任务，再按领取次数和可用时间排序。
- 为最小权限数据库角色 `enterprise_agent_outbox` 补充新字段的 `SELECT/UPDATE` 列级权限。

没有采用“无限重试”。无限重试会让永久损坏文件持续占用 Docling、Embedding、Qdrant 和 Worker，并阻塞后续正常文件。现在解除的是“系统重启也算文档失败”的错误限制，真实瞬时故障仍采用有界退避重试。

## 数据恢复与现场验证

- 通过正式知识管理服务重新排队 283 个历史重试耗尽版本。
- 另重新排队 52 个明确可恢复的旧失败版本，包括旧的解析器无效响应、解析服务不可用、AI 超时和 Qdrant 瞬时不可用。
- 修复数据库角色授权后，Worker 恢复领取任务。
- 观察快照中，恢复批次已有 13 个任务到达 `SUCCEEDED/READY`。
- 同一快照中，2 个 `DOCUMENT_PARSER_INVALID_RESPONSE` 和 1 个 `KNOWLEDGE_AI_TIMEOUT` 已按新逻辑回到 `PENDING`，其 `failure_attempts=1`，没有被提前判死。
- 服务重启前最后遗留的解析响应失败版本也已通过正式知识入库服务重新排队。

批量恢复仍会在后台持续运行。文档数量和 PPT/PDF 复杂度较大时，全部完成需要时间；页面应以文件夹处理百分比、处理中数量和异常列表呈现真实进度。

## 验证命令与结果

- Prisma migration deploy：成功，共 120 个 migration，新增字段和最小权限授权均已应用。
- API Vitest：219 个测试文件通过、23 个跳过；1,351 个测试通过、155 个跳过。
- API TypeScript typecheck：通过。
- API build：通过。
- API readiness：`ready`；repository、AI Runtime 均为 `up`。
- 使用真实 MinIO 源文件调用本地 Docling：HTTP 200，解析成功。

上述 readiness 和真实恢复结果是在修复上线后的有效观测。随后本机 Docker Desktop Linux Engine 在批量恢复压力下返回 500，WSL 命令也开始超时；Docker Desktop 进程级重启后仍停留在 Engine Starting。当前非管理员会话无法重启 `WslService`，因此交付时本机容器基础设施处于待恢复状态。该运行态故障不会丢失 PostgreSQL/MinIO 持久卷中的任务和文件，但需要管理员重启 WSL 服务或重启 Windows 后再执行本地一键启动并复核 readiness。
