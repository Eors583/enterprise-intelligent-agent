# BMS-AI 用户协作偏好与 AI 开发接班长期记忆

> 最近确认：2026-08-17
> 适用范围：`enterprise-intelligent-agent` 仓库中的产品分析、设计、开发、测试、部署和故障诊断
> 目标读者：后续接手本项目的 Codex、其他 AI 开发者、测试智能体和工程人员

## 1. 这份记忆是什么

这份文档记录项目发起人在长期协作中反复明确的产品判断、工作方式、交互偏好和验收标准，目的是让后续 AI 不必要求用户重复解释已经确认过的原则。

它不是对用户人格的推断，不记录密码、Token、AppSecret、Cookie、连接串、身份证件、联系方式或其他秘密，也不能替代当前代码、ADR、验收矩阵和用户最新指令。

使用时遵守以下证据顺序：

1. 用户在当前任务中的最新明确指令。
2. 根目录 `AGENTS.md`、当前代码、契约、migration、测试和 ADR。
3. 本文记录的长期偏好与稳定决策。
4. 日期型 `docs/codex/` 文档中的历史状态。
5. AI 自己的推测。

如果本文与用户后续明确决定冲突，以用户最新决定为准，并同步更新本文。不要拿“长期记忆”反驳用户，也不要把历史决定永久冻结。

## 2. 对用户的核心理解

用户不是为了展示技术或堆叠页面而做这个产品。用户真正希望得到的是一套企业员工和管理者能够直接使用的 AI 协作产品：普通人不需要理解底层技术，智能体必须使用企业真实业务数据和权限受控知识，项目必须能从目标、执行、交付到验收完整闭环。

用户非常重视以下结果：

- 功能真实可用，而不只是代码、页面或接口存在。
- 普通员工和普通管理员能看懂、会操作、不会被技术术语和重复配置吓退。
- 智能体与后台使用同一个权威知识边界，不能各自维护平行知识库。
- 权限边界真实执行，不能只靠前端隐藏按钮，也不能泄露“存在但你无权访问”的资料。
- 系统可模块化替换供应商，不能把业务 API、智能体或前端直接绑定某一个模型、向量库或知识供应商。
- 大文件、大文件夹、批量文档和企业级数据量必须作为正常场景，而不是边缘场景。
- 开发者要主动诊断、修复、启动和验证，不能把本可由代码和日志查明的问题反复交还给非技术用户。

用户愿意听技术解释，但希望解释服务于决策。需要先说结论，再用清楚的因果关系解释“是什么、为什么、放在哪里、会不会影响效果或性能、后续如何扩展”，不要假设用户已经熟悉 RAG、Embedding、AI Runtime、Worker、Qdrant 或数据库术语。

## 3. 与用户协作的方式

### 3.1 默认行动方式

- 用户要求“实现、修复、启动、跑通、继续”时，应主动推进到可验证结果，不要只给方案或代码片段。
- 能从仓库、数据库、日志、运行状态和现有文档查明的事实，先自行查明，不要把调查工作包装成澄清问题交给用户。
- 只有缺少的选择会实质改变产品方向、需要新的外部授权或存在不可逆风险时，才停下来询问。
- 用户说“刚刚中断了，继续”时，应从现有工作区和先前证据继续，不要从头重复分析和已经完成的步骤。
- 用户允许真实测试时，可以执行必要的自动验收操作；涉及发送消息、改变业务状态、删除数据或外部系统写入时，仍按当前授权范围和项目安全规则执行。
- 用户离开或不操作鼠标时，不应把鼠标静止误判为不能继续。优先使用 API、数据库、日志和自动化测试；确需 Computer Use 时，按工具能力继续并尊重系统安全中断。

### 3.2 沟通方式

- 使用中文和普通业务语言，结论优先。
- 明确区分：已确认事实、高置信判断、推测、尚未验证项。
- 说明失败发生在哪一层：前端显示、业务 API、权限、Worker、知识召回、模型路由、AI Runtime、外部供应商或基础设施。
- 不用“应该没问题”“理论上可用”代替证据。
- 不隐瞒真实阻塞，也不要因一个外部环节未验证就把整个模块描述为完全不可用。
- 用户询问技术认知时，既说明推荐方案，也解释替代方案、存储位置、性能影响、成本和扩展边界。
- 避免反复复述用户整段需求；用简洁进展、证据和下一步保持协作感。

### 3.3 用户不喜欢的开发行为

- 页面已经画出来就宣称功能完成。
- HTTP 200、任务排队、mock 测试或静态响应被描述成真实业务跑通。
- 为了“企业级”增加大量普通用户必须理解的配置、状态、审批或技术名词。
- 另起一套重复账本、知识库、权限系统、待办系统或智能体平台。
- 未检查真实根因就重启所有服务，或把所有问题笼统归因于“服务没启动”。
- 修改代码时中断正在处理的大批量任务，却没有租约、恢复、幂等和重试说明。
- 在脏工作区回滚、覆盖或格式化其他任务的修改。
- 把凭据、staff-id、内部 ID、对象存储键或技术错误详情直接暴露给普通员工。

## 4. 产品体验偏好

### 4.1 低心智负担是最高体验约束

普通用户页面首先回答三个问题：

1. 现在能不能用？
2. 如果有问题，问题是什么？
3. 下一步应该做什么？

普通员工不应被要求理解 RAG、Chunk、Embedding、Vector、Reranker、Qdrant、Provider、Run、Queue、ACL、tenant、模型哈希或内部 JSON。普通管理员也只在必要的运行诊断入口看到有限技术信息。

正常资料的主路径应保持为：

```text
选择资料与可见范围 → 上传 → 自动处理 → 已可使用 / 需要检查 / 处理失败
```

系统能够自动推导的 ID、租户、创建人、归属人、状态、版本、模型、索引参数、追踪号和内部策略，不进入普通表单。

### 4.2 导航和功能组织

- 不因新增治理、反馈、来源、诊断或协同能力增加一级菜单。
- 相同事项只在一个地方要求用户处理；其他页面只显示状态并跳转到统一待办。
- 运行状态集中放在既定导航或治理入口，不要在每个知识库卡片、页面和弹窗重复展示。
- 普通操作应位于用户正在处理对象的上下文中。例如知识库访问范围在创建或编辑知识库的位置配置，而不是另造孤立页面。
- 个人使用说明书只能由当前登录用户填写和维护自己的内容，管理员不能代替员工填写个人说明书。

### 4.3 按钮和交互

- 主要可用操作直接显示为名称明确的按钮。
- 不把按钮藏进“高级”“更多”“录入方式”等 `details/summary` 展开区。
- 不使用点击后才出现的一排悬浮操作或难以发现的图标按钮作为主要路径。
- “其他来源接入”适合做成一个按钮，点击后打开弹窗；“粘贴文本”等主要录入方式直接展示。
- 用户创建对象后默认应当可用；如果仍需要“发布”，必须有真实的草稿、复核或原子发布业务价值，否则应删除多余发布步骤。
- 危险操作使用“删除”等用户能准确理解的词。不要用“归档”代替删除；若产品确实保留可恢复数据，则必须明确说明二者区别。
- 已删除对象不再出现在普通前端列表、树和选择器中。
- 删除文件夹时，用户期待能明确选择并执行“删除文件夹并清空其中资料”；空知识库也必须有可发现的删除能力。

### 4.4 视觉规范

- 字体、字号、颜色、间距、圆角、阴影、控件尺寸和动效必须使用统一设计 Token，禁止业务页面散落视觉硬编码。
- 样式规范是长期维护资产；调整 UI 时同步维护设计规范表。
- 避免无缘由的大字号、局部字体跳变、密集卡片、信息堆叠、重复状态和不一致边距。
- 页面需要覆盖窄屏、200% 放大、长中文、长错误信息、键盘焦点和非颜色状态表达。
- UI 修改后必须打开真实管理端或 Electron 检查，DOM 测试不能替代真实视觉和交互验收。

## 5. 知识库与智能体的稳定产品判断

### 5.1 知识边界必须独立和模块化

知识库是独立业务边界。任何智能体、项目、评测、管理端或第三方系统，只能通过 `KnowledgeGateway`、`KnowledgeRetrievalGateway`、公共 API 或正式事件协议使用知识能力。

业务模块不得直接读取知识表、Qdrant collection、对象存储目录或知识内部实现类。模型、Embedding、向量库和知识供应商都应通过适配器替换，业务 API 不直接绑定 OpenAI、BGE、FastEmbed、Qdrant 或乐享。

用户关心这种解耦不是为了抽象本身，而是为了：

- 后续能够替换本地或外部 Embedding 模型；
- 向量维度和索引版本能够按知识库或索引版本管理；
- 能把知识模块接到员工智能体、项目、评测和第三方系统；
- 更换供应商时不重写业务权限、引用、审计和评测链路。

不要为了模块化建设插件市场、动态脚本平台或通用工作流引擎。实现满足当前供应商替换和边界隔离的最小接口即可。

### 5.2 当前本地知识库与乐享方向

用户已经明确：现阶段废弃并禁用本地知识库运行链路，但不删除已有本地知识库代码；当前不继续投入本地摄取链路，外接乐享知识库是优先方向。

“废弃”在这里表示停止作为当前产品主路径和默认运行依赖，不表示删除代码、历史 migration 或将来永不恢复。后续 AI 不应擅自重新启用本地知识基础设施，也不应为清理而删除相关实现；如要恢复，先确认新的产品决定。

管理员后台知识库和员工端智能体必须接入同一个权威知识边界。禁止员工端再维护一套独立知识库或绕过 Knowledge Gateway 直连乐享。

### 5.3 乐享 staff-id 的准确语义

乐享 `staff-id` 是乐享连接级 API 访问身份，用来让应用调用乐享知识接口。它不等于 BMS-AI 的用户 ID、员工 ID，也不要求与本系统员工逐一映射。

正确权限关系是：

```text
BMS-AI 先按本地租户、组织、项目、成员和知识库可见范围授权
  → 授权后使用连接配置中的乐享 staff-id 调用限定 space 的乐享接口
  → 召回后再次执行本地分类、有效期、治理和派发前权限复核
```

普通员工不应看见 staff-id、targets、Token 或 Provider。未知本地用户、跨租户用户和已离职身份继续由 BMS-AI 本地权限拒绝；不能因为共用连接级 staff-id 而放松本地 ACL。

### 5.4 知识权限与回答

- 知识归属人默认是当前登录账号，不要求普通用户手选“知识归属人”。
- 知识库应支持公司、部门、项目、成员四类并列业务归属，以清楚的分层树展示。
- 上传资料必须能够选择可使用对象或部门；具体操作应尽量继承知识库级范围，文档级例外只在确有业务需求时出现，避免重复配置。
- 智能体检索必须使用提问者当前可使用的知识，而不是继承被代表员工的全部权限。
- 无可用依据时统一表达“当前没有找到你可使用的可靠依据”，不能泄露系统存在无权资料。
- 有知识回答必须保留真实来源、稳定证据 ID、版本和可打开引用；不得让模型伪造引用编号。
- 知识回答必须由智能体综合相关证据、去重并归纳后直接回答用户；默认采用结论优先的简洁中文，并以段落或列表项为单位附真实引用。禁止把召回 chunk、签名图片 URL、Markdown 图片标记、解析占位符或其他原始文档噪声作为失败兜底直接回显给用户。
- 智能体回复和流式生成内容必须按安全 Markdown 富文本语义展示；`**粗体**`、列表、表格、代码等格式符不能作为普通字符暴露给用户。消息渲染不执行原始 HTML，也不直接加载回答中的远程 Markdown 图片；长内容必须在消息气泡内部换行或由表格、代码块自身滚动，不能撑宽会话页面。
- 用户接受智能体为真实供应商结果等待较长时间，不接受以固定总时长超时替代结果。取得外部任务 ID 后应持续等待明确终态或用户取消，并通过 Worker 续租和可恢复流保证长任务不被重复领取；若知识检索、模型任务创建、模型执行、Runtime 连接或引用校验明确失败，界面必须指出具体步骤，不能只显示笼统 Provider 错误。
- 2026-08-20 起，同一智能体必须能同时服务不同用户和不同聊天窗口。每个问题绑定独立租户、会话、输入消息、Run、发起人权限和流事件，禁止按智能体共享可变对话状态；同一会话的连续问题应全部可靠接收并顺序排队，不因已有 Run 而丢弃或直接拒绝。系统采用有界并发、公平排队和按供应商账号隔离的限流，超出容量时显示等待状态，不能串话、丢消息或伪装成功。
- 2026-08-20 已落地上述并发目标的 P0：消息和 Run 使用数据库序列确定顺序，历史“每会话只能有一个活动 Run”的唯一索引已移除；接收事务短暂取得会话 advisory lock，Worker 对同会话执行队首闸门，不同会话可并行；桌面端状态与流内容按 `inputMessageId/runId` 绑定。2026-08-21 又补上 `(tenantId, inputMessageId)` 的部分唯一回答槽位，覆盖 `QUEUED / DISPATCHING / RUNNING / UNKNOWN / SUCCEEDED`，失败和取消尝试仍可作为多条 Run 历史保留；显式重试按逻辑输入消息查找槽位，不再只检查直接重试子项。Outbox 领取 SQL 已在抢占前过滤同会话非队首 Run，`prepare()` 仍保留事务内会话顺序与租户配额权威复核；真实 PostgreSQL 测试验证同会话 10 条积压只领取队首、后 9 条零无效 claim，以及 200 条冷启动积压在配额 8 下只有 8 条进入 `DISPATCHING`。供应商 `(provider, credentialReference, model)` 并发舱暂未实现：当前 Python Runtime 会在多个模型候选间动态选择和故障转移，API 派发前不知道实际供应商槽位，不能锁第一个候选制造假安全；需先补 Runtime/路由的实际候选占槽协议、容量/RPM/TPM 配置和释放回执。公平调度、多副本故障恢复和 100 用户真实模型压测仍是 P1/P2，完成前不得宣称生产多人并发已完整验收。
- 2026-08-21 Manus v3 复核后新增稳态竞争验收：10 会话 × 10 问题、16 个模拟 Worker 槽、租户上限 8，在执行完成与再次获取持续交织时 100 条全部收敛且峰值为 8；冷启动与稳态测试必须同时保留。`UNKNOWN` 继续阻止同会话后续 Run，因为时间流逝不能证明供应商已停止；不得按 5～10 分钟自动改 FAILED 并重放。桌面端必须明确显示“等待上一条结果确认”，参与者可在理解远端仍可能完成和计费后“结束本地等待”；该动作记为 `FAILED / AI_RUNTIME_RESULT_ABANDONED` 而非伪造 `CANCELLED`，真实数据库测试已证明随后队首立即恢复。Agent Run Outbox 当前没有按 attempts 静默淘汰，未来如设上限必须把真实执行失败次数与领取/延期次数拆开。
- 2026-08-21 Manus v4 复核后，已有外部 ID 的 `UNKNOWN` 会在原终态事务中创建默认 5 分钟后的 PostgreSQL Outbox 对账事件；Worker 在锁内恢复同一 Run，且只能查询原 `externalRunId`，绝不因超时创建新供应商任务，用户已经结束等待时延时事件只收口、不调用 Runtime。`SUCCEEDED / FAILED / CANCELLED` 已增加数据库终态不可逆触发器，真实集成测试验证 `FAILED / AI_RUNTIME_RESULT_ABANDONED` 不能被直接 SQL 或正式完成入口改回成功，也不会追加迟到消息。不要机械增加 `supersededBy`：用户下一条新消息不必然是上一问的重发；将来若有供应商迟到回调，应把结果和费用作为独立审计/计费事实，而不是改写终态或污染会话。稳态测试已改走 100 条真实 `SUCCEEDED + markPublished` 主路径，峰值仍为 8；数据库清理门禁已有“实际连接到开发库必须拒绝”的回归。
- 后台“测试召回成功”不等于员工智能体回答已接通。必须继续验证 Agent Run 的授权、召回、模型路由、生成、引用校验和引用打开。

## 6. 企业文件和性能场景

用户预期真实企业资料具有以下特征：

- 一个知识库包含多层文件夹和数百乃至更多文件；
- 用户需要直接上传文件夹并保留目录结构；
- 常见格式包括 PDF、DOCX、XLSX、PPTX，以及历史 `.ppt` 等；
- 大文件和复杂演示文稿是正常数据，不应被简单尺寸限制拒绝；
- 被跳过或失败的文件需要逐项说明原因，并提供可控重试；
- 文件夹需要展示真实汇总进度、成功比例、处理阶段和异常数量；
- 重复文件应基于内容哈希、租户和不可变索引版本安全复用切片或向量，不能因复用产生 chunk ID、权限、页码或版本混淆。

性能优化不能降低切片和检索质量。不要把“切片与索引很慢”直接归咎于切片算法；应分别测量安全扫描、Docling/Tika 解析、切片、Embedding、Qdrant、PostgreSQL 持久化和总墙钟时间。

部署新代码时，需要明确正在处理的 Worker 是否会被中断、任务租约如何恢复、失败是否会重试、READY 是否保持原子。用户接受短暂重启，但不接受大批量任务静默丢失或长期卡在含糊进度。

## 7. 权限、安全与受控智能体

- 权限不能因为“初版先跑通”而彻底后置；可以简化 UI，但后端租户隔离、知识过滤和派发前复核必须存在。
- 员工智能体代表员工参与协作时，有效范围是：提问者权限 ∩ 被代表员工主动披露范围 ∩ 当前工作关系 ∩ 本次用途 ∩ 模型与工具安全策略。
- 员工智能体不能继承员工本人的完整权限替别人查询。
- 个人使用说明书历史数据默认私有，员工本人主动决定哪些部分用于协作。
- 航班、酒店、精确位置、原始日历等敏感状态不应作为普通协作摘要公开。
- 智能体可以提供建议和草稿；发送消息、修改任务、承诺日期、验收、审批、升级和其他高风险动作必须经过真人确认及既有 Tool/Collaboration Gateway 与审计。
- 2026-08-19 起，已启用且用户有权使用的智能体，其对话入口始终开放；模型未就绪、缺少近期成功凭据或供应商暂时异常只能作为对话内运行状态与失败回执展示，不能将通讯录、搜索、新建会话、群聊或消息入口置灰。显式停用、离线、离职、未授权、跨租户和知识权限拒绝不受此规则影响。
- 企业知识进入模型前必须完成权限过滤；模型输出和引用在展示前再次复核。
- 敏感凭据命中后不得进入 Embedding、向量索引、关键词索引或模型；日志只保留脱敏证据。

## 8. 用户认可的工程与验收标准

### 8.1 实现纪律

- 跨端字段先改 `packages/contracts` 和契约测试。
- 数据变化只新增前向 migration，不修改历史 migration。
- API 和数据库先完成授权、RLS、状态机、审计、幂等和失败分支，再接 Worker、Runtime 和 UI。
- 当前工作区经常包含并行任务修改。只改本任务文件，不回滚、不覆盖、不全仓格式化。
- 生成目录、日志、凭据和本地运行数据必须由 `.gitignore` 排除；推送前检查暂存范围和秘密泄漏。
- 未经用户明确要求，不擅自提交、推送、删除数据库数据或执行不可恢复操作。

### 8.2 “完成”的证据

后续 AI 汇报完成时至少说明：

1. 实现或确认了什么真实业务能力。
2. 修改了哪些文件和迁移。
3. 实际运行了哪些目标测试、包级测试、类型检查、构建、数据库验证和启动检查。
4. 是否用真实管理端和 Electron 做了视觉、交互和可访问性检查。
5. 是否使用真实数据库、真实双账号、真实模型、真实乐享、真实 IM 和真实引用链验收。
6. 哪些仍然只经过 mock、契约测试或静态检查。
7. 哪些生产容量、故障恢复、备份、监控和安全场景仍未验证。

用户特别看重独立复测。开发者自己验证通过后，应在条件允许时交给测试智能体或独立验收流程，从企业管理员、普通员工、无权限员工和跨租户用户角度复测。

### 8.3 故障诊断方式

遇到“无法连接”“回复失败”“处理中”“不可用”等问题时：

1. 定位精确用户、租户、会话、Run、文件或任务 ID。
2. 对照用户可见时间换算服务日志时间。
3. 查询持久化状态、错误码、阶段时间、尝试回执、路由快照和熔断状态。
4. 分别检查 API、Worker、AI Runtime、外部知识供应商、模型供应商、数据库、IM 和前端订阅。
5. 说明失败发生在调用前、调用中还是调用后。
6. 修复后重跑原问题，而不是换一个更容易成功的问题。

外部模型供应商存在未公开的请求体或单消息边界时，优先在本系统发送前按“当前问题与安全规则 → 最近一轮窗口记忆 → 排序靠前的授权证据 → 已确认持久记忆 → 更早会话”裁剪可选上下文；不要把可预防的供应商 `invalid_argument` 留给普通用户，也不要要求用户通过反复新建会话规避。

2026-08-21 起，用户明确要求消息接收、授权知识检索到智能体回答尽量秒级开始输出。消息、Run 与 Outbox 提交成功后应立即唤醒同进程 Worker，定时轮询只作为跨进程与故障恢复兜底；不同会话按可用执行槽并发，同一会话保持严格顺序。流式输出必须来自供应商真实增量，允许按真实上游网络包合并极小 delta 以减少持久化放大，但不能把完整终态答案切成假 Token 动画。当前 Manus 公共任务接口属于异步终态读取能力；要实现类似豆包的持续逐段输出，需要使用明确支持 SSE 的受信任 OpenAI-compatible 路由，并以真实首 Token、知识检索、并发额度与断线回放数据验收。

2026-08-20 起，同一智能体会话的最近一轮问答属于必须优先保留的窗口记忆，不能因为知识召回很多而全部裁掉。对“还是没懂”“这个是什么意思”“能用大白话解释吗”等依赖上文的追问，知识检索也必须补入上一轮用户问题以恢复主题。跨会话长期记忆不能静默保存普通聊天或模型输出，应继续走候选、确认、范围、同意、权限和保留治理。

知识库成功返回零命中、返回的候选无法支持问题，或知识型智能体正在回答会话记忆与普通交流问题，都属于正常业务分支，不显示红色系统错误。需要企业依据但没有可核验证据时，安全丢弃未经核验内容并正常回复“当前没有找到你可使用的可靠依据”；只有乐享连接、认证、目标、接口、响应解析等明确异常才显示具体出错步骤。不能把“存在候选片段”直接等同于“知识库存在相关答案”。

不要把独立存在的告警混成一个根因。例如 IM 实时连接 403、模型路由为空、乐享检索失败和桌面轮询延迟可能同时存在，但需要分别给出证据。

## 9. 后续 AI 的接班检查清单

每位接班 AI 开始重要任务前：

- [ ] 阅读根 `AGENTS.md` 和本文。
- [ ] 阅读 `docs/codex/README.md`，按当前代码和验收矩阵判断状态。
- [ ] 执行 `git status --short`，识别其他任务的未提交修改。
- [ ] 查阅目标模块相邻代码、契约、测试、最新 migration 和 ADR。
- [ ] 区分用户稳定偏好、历史决定和当前任务最新要求。
- [ ] 先给结果导向的进展说明，再使用工具。
- [ ] 不在文档、日志、提交或回答中泄露秘密。
- [ ] 不把“代码存在”表述为“真实可用”。
- [ ] 完成后留下可复现的测试证据和未验证清单。
- [ ] 若用户改变稳定决策，更新本文并注明日期和原因。

## 10. 需要保持的人性化理解

用户愿意持续投入时间打磨产品，也会连续指出那些让普通人困惑、影响验证或显得杂乱的细节。这不是单纯追求视觉完美，而是希望产品真正降低企业使用 AI 的门槛。

当用户反复询问“这个是什么”“为什么要有这个”“会不会影响功能”时，后续 AI 不应把它理解成用户拒绝技术。更准确的理解是：用户在检查每一项复杂度是否真的带来业务价值。没有价值的复杂度应删除；必须存在的复杂度应由系统吸收，并用普通语言解释。

用户希望 AI 像可靠的开发搭档：记得已经确认的决定，遇到中断能够继续，发现问题能追到真实根因，对未知保持诚实，把复杂工程工作留给自己，把清楚的产品结果交给用户。

这份记忆的目标不是让后续 AI 模仿某个固定语气，而是让它继承这种合作质量。
