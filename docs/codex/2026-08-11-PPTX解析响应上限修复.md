# PPTX 解析响应上限修复与真实验收

## 问题

知识库中的 `130个经典商业模型PPT(可编辑PPT).pptx` 首次处理失败，安全错误码为
`DOCUMENT_PARSER_INVALID_RESPONSE`。源文件大小为 18,549,393 字节，包含 133 张幻灯片；
它是合法的 Open XML 演示文稿，不是损坏文件。

对同一源文件直连受控 Docling 服务复现后确认：服务返回 HTTP 200、`status=success`，
Markdown 正文为 48,194 字符，但同时请求 Markdown 和完整 Docling JSON 时，HTTP 响应达到
65,958,620 字节，超过 API 的 32 MiB 非可信解析器响应上限。因此 API 按设计拒绝该响应，
并将内部原因收敛为安全错误码；不是向量模型或 Qdrant 连接失败。

文件内包含较多旧式 WMF 图片，Docling 会跳过无法加载的 WMF/异常图片对象。可编辑文本仍能
从 PPTX XML 中提取，这些图片警告不是本次整份文档失败的根因。

## 修复

1. PPTX 只向 Docling 请求 Markdown 投影，不再请求体积庞大的完整结构 JSON。
2. PPTX 的可编辑文本直接来自 Open XML，因此关闭对每个嵌入图片的冗余 OCR；PDF 和图片上传
   仍保留 OCR。
3. Markdown-only 返回没有 `json_content` 时，生成正式的
   `enterprise-knowledge-document/v1` 分页文档投影，保留文本、解析器、MIME 和幻灯片页边界。
4. 其他文档类型仍要求并校验 Docling 结构 JSON，未放宽非可信响应校验或 32 MiB 安全上限。
5. 同时修正知识处理队列优先级：已经到可执行时间的任务中，先处理尝试次数更少的新任务，
   避免用户手工“重试”长期排在大量正在退避的文件夹失败任务之后。
6. 管理端仅在用户打开“运行状态”页签时挂载运行诊断组件，避免隐藏页签继续发起昂贵的关系
   概览查询并耗尽数据库连接。

## 真实结果

- 同一文件 Markdown-only 响应为 101,150 字节，正文长度与完整模式一致，响应从约 62.9 MiB
  降到约 98.8 KiB。
- 正式知识管理服务重试任务达到 `READY / SUCCEEDED / 100%`，无错误码。
- 文档与版本均为 `READY`，当前版本指向本次成功版本，解析器为 `docling-serve-v1`。
- 解析质量分为 `0.9989`，结构化投影大小 194,684 字节。
- 生成 53 个知识切片，合计 49,923 个切片字符；版本元数据保留 `pageCount=133`。
- PostgreSQL 中 53/53 个切片具有 1,536 维
  `local-fastembed:BAAI/bge-small-zh-v1.5:pad-1536-v1` 向量。
- 该知识库的独立 Qdrant collection 中精确过滤到 53 个对应版本的向量点。

## 验证命令

- Docling 真实文件诊断：完整响应 65,958,620 字节；Markdown-only 响应 101,150 字节。
- `vitest`：Docling 适配器与处理队列仓库共 15 项测试通过。
- `pnpm --filter @enterprise/api typecheck`：通过。
- `pnpm --filter @enterprise/api build`：通过。
- `pnpm --filter @enterprise/admin typecheck`：通过。
- API 重启后 `/health/ready`：`ready`，AI Runtime：`up`。

## 范围说明

本次没有提高解析器响应上限，也没有把不受控的大型 Docling JSON 写入业务数据库或对象存储。
这样既修复大型 PPTX，又保留了响应体上限、UTF-8、结构与控制字符校验。对于主要由扫描图片
组成、没有可编辑文本的演示文稿，后续可增加“图片型 PPT OCR”显式模式；不应默认让所有企业
PPT 承担逐图 OCR 的耗时和资源成本。
