# 知识入库切片与索引性能优化

日期：2026-08-12

## 结论

页面长时间停留在“切片与索引”不等于切片函数慢。`chunkKnowledgeDocumentWithParents` 是同步、确定性的内存计算；原链路在 `INDEXING/80%` 下串行执行 Embedding 每 64 条一批、Qdrant 每 64 条 `wait=true` 写入，以及 PostgreSQL 事务内逐条向量 UPSERT。

本次不修改任何切片规则和输出，只优化索引阶段：

- Embedding 仍然最多 64 条一批，最多两批有限并发；`Promise.all` 结果按批次输入顺序重组，继续校验模型、维度、数量和向量有效性。
- Qdrant 单批由 64 调整为 128，继续串行并保留 `wait=true`，避免数据库 READY 时外部索引尚不可检索。
- PostgreSQL 向量由逐条 UPSERT 改为每 64 条一个参数化批量 UPSERT；仍在原租户事务和文档锁内，保留复合键冲突更新、租约校验和原子 READY。
- Worker 进度细分为 65% 生成向量、78% 写入检索索引、90% 保存切片与向量；管理端不再把三段都显示成笼统的“切片与索引”。
- 每个成功任务输出 `knowledge.ingestion.stage_timings` 结构化日志：安全扫描、解析、结构化对象、真实切片、Embedding、检索索引、PostgreSQL 持久化和总耗时，同时记录源字节、页数、字符数、父块/子块数、Embedding 批次数与输入 Token。

## 质量不下降证据

- 切片实现文件没有修改。现有固定测试继续校验 Markdown 标题路径、换行归一化、确定性内容哈希、稳定 overlap、父子关系和切片顺序。
- 新增 Embedding 129 条测试，验证恰好三批、最大并发为 2，并验证返回向量仍严格对应原 129 条输入顺序。
- 新增 Qdrant 129 条测试，验证写入为 128 + 1 两个 `wait=true` 批次。
- 目标测试共 54 项通过，包括切片快照/谱系、Worker 租约、完整入库处理、Embedding 契约和 Qdrant 写入。
- 修改前已有不可变真实检索 Run `9194abab-d955-4d0c-96a4-1fe63efb9893`：200/200，Recall@5=1、MRR=1、nDCG@10=1、无答案准确率=1、ACL 泄漏=0、P95=2495.5205ms。该 Run 是技术基线，不冒充本次修改后的重跑结果。

## 现场基线与边界

2026-08-12 修改前数据库快照：PENDING 353、RUNNING 4、SUCCEEDED 824、FAILED 366。过去 24 小时 795 个成功任务按 `created_at → finished_at` 计算 P50=18437.58 秒、P95=41662.03 秒；该值包含排队等待和多次恢复，不是纯处理耗时，因此只能作为批量墙钟基线，不能用于推断 chunker 耗时。

现场资源快照：Docling 重启计数 31、运行中、非 OOMKilled；约 599.55% CPU、3.914GiB 内存。Qdrant 约 0.20% CPU/651.4MiB，PostgreSQL 约 5.07% CPU/503.5MiB。该瞬时证据更支持“解析服务是当前批量吞吐主要压力源”，所以没有提高 Docling 并发，`KNOWLEDGE_INGESTION_BATCH_SIZE=1` 保持不变。

历史数据中存在 9 个 READY 版本无切片、27 个 READY 版本有切片但缺至少一个 PostgreSQL embedding 的记录；这可能包含语义索引启用前或旧索引版本数据，不能在没有版本上下文时直接判定为本次一致性故障。新任务仍以同一事务写切片、向量和 READY，Qdrant 写入失败时不会进入该事务。
