# 知识库网关与向量索引版本化

日期：2026-08-06

## 1. 本次目标

本次改造完成两件事：

1. 增加稳定的 Knowledge Gateway 边界，使 Agent Run、评测、知识管理和来源同步不再直接依赖具体的检索/入库实现。
2. 将原先以 1536 维为部署默认值的向量配置，提升为知识库级、索引版本级配置，支持在不覆盖当前可用索引的前提下重建并切换模型。

1536 现在只是新部署的默认值，不再是 PostgreSQL 向量字段、检索条件或 Qdrant 集合的固定约束。

## 2. Knowledge Gateway 边界

### 2.1 端口划分

- `KnowledgeRetrievalGateway`：无请求状态的检索端口，调用者必须显式传入租户和用户上下文。Agent Run、知识检索评测等后台/单例组件使用该端口。
- `KnowledgeEvaluationGateway`：面向评测的窄端口，只返回版本化的不透明快照和受治理语料，不向评测代码暴露知识表、向量或图谱存储布局。
- `KnowledgeGateway`：在检索端口之上增加上传、版本、发布、归档、重建索引等管理能力。管理后台和知识来源同步使用该端口。

Agent Run 的提交前证据复核现在使用 `KnowledgeRetrievalGateway.areChunksAccessible`。该端口不接收 Prisma transaction；知识边界自行建立读取事务，避免以“本地扩展”方式重新耦合业务数据库实现。

当前提供进程内适配器：

```text
业务模块
   │
   ├─ KnowledgeRetrievalGateway ── InProcessKnowledgeRetrievalGateway
   │                                  └─ KnowledgeRetrievalService
   ├─ KnowledgeEvaluationGateway ────┘
   │
   └─ KnowledgeGateway ─────────── InProcessKnowledgeGateway
                                      ├─ KnowledgeRetrievalGateway
                                      └─ KnowledgeIngestionService
```

以后若知识库拆成独立服务，只需新增 HTTP/gRPC 适配器并替换依赖注入绑定；Agent Run、管理 API 和评测模块不需要改成绑定 Qdrant、OpenAI、BGE 或 FastEmbed。

### 2.2 为什么分成两个 Gateway

`KnowledgeIngestionService` 使用请求级租户上下文，不能让它通过一个单一的请求级 Gateway 传播到 Agent Run 的单例 Prisma 仓储。检索端口因此保持无状态，并要求显式授权上下文；管理/入库端口继续使用现有 API 权限和租户上下文。这一拆分既保留模块化，也避免 NestJS 作用域被意外扩大。

## 3. 索引版本数据模型

每个知识库可拥有多条 `KnowledgeEmbeddingIndexVersion`：

| 字段                 | 含义                                        |
| -------------------- | ------------------------------------------- |
| `version`            | 知识库内递增的索引版本号                    |
| `provider` / `model` | 生成该版本向量的提供方与模型                |
| `dimensions`         | 此版本的真实向量维度，允许 1～16000         |
| `distance`           | 相似度距离策略，当前为 cosine               |
| `normalization`      | 向量归一化策略                              |
| `collection`         | 对应的外部向量集合名                        |
| `status`             | `BUILDING`、`ACTIVE`、`RETIRED` 或 `FAILED` |
| `failureReason`      | 构建失败原因                                |

知识库保存 `activeEmbeddingIndexVersionId` 和 `pendingEmbeddingIndexVersionId`。知识切片的向量记录保存 `embeddingIndexVersionId`，因此同一切片可以在切换期间同时保留旧模型和新模型的向量，检索只读取当前生效版本。

PostgreSQL 中向量列已由 `vector(1536)` 改为无 typmod 的 `vector`，并通过 `vector_dims()` 与索引版本维度进行一致性校验。PostgreSQL 继续保存业务事实、版本元数据和精确向量回退；Qdrant 按索引版本集合承接主要的高规模语义检索。

## 4. 安全切换流程

```text
AI Runtime 暴露当前 Embedding 能力
                │
                ▼
管理员创建 BUILDING 版本
（绑定 provider/model/dimensions/collection）
                │
                ▼
对现有文档执行重建
新旧版本向量并存，ACTIVE 版本继续服务
                │
                ▼
系统校验所有 READY 切片的内容哈希与向量覆盖
                │
       ┌────────┴────────┐
       │覆盖不足          │100% 覆盖
       ▼                 ▼
拒绝切换并给出缺口      事务内原子切换
                       旧版 RETIRED
                       新版 ACTIVE
```

- Runtime 返回的模型或维度与目标索引版本不一致时，API 返回冲突错误，不会把错误维度写入索引。
- 没有可用索引或多个知识库的生效版本不兼容时，检索显式降级到关键词模式，不混用不同维度的向量。
- 新建知识库在 Embedding Runtime 可用时自动创建 v1；Runtime 不可用时仍可先使用关键词检索。
- 管理端“知识库设置”已增加“向量模型与索引版本”面板，显示当前版本、待切换版本、Runtime 能力和历史版本，并提供创建、覆盖校验和激活操作。

## 5. 运行与存储边界

- 原始文件：仍由知识对象存储适配器保存，生产建议使用 S3/MinIO；PostgreSQL 只保存对象键、来源、版本和治理元数据。
- 解析文本、切片、实体关系和业务状态：PostgreSQL。
- 大规模向量召回：Qdrant，集合与索引版本绑定。
- 精确向量回退与一致性数据：PostgreSQL + pgvector，但不再创建混合维度 HNSW 索引。
- 向量化和重排：Python AI Runtime，通过期望模型和期望维度进行握手校验。
- 业务调用：统一经 Knowledge Gateway；未来可把进程内适配器替换为远程适配器。

## 7. 仍需生产验证或后续增强

1. 当前单个 AI Runtime 实例仍只暴露一套 Embedding provider/model。索引版本已经能校验和安全切换，但若多个知识库要同时使用不同模型，需要在 Runtime 前增加模型路由器或运行多实例池。
2. 跨多个不兼容索引版本的联合搜索目前降级为关键词搜索；后续可分别执行各版本语义召回，再按规范化分数/RRF 合并。
3. 管理端目前沿用逐文档重建操作。可增加“重建全部文档”的异步批处理、进度和失败重试，进一步降低非技术管理员的操作成本。
4. 尚未验证生产模型端点、生产 Qdrant 集群、生产 S3/MinIO、备份恢复、高并发和大规模数据压测。
