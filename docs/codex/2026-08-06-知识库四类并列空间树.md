# 知识库四类并列空间树

- 日期：2026-08-06
- 状态：已实现并在本地开发环境验收

## 1. 产品决定

知识中心采用四个同级根节点：

```text
知识中心
├─ 公司知识
│  └─ 当前企业
│     └─ 知识库
│        └─ 文档、版本、切片、向量和关系
├─ 部门知识
│  └─ 具体部门（显示完整组织路径）
│     └─ 知识库
├─ 项目知识
│  └─ 具体项目
│     └─ 知识库
└─ 成员知识
   └─ 具体成员
      └─ 知识库
```

这里的“同级”非常重要：公司、部门、项目和成员是四种知识存放位置，不是“公司包含部门、部门包含项目、项目包含成员”的单一路径。管理端即使某一类没有数据，也始终显示四个根节点，帮助非技术管理员形成稳定心智模型。

各空间的推荐资料如下：

| 根空间   | 典型内容                                     |
| -------- | -------------------------------------------- |
| 公司知识 | 企业战略、经营目标、公司制度、公共知识       |
| 部门知识 | 部门职责、部门目标、工作流程、专业方法       |
| 项目知识 | 项目目标、方案、过程记录、交付物、复盘经验   |
| 成员知识 | 员工技能、岗位知识、个人方法、可复用工作经验 |

## 2. 小白用户流程

### 2.1 上传资料

1. 管理员进入“知识中心 → 知识库与文档”。
2. 点击“上传资料”。
3. 先在四张并列卡片中选择公司、部门、项目或成员。
4. 部门空间选择完整组织路径；成员空间选择真实成员；项目空间可选择已有知识项目或输入新项目名称。
5. 选择“全公司成员可访问”或“仅指定部门或成员可访问”；部门可以包含下级部门，部门与成员按满足任一条件计算。
6. 拖入文件并创建草稿知识库。
7. 系统继续执行既有的文件对象存储、解析、切片、向量索引和关系图谱流程。

上传弹窗明确区分三个概念：知识归属账号由服务端固定为当前登录账号；公司、部门、项目和成员只表示树中的知识存放位置；谁能检索则由全公司/指定部门/指定成员访问范围、文档发布状态和知识授权策略共同决定。成员知识的目标成员同样固定为当前登录账号，界面不提供代其他成员选择的下拉框，API 也不会信任客户端提交的其他成员 ID。同一批上传文件共享创建时选择的访问范围，后续添加到该知识库的文件和新版本继承该范围。

### 2.2 浏览与调整

- 左侧树按“根空间 → 目标对象 → 知识库”展开，知识库仍是文档治理、索引、检索测试和关系图谱的工作单元。
- 搜索可按知识库名称、知识库 key 或目标对象名称过滤。
- 知识库设置中可调整存放位置；部门位置由 API 重新校验，成员位置强制绑定当前登录账号，不相信浏览器提交的成员 ID 或显示名称。
- 知识库设置中可调整访问范围；API 会校验指定部门以及指定成员的启用和有效任职状态，智能体检索和引用原文时再次复核。
- 详情页标题显示“根空间 / 目标对象”，避免重复显示知识库名称。

## 3. 数据与契约

`KnowledgeBase` 新增三个知识边界自有字段：

| 字段              | 含义                                                   |
| ----------------- | ------------------------------------------------------ |
| `spaceType`       | `COMPANY`、`DEPARTMENT`、`PROJECT` 或 `MEMBER`         |
| `spaceTargetId`   | 该企业、部门、项目知识空间或成员的稳定 UUID            |
| `spaceTargetName` | 显示名称快照，用于稳定渲染树，不作为权限或事实权威来源 |

公共响应返回：

```json
{
  "space": {
    "type": "DEPARTMENT",
    "targetId": "00000000-0000-7000-8000-000000000010",
    "targetName": "产品中心"
  }
}
```

创建或编辑采用判别联合：公司不接收伪造目标；部门和成员只接收目标 UUID；项目接收名称和可选的已有项目空间 UUID。服务端解析后才生成上述规范响应。

## 4. 服务端校验规则

- 公司：以当前租户 ID 和租户正式名称为准。
- 部门：必须是当前租户中未归档的组织单元，显示名称取服务端记录。
- 成员：必须是当前租户中启用的成员，显示名称取成员正式资料。
- 项目：已有项目空间按 UUID 在知识边界内复用名称；新项目空间由知识边界生成 UUID。

项目当前没有绑定仓库中的正式 Project 表，因为项目业务模块尚未提供权威 Project 实体。此处只建立知识空间身份，不冒充已经建立项目业务外键。未来项目模块落地后，应通过 Knowledge Gateway 或公共 API 绑定正式项目 ID；项目模块不得读取 `knowledge_bases`。

## 5. 迁移策略

迁移 `20260806000200_knowledge_space_hierarchy`：

1. 创建 `KnowledgeSpaceType` 枚举。
2. 增加三个空间字段和树形查询索引。
3. 将现有扁平知识库归入当前租户的公司空间。
4. 不修改知识库状态、文档版本、部门可见范围、切片、向量或关系。

因此旧数据不会丢失，也不会因为目录升级而扩大权限。

## 6. Knowledge Gateway 红线

四类空间没有改变既定依赖方向：

- 管理端通过知识公共 HTTP API 管理空间。
- NestJS 业务模块需要知识能力时，通过 `KnowledgeGateway`、`KnowledgeRetrievalGateway` 或 `KnowledgeEvaluationGateway`。
- 异步消费者通过版本化知识事件，再按需调用 Gateway/API。
- 项目、成员、智能体、评测和第三方不得访问知识表、Qdrant collection、对象存储路径或知识内部类。

空间归属元数据仍由知识边界拥有。若未来需要“按项目自动选库”或“获取成员技能知识”，应新增 Gateway 用例并在知识边界内完成访问过滤，不能在项目或成员服务中联表查询知识库。
