# 明略 OCTO 可借鉴能力与本项目可用性改进计划

> 分析对象：[`Mininglamp-OSS`](https://github.com/orgs/Mininglamp-OSS/repositories) 公开开源项目
> 对标项目：企业 AI 协同平台（本仓库）
> 基线日期：2026-07-31
> 文档状态：V2.0，已将主线从“部署 OCTO”纠正为“提炼可借鉴能力并提升本产品可用性”

## 1. 结论先行

本次不建议部署 OCTO，也不建议把本项目替换成 OCTO 的 Go、MySQL、WuKongIM 技术栈。

OCTO 对本项目最有价值的不是底层架构，而是它把复杂能力包装成了普通员工能直接使用的产品入口：聊天是主界面，Agent 是通讯录和会话中的一等成员，会话可以直接生成摘要和行动项，Skill/MCP 可以浏览和安装，运行时状态能被用户看懂。

本项目的问题并非“后端能力少”。相反，本项目已经拥有 OCTO 没有展示出同等深度的企业治理能力，包括 PostgreSQL RLS、业务语义主链、可靠 Outbox、受治理 Agent Run、Tool Gateway、权限感知知识引用、评测、记忆和 FinOps。当前可用度低的核心原因是：

1. 高频员工流程没有形成完整闭环。聊天目前只有直接会话和文本主链，群聊、消息分页、已读/未读、撤回、富媒体、WebSocket 和系统通知仍明确列为未完成。
2. “聊天、任务、知识、工具、Agent”都已有基础能力，但用户需要在不同模块之间理解大量内部概念，聊天内容不能顺手转成摘要、任务或证据。
3. Agent 有运行就绪度和授权判断，但缺少一个面向普通员工的“我现在可以用哪个 Agent、它能做什么、为什么不可用”的低门槛入口。
4. Tool Gateway 已具备风险、审批、补偿和对账，但入口绑定在具体任务的高级工具面板中，尚未形成可搜索、可理解、可按 Agent 启用的能力目录。
5. 桌面端几个核心工作区文件已达到 642～1322 行，显示业务状态集中、组件职责过重。它不直接证明界面难用，但已经是交互继续叠加前必须处理的维护风险。

因此，近期产品优先级应调整为：

| 优先级 | 应先做什么                       | 用户得到的结果                                             | OCTO 参考对象                                          |
| ------ | -------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| P0     | 补齐消息基本盘                   | 聊天真的能作为日常工作入口使用                             | `octo-web` 的会话、群组、消息类型、搜索、撤回和反应    |
| P0     | 会话一键转工作                   | 聊完即可得到可编辑摘要、任务草稿和来源                     | `octo-smart-summary` + `octo-matter`                   |
| P0     | Agent 可发现、可解释、可直接调用 | 用户知道该找谁、能做什么、为何不可用                       | `octo-web` Bot 资料页 + `octo-daemon-cli` 状态模型     |
| P1     | 能力中心                         | 用户按场景找到并启用 Tool/Skill/MCP，而不是填写底层 Schema | `octo-marketplace` + `dmworkskillmarket` + `dmworkmcp` |
| P1     | Runtime 中心                     | 管理员看到运行时、版本、绑定、健康和升级状态               | `octo-daemon-cli` + `octo-fleet`                       |

一句话策略：**借 OCTO 的产品壳和闭环，保留我们的治理内核。**

## 4. OCTO 中真正值得借鉴的东西

### 4.1 消息工作台：把沟通做成稳定主入口

`octo-web/packages/dmworkbase` 中已经形成较完整的消息产品面：

- 会话列表分类与排序；
- 群组创建、成员选择、群管理和频道设置；
- 文本、图片、文件、视频、语音、富文本、合并转发、撤回消息；
- 消息反应、输入中状态、@ 提及；
- 会话内搜索、跨会话全局搜索、文件/媒体筛选和定位上下文；
- AI 消息卡、交互卡片和摘要卡片；
- Bot 资料、管理入口和 AI 身份标识。

对本项目的借鉴方式：

- 复用“会话是主工作区”的信息架构和状态矩阵。
- 在现有 `conversation` 模块上增量补齐消息能力，不移植 WuKongIM 数据模型。
- 消息正文继续由本项目保存事实、ACL、审计和 Agent Run 关联；实时层可以按既定技术方案接腾讯云 IM 或自有 WebSocket。
- 先完成消息可靠性和基础协作，再做更多办公套件。

### 4.2 Agent 是联系人，不是后台配置项

OCTO 的产品表达始终把 Bot/Agent 放在通讯录、资料卡、单聊、群聊和 @ 提及里，而不是只放在管理后台。`octo-daemon-cli` 又把运行时、版本、插件和绑定状态上报给平台，用户能够把“这个 Agent 是谁”和“它现在是否能工作”联系起来。

本项目已经有“联系本人 / 联系智能体”和运行就绪度判断，下一步不是重做身份模型，而是补齐以下呈现：

- Agent 能做的 3～5 个典型任务；
- 使用的知识范围、工具类别和高风险动作提示；
- 可用、降级、不可用三态，以及一条人能理解的原因；
- “立即提问”“带着当前任务提问”“查看最近结果”三个动作；
- 管理员可见的修复入口，普通员工只看简洁说明。

### 4.3 会话侧栏总结：把聊天结果沉淀下来

`octo-web/packages/dmworksummary` 不是一个孤立页面，而是可以嵌入当前聊天的可调整侧栏，包含列表、新建、详情三个视图。代码中还能看到：

- 创建、查看和取消总结；
- 个人报告与团队汇总；
- 引用来源；
- 编辑、按意见调整、全部重新生成；
- 版本记录、历史预览与恢复；
- 定时更新、参与者确认与分享；
- 结构化生成流程状态。

`octo-smart-summary` 后端将输出约束为重点、决策、未决问题和候选行动，并按发言人和时间边界切分长对话；结构化 JSON 无效时会做受限的再次生成。

对本项目的借鉴方式：

- 首版只做“当前会话总结”，不做全量定时总结平台。
- 输出必须带来源消息 ID，并延续本项目的可信引用和权限快照。
- 总结先成为可编辑草稿，用户确认后才生成任务、证据或交付物。
- 生成过程复用 Agent Run、流式事件、取消、重试、配额和评测，不另起一套 LLM 调用链。

### 4.4 Matter：借任务抽取模式，不借第二套任务系统

`octo-matter` 的高价值设计有三点：

1. 每个 matter 自带追加式 timeline，状态变化、评论和抽取结果可以追踪。
2. 自由文本或聊天片段先转成结构化任务草稿，包含标题、描述、截止时间、负责人和来源消息。
3. 访问控制同时考虑创建者、负责人、参与者和关联频道，通知可进入 OCTO IM 或 Webhook。

本项目已有更完整的 Objective → Task → Deliverable → Acceptance → Evidence 主链，所以不能直接接入 `octo-matter` 数据库。应该只借它的“抽取—确认—落库—回链”流程：

```text
选择消息/当前会话
        ↓
生成摘要与行动项草稿
        ↓
用户编辑负责人、截止时间、目标和证据
        ↓
写入本项目现有 Task / Evidence
        ↓
在原会话显示已创建任务卡片和双向链接
```

### 4.5 Skill/MCP 市场：把 Tool Gateway 变成可发现的能力中心

`octo-web/packages/dmworkskillmarket` 和 `dmworkmcp` 已包含：

- 名称/描述搜索、分类和标签筛选；
- 下载量、版本、发布者和平台认证标识；
- 详情、版本记录、发布、编辑、删除和安装提示；
- MCP 列表、详情和连接探测。

`octo-marketplace` 的后端契约还覆盖空间级可见范围、私有资源存在性隐藏、软删除、标签聚合、MCP `initialize + tools/list` 探测，以及 Skill 制品的哈希校验、安全解压和原子替换。

本项目不应允许普通员工下载任意可执行包。建议把市场模型改造成受治理的“企业能力中心”：

- 管理员发布 Tool/MCP/Skill 版本并完成安全审查；
- 员工按业务场景浏览，只能启用租户策略允许的能力；
- Agent 绑定的是不可变能力版本和权限快照；
- 高风险 Tool 继续走现有确认、独立审批、幂等、补偿和对账；
- 市场页面隐藏底层 JSON Schema，使用业务表单和示例任务。

### 4.6 Runtime 中心：把“不可用”变成可诊断状态

`octo-daemon-cli` 会探测本机 Agent CLI、版本、插件和绑定，先快速注册，再异步深度探测，并通过心跳维持在线状态；服务端还能下发升级任务。

本项目可以借它的状态模型，但不应直接采用 OCTO profile、fleet URL 和升级协议。建议在现有 Agent operational readiness 上补充：

- Runtime 实例、主机/节点、驱动、版本和最后心跳；
- Agent 与 Runtime/模型/知识库/工具的绑定关系；
- “配置启用”和“运行可用”分开显示；
- 失败原因分为模型不可达、凭据错误、版本不兼容、绑定缺失、证据过期；
- 首版只做诊断和受控重连，远程升级放在签名、灰度和回滚闭环完成之后。

### 4.7 面向 Agent 的稳定操作面

`octo-cli` 使用内嵌 OpenAPI 元数据自动生成命令，并为 Agent 输出稳定 JSON 信封，支持 schema 查询、dry-run 和非交互调用。其价值不是增加一个 CLI，而是提醒我们：Agent 调用平台时也需要稳定、可发现、可验证的契约。

本项目可在现有 API 与 Tool Gateway 上增加机器可读能力清单和统一执行信封，避免让 Agent 直接拼接内部接口或解析人类界面。

## 5. 复用决策矩阵

| OCTO 能力      | 我们采用什么                                     | 不采用什么                | 复用方式                      |
| -------------- | ------------------------------------------------ | ------------------------- | ----------------------------- |
| 消息工作台     | 会话分类、群聊交互、富媒体状态、搜索、撤回、反应 | WuKongIM 业务表和 Go 服务 | 产品模式 + 契约对照，自有实现 |
| Bot/Agent 资料 | Agent 作为联系人、能力说明、状态与一键对话       | OCTO Bot Token 和绑定模型 | 扩展现有成员/Agent 投影       |
| 智能总结       | 聊天侧栏、结构化输出、版本和来源                 | 独立 Summary 数据孤岛     | 复用现有 Agent Run 与知识引用 |
| Matter         | 聊天转任务草稿、来源消息、append-only 活动       | 第二套任务库和状态机      | 映射到现有 Task/Evidence      |
| Skill 市场     | 搜索、分类、版本、发布者、安装状态               | 任意本地脚本直接安装      | 管理员审核后的能力包投影      |
| MCP 市场       | 可见范围、探测、工具列表、Secret 隔离            | 浏览器直连任意 MCP        | 通过 Tool Gateway 服务端探测  |
| Runtime daemon | 发现、心跳、绑定、版本、诊断                     | OCTO fleet/profile 协议   | 独立适配器或重写探测器        |
| Agent CLI      | 稳定 JSON 信封、schema 发现、dry-run             | 新建一套绕过授权的接口    | 复用现有 API/Tool Gateway     |

### 5.1 可以考虑选择性复用的源码

在许可证和依赖审查后，可考虑移植低耦合的交互算法、数据校验和安全测试思路，例如：

- 摘要侧栏宽度保存、版本恢复和引用展示的交互模式；
- Skill ZIP 的路径遍历防护、哈希校验和原子替换测试用例；
- MCP 探测的 URL 校验、超时、重定向和 SSRF 防护测试矩阵；
- 消息搜索的筛选、分页、定位上下文和竞态测试思路；
- Runtime 快速探测与慢速深探分层模型。

### 5.2 不建议直接复制的源码

- `octo-web` 的消息组件深度依赖其 `dmworkbase`、WuKongIM runtime 和组件体系，整体复制会把对方架构一并带入。
- `octo-matter`、`octo-smart-summary` 和 `octo-marketplace` 是 Go/MySQL 服务，与本项目 NestJS/PostgreSQL/RLS/Outbox 边界不一致。
- 任何带 OCTO Token、Space、Channel 或 Fleet 语义的协议都不应直接成为本项目核心契约。
- 许可证兼容不等于可以忽略 NOTICE、版权声明、依赖许可证和商标边界；正式复制前仍需法律审查。

```mermaid
flowchart LR
    A["员工在工作台或通讯录找到 Agent"] --> B["看到能力、数据范围和实时可用状态"]
    B --> C["进入单聊或群聊并完成协作"]
    C --> D["生成带来源的摘要与行动项草稿"]
    D --> E["人工确认后写入 Task / Evidence / Deliverable"]
    E --> F["Agent 使用已授权 Tool 执行"]
    F --> G["结果、审批、成本与证据回到任务和会话"]
```

该闭环全部建立在本项目现有治理能力上。OCTO 只提供产品形态和交互参考，不成为新的事实系统。

## 7. 依赖顺序与实施计划

### 批次 U0：先让现有能力容易找到和理解（1 周）

目标：不依赖新的外部 IM 服务，先降低首用门槛和界面复杂度。

1. 拆分 `DirectoryWorkspace.tsx`、`MessagingWorkspace.tsx` 和 `TaskToolPanel.tsx`，把查询状态、列表、详情、对话框和业务动作分开。
2. 新建会话列表增加推荐 Agent、最近使用、能力标签、示例问题和可用性原因。
3. 会话头展示 Agent 能力、知识范围、工具风险和降级状态；技术原因放到“查看详情”。
4. 工作台默认只显示“今天要做什么、卡在哪里、下一步是什么”；Value、Strategy、版本、revision 和完整证据链移动到高级详情。
5. 补齐按钮名称、焦点、键盘操作、`aria-live`、错误恢复和自动化可定位属性。

验收标准：

- 已开通账号在 3 分钟内能找到一个可用 Agent 并得到首个有效回答。
- 新建 Agent 会话不超过 3 次主要点击。
- Agent 不可用时，员工看到一条可理解说明；管理员可以进入具体修复页。
- 普通任务首页不要求理解内部版本号、语义实体 ID 或 JSON。
- 桌面端可访问性树能识别导航、搜索、会话列表、消息时间线和输入框。

### 批次 U1：补齐消息基本盘（2～4 周，分小批交付）

依赖顺序：消息分页 → 未读/已读 → 编辑/撤回 → 附件 → 群聊 → 实时连接与通知。

| 子任务            | 后端/数据                                                     | 桌面端                               | 最小验收                            |
| ----------------- | ------------------------------------------------------------- | ------------------------------------ | ----------------------------------- |
| MSG-01 历史分页   | `conversation.ts` 增加 cursor page；repository 使用稳定排序键 | 上拉加载、加载失败重试、保持滚动锚点 | 10 万消息会话可分页；无重复、无跳页 |
| MSG-02 未读与已读 | 成员级 read cursor、unread count、幂等更新                    | 会话未读数、已读位置、聚焦窗口策略   | 多端重入后未读数一致                |
| MSG-03 编辑与撤回 | 版本/撤回事件、权限和时间窗、审计 tombstone                   | 显示“已编辑/已撤回”，失败可恢复      | 越权和超时撤回被拒绝                |
| MSG-04 附件       | 对象存储上传会话、扫描、ACL、内容类型                         | 图片/文件发送、进度、失败重试        | 恶意或超限文件失败且不进入 READY    |
| MSG-05 群聊       | group 会话、成员、角色、邀请/移除事件                         | 建群、成员选择、@人/@Agent、群设置   | 离群成员不能读取新消息              |
| MSG-06 实时与通知 | WebSocket/IM adapter、游标补拉、幂等                          | 断线重连、前后台通知、免打扰         | 断线后不丢消息，通知不泄露敏感正文  |

主要目标文件：

- `packages/contracts/src/conversation.ts`
- `apps/api/src/modules/conversation/`
- `apps/api/prisma/schema.prisma` 与可追踪迁移
- `apps/desktop/src/renderer/src/features/messaging/`
- `apps/desktop/src/renderer/src/features/directory/`

### 批次 U2：会话总结与一键转任务（2 周）

建议新增一个 `conversation-insights` 应用模块，但不新建第二套任务事实表。

功能范围：

1. 用户在当前会话选择“总结本次讨论”。
2. 生成结构化草稿：背景、结论、决策、未决问题、行动项。
3. 每个结论/行动项保存来源消息 ID、会话 ID、生成模型和运行快照。
4. 用户编辑负责人、截止时间、优先级、关联 Objective 和证据。
5. 确认后调用现有任务/证据服务，并在会话插入任务卡片。
6. 支持取消、失败重试、人工编辑和版本查看；首版不做定时总结与跨群团队报告。

建议契约：

```ts
interface ConversationInsightDraft {
  conversationId: string;
  sourceMessageIds: string[];
  summary: string;
  decisions: Array<{ text: string; sourceMessageIds: string[] }>;
  openQuestions: Array<{ text: string; sourceMessageIds: string[] }>;
  actions: Array<{
    title: string;
    description: string;
    assigneeUserId: string | null;
    dueAt: string | null;
    sourceMessageIds: string[];
  }>;
  runSnapshotId: string;
  version: number;
}
```

验收标准：

- 摘要中的每条决策和行动项都能回到来源消息。
- 未经用户确认不创建正式任务。
- 被撤销权限的消息不再进入重新生成输入。
- 创建出的 Task 进入现有业务语义、权限、Outbox 和审计链路。
- 失败不会留下半创建的 Task/Evidence 组合。

### 批次 U3：Agent 资料与能力中心（2 周）

#### Agent 资料卡

- 输入：现有成员、Agent、Blueprint/Version、知识授权、工具授权和 operational readiness。
- 输出：业务名称、负责人、适用场景、示例问题、数据范围、工具类别、最近更新时间和可用状态。
- 入口：通讯录、全局搜索、新建会话、任务“问 Agent”。

#### 能力中心

- 将现有 `AvailableTool` 提升为可浏览的能力投影，不改变 Tool Gateway 的可信执行边界。
- 增加名称、业务描述、分类、标签、发布者、版本、风险级别、数据范围、示例任务和适用 Agent。
- 管理员负责发布、审查、停用和回滚；员工只进行“申请/启用到我的 Agent”或“在当前任务中使用”。
- MCP 探测必须在服务端执行，并复用最小权限、超时、SSRF 防护、Secret 隔离和审计。

验收标准：

- 用户可以按业务目标而不是技术 ID 找到能力。
- 禁用、未授权或运行不就绪的能力不会显示为可执行。
- 启用操作固定不可变版本，保留审批人、时间和策略快照。
- 高风险工具仍必须经过现有确认/独立审批，市场入口不能绕过治理。

### 批次 U4：Runtime 中心（1～2 周）

1. 在管理端增加 Runtime 列表和详情。
2. 聚合运行时状态、驱动、模型、版本、绑定、最近心跳和失败原因。
3. 提供探测刷新、受控重连和诊断下载。
4. 远程升级必须等代码签名、版本 pin、灰度、回滚和审计完成后再开放。

验收标准：

- “Agent 不可用”能在两级页面内定位到具体阻断项。
- 心跳过期不会继续显示在线。
- 配置启用但真实运行不可用时，状态保持不可用。
- 普通员工不看到密钥、内部地址和堆栈信息。

## 9. 产品指标与发布门禁

### 9.1 可用性指标

- 首次有效 Agent 回答中位时间 ≤ 3 分钟（已完成账号和 Agent 配置的用户）。
- 新建 Agent 会话主要点击数 ≤ 3。
- 消息发送成功率 ≥ 99.9%，重连后消息缺失率为 0。
- 会话总结生成成功率 ≥ 95%，结构化解析失败必须可见且可重试。
- 总结转任务后来源消息可追溯率 = 100%。
- “Agent 不可用”原因可诊断覆盖率 = 100%，不得只显示笼统失败。
- 普通员工核心任务的人工 UAT 完成率 ≥ 90%。

### 9.2 不得降低的治理门禁

- 租户隔离、资源 ACL、RLS 和默认拒绝。
- Agent/用户/租户/资源五层工具授权交集。
- 高风险动作的人工确认或独立审批。
- 消息、摘要、任务、附件和引用的来源与权限版本。
- 幂等、Outbox、重试上限、补偿、审计和成本记录。
- 真实外部供应商、非空知识数据和目标客户端 UAT 未通过时不得宣称生产可用。

## 10. 不进入近期范围的 OCTO 能力

- 不部署 OCTO 全套服务作为本项目依赖。
- 不迁移到 Go/MySQL/WuKongIM。
- 不新建与现有 Task 并行的 Matter 主数据。
- 不立即建设邮件服务器、协作文档、完整移动端或音视频会议。
- 不在客户端直接安装未经管理员审核的 Skill 或访问任意 MCP。
- 不在签名、灰度、回滚和审计闭环前开放远程自升级。
- 不用仓库星数、README 描述或本地 HTTP 200 代替真实用户 UAT。

## 12. 风险与未验证项

1. 本轮没有运行 OCTO，所有交互判断来自公开源码、测试、契约和 README，不构成 OCTO 生产验收。
2. 当前 Electron 可访问性检查不足以替代真实用户人工走查，必须按目标角色录屏验证完整任务。
3. 本项目现有消息供应商、对象存储和 WebSocket/IM 接线仍需真实环境验证。
4. 会话总结涉及消息正文派生数据，必须继承原消息 ACL、删除/撤回和保留策略。
5. 能力市场会扩大供应链攻击面，必须有制品签名、哈希、恶意文件扫描、依赖审计和发布者治理。
6. Runtime 远程升级具有高运维风险，不能因为 OCTO 已实现类似功能就提前开放。
7. Apache-2.0/MIT 仓库的具体文件、依赖和 NOTICE 仍需逐项确认；本报告不是法律意见。

## 13. 下一步建议

按“可用度优先”推进时，建议先实施 `UX-001 + UX-002 + MSG-001`：拆分复杂工作区、强化 Agent 能力入口、补消息分页。它们能改善当前日常体验，也是后续群聊、摘要和能力中心的共同基础。

随后实施 `INS-001 + INS-002`，优先打通“聊天 → 有来源的摘要 → 人工确认 → 任务/证据”这一条最能体现本项目差异化的闭环。能力中心和 Runtime 中心放在该闭环稳定之后。

部署 OCTO 只在未来需要做同场景竞品 UAT 时作为独立、可销毁的评估环境使用，不再作为本项目近期实施目标。
