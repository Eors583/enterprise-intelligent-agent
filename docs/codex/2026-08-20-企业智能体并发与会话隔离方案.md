# 企业智能体并发与会话隔离方案

日期：2026-08-20

实施状态：P0 已于 2026-08-20 落地；2026-08-21 又完成了输入消息回答槽位、Outbox 领取阶段会话队首过滤和 200 条冷启动积压配额验证。P1 的供应商并发舱、公平调度、生产多副本与真实模型容量压测仍待实施和验收。

## 1. 结论

企业里的“一个智能体”应当被理解为一份可复用的智能体配置，而不是一个只能服务一名用户的常驻会话进程。同一智能体必须能够同时产生多个 Agent Run；每个 Run 绑定自己的租户、会话、提问消息、发起人权限和执行快照，Run 之间不共享可变对话上下文。

系统也不能承诺“无限请求同时执行”。正确目标是：所有合法问题都能被可靠接收，执行并发有明确上限，超出容量后公平排队，扩容后继续处理；任何排队、重试、取消、超时或乱序完成都不能造成跨租户、跨用户、跨会话串话。

本项目建议采用以下并发模型：

- 同一个智能体、不同会话：并发执行。
- 同一个会话、连续多个问题：全部接收，按消息顺序执行，首版保持每个会话最多一个运行中的 Run。
- 不同租户：数据、配额、队列和权限完全隔离。
- 同一模型供应商：按供应商账号和模型设置独立并发舱与速率限制，不能用一把全局锁串行所有智能体。
- 超出执行能力：进入持久化队列并显示“等待处理”，不能拒绝消息、丢消息或假装已经回答。

## 2. 实施前代码核对结果

当前代码已经具备一部分正确基础，但默认容量和同会话交互方式还达不到企业多人稳定使用的目标。

### 2.1 已有的正确隔离

1. `AgentRun` 已持久化绑定 `tenantId`、`conversationId`、`inputMessageId`、`requesterUserId`、`agentId` 和 `agentVersionId`。
2. 输入消息与输出消息通过包含租户、会话的复合外键关联，降低把回答写入其他会话的风险。
3. Run 幂等键是租户内唯一的，外部 Runtime Run ID 也有租户和供应商范围内的唯一约束。
4. 流式事件以 `(tenantId, runId, sequence)` 唯一，桌面端读取接口同时携带 `conversationId` 和 `runId`。
5. 上下文加载按精确的 `tenantId + conversationId` 查询，并且只读取当前提问消息之前的消息，不是按 `agentId` 读取“这个智能体最近看过的内容”。
6. 不同用户访问同一个员工智能体时，会话键包含提问人和被代表员工：`member-assistant:{requesterUserId}:{ownerUserId}`。因此不同提问人不会天然共用一份对话历史。
7. Worker 使用持久化 Outbox、租约和批量 claim，单个 Worker 内通过独立任务并发处理多个 Run；Python Runtime 的锁只用于维护以 `runId` 为键的活动任务表，没有包住整个模型请求。
8. Run 已保存策略、模型路由、记忆和协作上下文快照，知识检索按当前 Run 的发起人重新做授权。

这些约束说明当前主干设计不是“一个智能体一把锁”，也没有发现按智能体共享全局对话文本的实现。

### 2.2 当前会让多人使用出问题的点

#### A. 默认总容量只有 4 路

- `Tenant.agentRunConcurrencyLimit` 默认是 4。
- `AGENT_RUN_WORKER_CONCURRENCY` 默认也是 4，而且环境校验当前最多只允许配置到 8。
- 租户第 5 个处于执行阶段的 Run 会被延后 2 秒再次尝试。

这不会直接造成串话，但会造成多人同时提问时排队、反复等待，容易被用户感知为“智能体出问题”。仅增加某一处数字也不够：租户配额、Worker、Runtime 实例、模型供应商配额必须一起核算。

#### B. 同一会话有活动 Run 时，第二个问题被直接拒绝（本次 P0 已修复）

实施前，消息创建事务会检查同一会话中的 `QUEUED / DISPATCHING / RUNNING / UNKNOWN` Run；只要存在就抛出 `ActiveAgentRunConflictError`，API 返回冲突。

这保证了同一会话不乱序，却没有做到“多个问题都能可靠接收”。更合适的行为是保存第二条消息并创建第二个 `QUEUED` Run，然后由已有的 `EARLIER_AGENT_RUN_ACTIVE` 规则按会话顺序执行。

#### C. 桌面端以“当前会话的一个活动 Run”为中心（本次 P0 已修复）

实施前，`ConversationWorkspace` 只选择一个 awaiting Run 并建立一条流式订阅。首版若维持“同会话单执行”可以继续工作，但一旦允许同会话多条消息排队，界面需要把每个 Run 的状态和它的 `inputMessageId` 对齐，否则用户分不清哪一个问题在排队、哪一个问题正在回答。

#### D. 供应商侧缺少可见的分布式并发舱

当前有租户级配额、模型路由重试和断路器，但未看到按 `(provider, credentialReference, model)` 统一协调的分布式并发/速率令牌。多个 Worker 或 Runtime 副本同时扩容后，可能一起打满同一模型账号的 RPM、TPM 或并发限制，形成大量 429、超时和重试。

#### E. Runtime 的实时流会话仍含进程内状态

Python Runtime 用 `(tenantId, runId)` 隔离流会话，这是正确的；但活动流会话存在进程内。进程重启后，持久化的 `RUNNING` Run 会进入需要协调的状态，不能盲目重新调用模型。这能避免重复消费，却会降低故障恢复体验。生产化需要供应商任务 ID 对账或可恢复执行协议。

#### F. 缺少“多人、多窗、乱序完成”的正式容量验收证据

现有单元测试覆盖了不少幂等、租约、状态和流事件行为，但本次核对没有发现能够证明以下目标的正式压测报告：同一租户多用户同时请求同一智能体、不同供应商延迟下乱序完成、Worker 重启、单 Run 取消以及跨租户零泄漏。

## 3. 目标执行模型

每次提问产生一个不可变的执行信封：

```text
RunEnvelope
├─ tenantId                  租户边界
├─ conversationId            会话边界
├─ inputMessageId            问题边界
├─ runId                     执行与流事件边界
├─ requesterUserId           权限主体
├─ targetAgentId             智能体配置
├─ agentVersionId            提问时的智能体版本
├─ permission/policy snapshot
├─ model route snapshot
├─ knowledge/memory snapshot
├─ idempotencyKey
└─ providerTaskId / stream cursor
```

核心不变量如下：

1. 任何上下文查询都必须至少包含 `tenantId + conversationId`，并截断到 `inputMessageId`。
2. 任何回答落库都必须从 Run 读取 `conversationId + inputMessageId`，不得从“当前选中的窗口”“智能体最近会话”或全局变量推导。
3. 任何流式事件都只允许写入和订阅当前 `runId`。
4. 取消、重试、超时和供应商回调必须包含并校验 `tenantId + runId + providerTaskId`。
5. Agent 只是一份只读配置和版本引用，不能成为会话状态容器，也不能成为并发锁的键。
6. 模型客户端、知识检索客户端可以共用连接池，但请求消息、引用、令牌统计、流缓冲区和取消信号不能共用。

## 4. 建议实施方案

### P0：先解决“问题收不下”和串话验收

1. 修改消息创建事务：保留消息级幂等锁，移除“同会话存在活动 Run 就拒绝整条消息”的行为。
2. 每条发给智能体的消息都创建独立 Run；继续使用 `message:{messageId}:agent:{agentId}` 幂等键。
3. 将原有的 direct-only 前序检查扩展为所有同会话 Run 的检查，使用数据库分配的 `conversationSequence` 和中继 `turnIndex` 排队；不能以应用服务器时间作为并发顺序的最终依据。这样同一会话不会因为两个模型调用读取不同时间点的上下文而乱序覆盖，中继链也会在下一个用户问题前完整结束。
4. API 返回消息时同时返回或可查询对应 Run 状态。桌面端把“等待处理、回答中、失败、已完成”显示在对应问题下面。
5. 前端维护 `runId -> stream state` 或至少 `inputMessageId -> run state` 的映射，禁止用全局 `activeRun` 的文本覆盖其他消息。首版同会话只会有一个 RUNNING，但可以有多个 QUEUED。
6. 对回答落库、流事件读取、取消和重试接口补充跨会话负向测试：拿 A 会话的 `conversationId` 搭配 B 会话的 `runId` 必须返回 404/无权访问，不能返回 B 的任何数据。

P0 不需要引入新消息队列或新智能体框架；现有 PostgreSQL Outbox、Run 表和 Worker 足以完成。

### P1：建立可扩容的有界并发和公平排队

并发需要分四层治理，不能只改一个环境变量：

| 层级           | 推荐键                                   | 作用                                             |
| -------------- | ---------------------------------------- | ------------------------------------------------ |
| 会话           | `tenantId + conversationId`              | 首版最多 1 个运行中，保证上下文顺序              |
| 租户           | `tenantId`                               | 防止一个企业耗尽整个平台，同时允许按套餐配置容量 |
| 供应商并发舱   | `provider + credentialReference + model` | 遵守模型账号并发、RPM、TPM 限制                  |
| Worker/Runtime | 实例级                                   | 控制单实例连接数、内存、文件描述符和退出等待     |

具体措施：

1. 将 Worker 的当前 8 路配置上限改成符合部署容量的上限，但不要直接设成无限；建议先用压测确定单实例安全值。
2. 租户并发不再统一默认 4 后永久不变。管理端已有配额字段，应按客户容量配置，并为重要业务保留容量。
3. 队列 claim 增加公平性：同一用户或同一会话不能长期占满租户全部槽位；至少采用租户内轮转或每用户最大在途数。
4. 增加供应商并发舱与 RPM/TPM 令牌桶。多副本部署时状态放在 PostgreSQL 或 Redis，不能只放在单个 Python 进程内。
5. 429 或明确的供应商限流进入带抖动的退避队列；已经产生部分输出或执行结果不明确时进入 `UNKNOWN` 对账，不能自动重复发起并产生双倍成本。
6. API 保持无状态并可多副本；Worker 和 Runtime 可水平扩容。队列等待时间和使用率作为扩缩容信号，而不是只看 CPU。
7. SSE/流式连接允许断线后用 cursor 重连；前端切换聊天窗口不取消其他 Run，只取消该窗口的本地订阅，后台 Run 继续执行。

### P1.5：故障恢复

1. 对支持异步任务查询的供应商保存真实 `providerTaskId`，Runtime 重启后先查询任务状态，再决定继续拉取、完成或人工协调。
2. 对不支持任务查询的同步模型明确采用“结果不明不自动重发”的策略，并在用户端提供安全重试。
3. Worker 租约过期可重新 claim，但重新 claim 只能对已知外部执行 ID做查询，不能悄悄创建第二个模型任务。
4. 取消只作用于指定 Run；取消 A 会话绝不能取消同一智能体在 B 会话的任务。

### P2：生产容量与多租户验收

至少建立以下并发场景：

1. 同一智能体、100 个用户、100 个不同会话同时提问。
2. 同一用户打开 20 个聊天窗口，同时向不同智能体提问。
3. 同一会话快速发送 10 个问题：10 条消息全部落库，Run 顺序执行，回答分别锚定原问题。
4. 两个租户使用相同的用户名、智能体名和相似问题，验证上下文、知识引用、流事件和输出消息完全不交叉。
5. 模型故意乱序返回：后开始的其他会话可先完成，但回答不能写错会话。
6. 运行中取消一个 Run，其余 99 个 Run 不受影响。
7. Worker 或 Runtime 在模型执行中重启，验证无重复回答、无重复计费、无串流。
8. 模拟供应商 429、超时和 5xx，验证公平排队、退避和断路器。
9. 模拟一个大客户持续满载，验证其他租户仍有可用容量。

验收红线：

- 跨租户、跨用户、跨会话上下文泄漏：0。
- 回答写错 `inputMessageId` 或 `conversationId`：0。
- 流事件投递到错误 Run：0。
- 同一消息产生重复回答：0。
- 已接收消息丢失：0。
- 排队请求必须有明确状态和可观测等待时间，不能长期无反馈。

性能目标应区分平台响应和模型响应：

- 消息可靠落库 P95：小于 300 ms（同地域、数据库健康时）。
- 返回“已接收/等待处理” P95：小于 1 秒。
- 已获得执行槽后的首个流式片段：由模型供应商延迟决定，单独统计。
- 队列等待 P95、P99：按租户套餐和峰值容量定义并告警。

## 5. 容量计算原则

系统安全并发不是“CPU 核数”等于“模型并发数”。外部模型调用主要等待网络，单机可以维持多路异步请求，但还受数据库连接、SSE 连接、响应缓冲、知识检索、模型 RPM/TPM 和成本预算限制。

可先用下式估算所需执行槽：

```text
目标并发槽 ≈ 峰值每秒提问数 × 单次回答 P95 秒数
```

例如峰值 2 次提问/秒、模型 P95 为 15 秒，理论上约需 30 个在途槽；还要预留故障和抖动余量。若供应商账号只允许 10 路并发，就应部署 10 路执行槽并让其余请求可靠排队，或申请更高配额/增加合规的模型路由，不能靠把 Worker 改成 30 强行突破供应商限制。

## 8. Manus 方案评审与实际落地记录

### 8.1 采用的核心设计

Manus 附件中的总体方向可用，本次采用了以下原则：

1. 接收层始终接收合法问题，在同一事务中写入输入消息、独立 Agent Run 和 Outbox 事件。
2. 每个问题有独立 `messageId`、`inputMessageId`、`runId` 和流事件序列；SSE 按 `runId` 精确订阅与回放，不按会话共用一条易串流的订阅。
3. 同一会话严格串行，不同会话可并行；排序与领取在数据库中完成，允许多个 Worker 竞争而不重复执行。
4. 重试、租约和流事件继续复用项目已有 PostgreSQL Outbox/Worker，不引入 BullMQ 或新的队列依赖。
5. 客户端将排队、执行、失败与重试状态绑定到各自的 `inputMessageId/runId`，发送第二个问题不会覆盖第一个问题的流状态。

### 8.2 根据本项目约束做出的调整

没有直接执行附件中的 `claim.sql`、`schema.sql` 或 Python 验证脚本，也没有照搬其表结构。原因如下：

1. 本项目已经先 claim `outbox_event_deliveries`，再由 `AgentRun.prepare()` 执行会话头部闸门；改为直接 claim `agent_run` 会形成两套权威队列和重复领取风险。
2. 不增加覆盖全部状态的无条件 `UNIQUE(input_message_id)`，但必须有数据库回答槽位。失败和取消 Run 可以保留为多条审计历史；对 `QUEUED / DISPATCHING / RUNNING / UNKNOWN / SUCCEEDED` 建立 `(tenantId, inputMessageId)` 部分唯一索引，保证同一输入消息最多有一个在途、结果不明或成功回答。显式重试仍可创建新 Run，但只有当前槽位释放后才能创建；`idempotencyKey` 不能替代这条业务唯一性约束。
3. 没有使用 `created_at` 或应用服务器时间决定同会话顺序。新增数据库序列 `Message.sequence` 与 `AgentRun.conversationSequence`，并让自动中继子 Run 继承根 Run 的会话序列。
4. 接收事务中的 PostgreSQL advisory lock 只用于给同会话写入确定顺序，模型执行期间不持锁；Worker 通过 `NOT EXISTS` 前序活动 Run 检查形成会话头部闸门。
5. 未用容量为 1 的 advisory lock 假装实现供应商并发控制。供应商舱需要可信的 `(provider, credentialReference, model)` 容量、RPM 和 TPM 配置；在这些配置及多副本令牌协议完成前，继续保留现有租户并发配额并将供应商舱列为 P1。

### 8.3 已实现内容

后端与数据层：

- `Message.sequence` 为消息提供数据库分配的稳定顺序，并以 `(tenantId, conversationId, sequence)` 唯一。
- `AgentRun.conversationSequence` 为用户问题及其完整中继链提供会话内执行顺序。
- 移除了历史 migration 遗留的“每会话只能存在一个活动 Run”部分唯一索引；第二个问题现在正常落库为 `QUEUED`，不再返回冲突或 500。
- 会话写入仍保留消息级幂等，并在短事务内取得会话 advisory lock；相同幂等键重复提交返回已有结果。
- `prepare()` 会阻止任何较晚的同会话 Run 越过较早的 `QUEUED / DISPATCHING / RUNNING / UNKNOWN` Run；不同会话不互相阻塞。
- 上下文窗口以当前输入消息的数据库序列为上界，避免并发写入时把“未来问题”读入较早 Run。
- 重试 Run 可以在已有活动 Run 时进入队列；自动中继子 Run 继承父链顺序，整条中继链结束后才放行下一问题。

桌面端：

## 9. Manus v2 针对性优化（2026-08-21）

### 9.1 对 v2 结论的取舍

本轮将 Manus 的 v2 文档、实测记录和脚本作为外部评审材料使用，没有直接执行其中带固定连接参数的 Python/SQL。对照真实代码后的结论如下：

1. **采纳输入消息回答槽位。** 之前把“允许显式重试创建新 Run”作为不增加输入消息唯一约束的理由不完整。重试历史与回答唯一性是两个维度：允许保留多个 `FAILED / CANCELLED` Run，不等于允许两个在途、结果不明或成功 Run。现在由部分唯一索引给数据库最终兜底。
2. **采纳 claim 阶段的会话队首过滤，同时保留 `prepare()` 双保险。** Outbox 先通过 `outbox_events.aggregate_id` 关联真实 `agent_runs.id`，只为 `QUEUED` Run 检查同会话更早活动项；缺失 Run、终态 Run和恢复中的非 `QUEUED` 事件仍可被领取并由 Worker 正常收敛，不能因优化把恢复事件饿死。
3. **租户冷启动配额继续以 `prepare()` 为权威闸门。** 每个 Run 都在最终 `QUEUED -> DISPATCHING` 事务内重新取得租户 advisory transaction lock、重新统计在途量并预留 Token，不是一批 Run 共用一次旧快照。真实 200 条积压测试已证明上限 8 时只有 8 条进入在途状态。
4. **暂不照搬 API 侧两级供应商锁。** 当前受信模型路由可以包含多个候选，Python Runtime 在执行时逐候选选择并故障转移；NestJS 派发前不知道实际使用的 `(provider, credentialReference, model)`。锁第一个候选可能限制了没被调用的模型，却放过真正回退到的模型，属于假安全。正确实施点应靠近 Runtime 的实际候选尝试，并且必须先有每个供应商槽位的容量、RPM/TPM、租约和最终释放协议。
5. **没有加入新的 BullMQ/Redis 队列。** PostgreSQL Outbox、`SKIP LOCKED`、租约与状态机已经是权威队列；增加第二套队列只会扩大一致性和运维故障面。
6. **当前 Agent Run Worker 没有按 attempts 静默丢弃请求的阈值。** 开发库中确有少量历史 delivery attempts 较高，说明无效 claim 会制造 churn，但没有证据表明当前代码会在固定次数后静默 dead-letter。本次把同会话非队首过滤前移，直接减少这类无效领取；后续若增加最大次数，必须为会话阻塞延期和真实执行失败使用不同计数语义。

### 9.2 实际实现

数据库：

- migration `20260821000100_agent_run_input_execution_slot` 新增部分唯一索引 `agent_runs_one_answer_per_input_message_idx`，键为 `(tenant_id, input_message_id)`，覆盖 `QUEUED / DISPATCHING / RUNNING / UNKNOWN / SUCCEEDED`。
- 同一 migration 新增活动会话顺序索引 `agent_runs_active_conversation_order_idx`，支持 claim 与 `prepare()` 的前序检查。
- migration `20260821000200_agent_run_outbox_queue_head_read` 只向 `enterprise_agent_outbox` 授予 `id / tenant_id / conversation_id / conversation_sequence / turn_index / status` 六列读取权；RLS 只允许固定 Outbox 角色跨租户读取这些列，`policy_snapshot`、模型路由、提示词、输出和用量等仍不可读。
- Prisma 会把单个 migration 放进事务，PostgreSQL 的 `CREATE INDEX CONCURRENTLY` 在该正式链路上会报 `25001`，因此仓库 migration 使用普通 `CREATE INDEX`。生产大表上线必须安排短维护窗口；如果以后需要无阻塞建索引，应先建立独立、受审计的事务外运维通道，不能把无法执行的 `CONCURRENTLY` 留在 Prisma migration 中。

应用与队列：

- 显式重试不再只查 `retryOfRunId = 当前 Run` 的直接子项，而是按同一 `inputMessageId` 查找任何 `QUEUED / DISPATCHING / RUNNING / UNKNOWN / SUCCEEDED` 槽位；从不同失败祖先同时重试也只返回同一个当前 Run。
- 当前槽位为 `QUEUED / DISPATCHING / RUNNING` 时返回现有 Run；为 `UNKNOWN` 时要求先对账或由用户明确结束等待；为 `SUCCEEDED` 时要求用户发送一条新消息，而不是给同一输入再生成第二个回答。
- 数据库部分唯一索引发生 `P2002` 竞争时，服务会重新进入带会话锁的事务一次：槽位仍存在就返回/拒绝当前持有者，槽位已因状态变化释放才创建新重试。应用检查负责体验，数据库索引负责最终正确性。
- Agent Run Outbox claim 在 `FOR UPDATE OF delivery SKIP LOCKED` 前增加会话队首谓词。同一会话后续 Run 不再反复增加 delivery attempts；`prepare()` 的权威顺序检查仍保留，防止未来其他入口绕过 claim 优化。

## 10. Manus v3 复核与稳态优化（2026-08-21）

### 10.1 结论与取舍

1. **采纳稳态释放测试。** 冷启动积压与“执行完成—释放容量—再次获取”覆盖的是不同竞争窗口，不能互相替代。本轮保留原 200 条冷启动测试，并新增 10 会话 × 10 问题的稳态测试。
2. **UNKNOWN 阻止同会话后续 Run 是正确性闸门，不是需要移除的锁。** 前序结果不明时继续执行后续问题，会让后续上下文缺失或在供应商稍后返回时发生顺序反转。真实产品必须明确展示阻塞原因，并提供受控恢复入口。
3. **“用户完全无法自救”不符合当前真实实现。** API 已有 `POST /conversations/:id/runs/:runId/abandon`，桌面端已有“结束本次等待”入口。该操作由参与者权限约束，在租户配额锁和 Run 锁内把 `UNKNOWN` 记为 `FAILED / AI_RUNTIME_RESULT_ABANDONED`，追加流终态和审计，并按预留上限保守结算 Token；它不声称远端任务已经取消。
4. **不按 5～10 分钟墙钟时间强制把 UNKNOWN 改成 FAILED。** 时间流逝不是供应商已经停止的可信证据；自动释放回答槽位后重试，可能造成两次回答与两次计费。5～10 分钟阈值适合触发告警、自动查询 Runtime 和人工升级，不适合作为业务终态证据。只有可信供应商终态、确认取消，或用户理解风险后主动结束本地等待，才能释放会话顺序闸门。
5. **不把用户结束本地等待记成 CANCELLED。** `CANCELLED` 表示 Runtime 已确认远端取消；用户本地放弃无法证明这一事实。使用带专用错误码的 `FAILED` 能保留“不再阻塞，但远端结果仍未知”的真实语义。
6. **Agent Run Outbox 当前没有 `maxAttempts` 静默淘汰。** `outbox_event_deliveries.attempts` 只记录领取次数，claim SQL 不按它过滤，Worker 也没有按固定阈值转死信。若未来增加重试上限，必须把“真正执行失败次数”与“租约恢复/容量延期/会话等待造成的领取次数”拆开，不能复用一个计数器。

### 10.2 本轮实现与验证

- 桌面端发现会话中存在 `UNKNOWN` 时，不再把后续 `QUEUED` Run 当成当前执行项；后续问题明确显示“等待上一条问题的远端结果确认”，并指向上一条消息中的结束等待入口。
- UNKNOWN 提示补充风险说明：结束等待只解除本地阻塞，不代表远端任务已取消，远端仍可能完成并产生费用；执行前使用系统确认框再次确认。
- 新增真实 PostgreSQL 解冻链路测试：首个 Run 进入 `UNKNOWN` 后，第二条消息不能 claim 且 delivery attempts 保持 0；参与者结束等待后，首个 Run 留下失败码和审计，第二条立即恢复 claim 和 `prepare()`。
- 同一测试将第二条 delivery 的 attempts 预置为 99，解冻后仍正常领取且返回 100，证明当前 Agent Run 领取路径不存在隐藏次数上限。
- 新增稳态配额测试：10 个会话、每会话 10 条消息、16 个模拟 Worker 槽、租户并发上限 8；每个 ready Run 保持 25ms 后完成，让容量释放与再次获取持续交织。100 条 Run 全部完成，数据库在途峰值为 8，零超配。
- Agent Run PostgreSQL 集成套件由 17 项增至 19 项，本轮一次性数据库实测 19/19 通过；全部 133 条 migration 从空库执行成功。

### 10.3 UNKNOWN 自动对账的正确边界

当前已有管理员发起的可信对账入口，能够使用已经持久化的 `externalRunId` 查询 Runtime，再把同一 Run 放回恢复链路；没有可信外部 ID 的 UNKNOWN 必须人工核验供应商侧证据。后续自动化应当是“定时探测和升级”，而不是“到点强制失败”：

1. 超过告警阈值后，以带租约、退避和抖动的对账任务查询同一个外部 Run，不创建新的供应商任务。
2. 得到可信成功、失败或取消终态后，收敛原 Run、额度和流事件。
3. 仍不可达或返回歧义时保持 UNKNOWN，记录探测次数和最近错误，通知管理员并继续向用户提供结束本地等待入口。
4. 用户主动结束等待后不得自动重放被放弃的原输入；已有独立 `inputMessageId` 的后续问题是用户已明确提交的任务，可以恢复排队执行。若要重做原问题，必须再次明确点击重新生成或发送新消息，并继续保留潜在重复费用提示。

### 10.4 供应商舱位的租约约束

供应商舱位仍必须落在 Python Runtime 的实际候选调用处，键为真实 `(provider, credentialReference, model)`。实施时必须同时满足：

- 槽位所有权使用共享存储中的租约、心跳和 fencing token；进程崩溃后允许另一个协调者接管，不能只靠 `finally` 显式释放。
- Worker 所有权租约与供应商容量占用是两个语义。租约过期只能证明本地持有者失联，不能证明远端任务已经停止；不得因此直接启动同一输入的新任务。
- 已有供应商任务 ID 时，由接管者查询同一任务并续管；没有可查询 ID 时进入 UNKNOWN、告警或供应商熔断，不能把一个简单 TTL 当成远端终止证据。
- 429、RPM、TPM、并发舱和故障转移都按实际候选记录；占槽、续约、接管、释放原因和供应商回执必须可审计。

### 10.5 并发测试评审规则

后续并发测试评审固定回答四个问题：是否存在真实多连接竞争、是否覆盖冷启动和稳态释放两个窗口、是否经过真实 Outbox/租约/`prepare()` 链路、是否同时验证错误实现会失败。单线程模拟、只测最终行数或只看 HTTP 200 都不能作为并发正确性证据。

## 11. Manus v4 复核与灰度前收口（2026-08-21）

### 11.1 迟到回答结论：附件告警没有复现真实链路

Manus v4 的 `t7_v3.py` 在自建简化表上直接执行 `UPDATE agent_runs SET status='SUCCEEDED'`，据此认定用户结束等待后原 Run 仍可成功并追加第二条回答。这项验证没有经过真实 `AgentRunControlService`、`PrismaAgentRunRepository.completeSucceeded()`、流事件和消息写入事务，因此只能证明简化表缺少状态约束，不能证明本项目存在迟到消息入口。

真实链路已有两道应用门禁：

1. `reconcileUnknown()` 只接受仍为 `UNKNOWN` 且 `externalRunId` 未变化的 Run。用户结束等待后状态为 `FAILED / AI_RUNTIME_RESULT_ABANDONED`，对账入口返回冲突，不能把它放回执行链路。
2. `completeSucceeded()` 只允许 `RUNNING + externalRunId`，对 `FAILED / CANCELLED / UNKNOWN` 等终态直接拒绝，并且消息创建与 Run 成功转换在同一事务中完成。abandon 与完成均取得 Run 锁；谁先完成决定唯一结果，后到者不能再追加消息。

本轮仍把这项不变量下沉到数据库：migration `20260821000300_agent_run_terminal_immutability` 禁止 `SUCCEEDED / FAILED / CANCELLED` 改成其他状态；重试必须创建新 Run，`UNKNOWN -> RUNNING` 仍只为可信对账保留。真实集成测试验证：abandon 后直接 SQL 改 `SUCCEEDED` 被 `23514 / agent_runs_terminal_status_immutable` 拒绝，调用正式成功完成入口同样被拒绝，`clientMessageId = agent-run:{runId}` 的迟到消息数量为 0。

因此没有增加 `supersededBy`：系统不能仅凭用户随后发送一条新消息，就断言它在语义上替代上一问；自动关联会把正常的下一问题误标为重发。若将来接入供应商主动回调，已放弃 Run 的迟到成功和费用回执应进入独立审计/计费事实，不得改写 Run 终态或追加会话消息。

### 11.2 UNKNOWN 自动探测已沿现有 Outbox 落地

- 已有 `externalRunId` 的 Run 因不可确认结果进入 `UNKNOWN` 时，在同一数据库事务中写入延时 `agent.run_requested.v1` 对账事件和 delivery；默认延时由 `AGENT_RUN_UNKNOWN_RECONCILIATION_DELAY_MS=300000` 控制。
- 延时事件带 `reconciliation: true` 和原 `externalRunId`。Worker 使用 `prepareReconciliation()` 在租户配额锁和 Run 锁内执行 `UNKNOWN -> RUNNING`，然后只调用 Runtime `get` 查询同一个外部任务；不会调用 `create`，不会产生第二个供应商任务。
- 查询得到可信终态时收敛原 Run；仍无法确认时再次保持 `UNKNOWN` 并安排下一次延时探测。没有可信 `externalRunId` 的歧义派发不会自动探测，继续要求人工核验供应商侧证据。
- 用户在延时事件到期前结束等待时，Run 已成为不可逆的 `FAILED / AI_RUNTIME_RESULT_ABANDONED`。Worker 只收口该 delivery，不调用 Runtime、不追加回答。
- 调度和开始探测分别记录 `agent.run.reconciliation_scheduled`、`agent.run.reconciliation_started` 审计。当前采用固定受控间隔；指数退避、抖动、UNKNOWN 专项告警面板仍属于灰度可观测性增量，不能把已有审计等同于完整告警系统。

### 11.3 v4 其余建议的实施

- 稳态配额测试已从 `completeFailed` 改为生产成功主路径：100 个 Run 均执行 `prepare -> attachExternalRun -> completeSucceeded -> markPublished`，16 个模拟 Worker、租户上限 8，全部成功且峰值为 8。
- 数据库清理安全门禁新增独立回归：即使 `RUN_DATABASE_TESTS=true` 且连接用户是 superuser，只要实际 `current_database()` 为开发库 `enterprise_agent`，也必须在事务和删除前拒绝。门禁以实际连接目标为准，不只信任 `DATABASE_URL` 字符串。
- 历史配额测试曾把一个已成功 Run 直接改回 `RUNNING` 复用夹具；终态 migration 正确暴露了该问题。测试已改为创建新的真实容量占用 Run，而不是放宽生产约束。

本轮实际完成：

- 空的一次性 PostgreSQL 17/pgvector 数据库 `enterprise_agent_concurrency_v4_test` 从第 1 条开始完整应用 134 条 migration。

仍不能据此宣称生产并发全部验收：本轮没有使用真实模型供应商验证 UNKNOWN 查询、费用回执、429/RPM/TPM，也没有完成多副本 Worker/Runtime、网络分区、fencing token、供应商候选级容量租约、100 用户长 SSE、真实 IM 和 UNKNOWN 三分辨率视觉验收。进入受控灰度时仍应限制单租户、单 Worker/API 副本和数十名用户，并重点观测 UNKNOWN 频率、重复探测次数、供应商费用争议和队列等待时间。

## 12. 多用户及时响应与 UNKNOWN 非阻塞收口（2026-08-21）

### 12.1 最新产品取舍

用户明确要求企业多人、多窗口问答应及时响应，不能因为一条历史任务结果不明而等待数小时。基于这一最新要求，`UNKNOWN` 的角色调整为“保留供应商结果不确定性的审计与对账状态”，不再等同于本地正在执行的任务，也不再无限占用租户本地并发槽。

可靠 Outbox 仍保留，用于接收事务、租约、崩溃恢复和突发流量削峰；产品界面不再向普通用户展示 `QUEUED` 或“会话内排队”等内部术语。目标不是承诺无限容量，而是做到：

1. 发送接口立即接收并显示正在准备；不同用户、不同窗口和不同会话由 Worker 池并行处理。
2. 同一会话只对仍在真实执行的 `QUEUED / DISPATCHING / RUNNING` 保留短顺序链，避免上下文和回答串线。
3. 一条 Run 进入 `UNKNOWN` 后，如果已有或新建了后续 Run，旧 Run被标记为已被后续 Run 接管会话调度；后续问题无需用户手动结束等待即可执行。
4. 旧 Run 仍保留 `UNKNOWN`、`externalRunId`、Token 预留与审计，可继续查询同一个远端任务；该调度接管不伪造远端失败或取消。
5. 被接管的旧 Run 若后来可信收敛为成功，系统记录真实成功与费用事实，但不向会话追加迟到回答，避免答案倒序、上下文污染和双回答。

这里的 `supersededByRunId` 只表示“会话调度位置已由后续 Run 接管”，不声称两个用户问题语义相同，也不用于费用抵扣。用户主动 abandon 的既有终态不变，仍使用 `FAILED / AI_RUNTIME_RESULT_ABANDONED`。

### 12.2 防止网络重试制造重复远端任务

NestJS 现在把本地 `AgentRun.id` 作为 `run_id` 传给 Python Runtime。Runtime 对调用方给定的 Run ID 执行严格幂等创建：完全相同的请求重复到达时返回同一 Run；相同 ID 但请求内容不同仍拒绝冲突。

因此“Runtime 创建请求已发出，但 HTTP 响应在返回前断开”的场景不再立即冻结为无外部 ID 的 `UNKNOWN`。Worker 将同一个本地 Run 延后重试，Runtime 依靠确定性 ID 返回已经创建的同一任务。只有已经确认外部执行、后续结果查询仍不确定的情况才进入可对账的 `UNKNOWN`。

### 12.3 数据与队列实现

- migration `20260821000400_agent_run_unknown_supersession` 新增 `superseded_by_run_id / superseded_at`、同租户自引用外键、配对约束和索引，并为固定 Outbox 角色增加仅该排序字段的列级只读权限。
- migration 会把升级前已经存在且后面已有新 Run 的 `UNKNOWN` 前向修复为已接管状态，并写入哈希链审计；不删除或伪造原 Run。
- 新消息与 Run 在同一个接收事务中创建后，批量标记该会话未接管的历史 `UNKNOWN`；`completeUnknown()` 也会检查已经排在后面的最早 Run，覆盖“后续问题先排队、前一条随后才变 UNKNOWN”的竞争窗口。
- Outbox 队首过滤和 `prepare()` 的权威前序检查都忽略已经接管的 `UNKNOWN`。租户本地并发计数只覆盖 `DISPATCHING / RUNNING`，但 `UNKNOWN` 的未确认 Token 预留仍计入月度预算。
- 普通用户界面显示“正在准备 / 正在连接 / 正在回答”，不再显示内部状态名；只有真正存在同会话活动前序时，才诚实说明本条会在前一条回答完成后自动开始。

### 12.4 本轮真实验证

- 全新一次性 PostgreSQL 17/pgvector 数据库 `enterprise_agent_unknown_supersession_test` 从空库完整执行 135 条 migration。
- Agent Run PostgreSQL 集成测试 19/19 通过，覆盖：`UNKNOWN` 释放本地并发槽但保留 Token 预算、已有后续 Run 自动接管、后续 Outbox 立即领取、迟到成功不创建消息但写审计、冷启动及稳态配额不超限。
- API 目标单元测试 76/76、桌面消息测试 35/35、共享契约测试 32/32、Python Runtime API 测试 18/18 通过；API、Desktop、Contracts 类型检查以及 Prisma schema 校验通过。
