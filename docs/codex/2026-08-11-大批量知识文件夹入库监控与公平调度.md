# 大批量知识文件夹入库监控与公平调度

日期：2026-08-11

## 现场对象

- 租户：`future-collaboration`
- 知识库：`咨询圈文库资料1`
- 知识库 ID：`a3f1b185-90a1-4098-b88b-0e02512e9efc`
- 数据库实际创建 583 份文档：580 份进入入库队列，3 份因超过 100MB 对象上限被明确拒绝。
- 队列文件类型：525 份 PPTX、46 份 PDF、8 份 PPT、1 份 XLSX。

## 根因与修复

原 claim 顺序只按失败次数、领取次数和创建时间排序。另一个租户已有更早的大批量积压任务，导致新上传租户长期拿不到 Worker，页面持续显示 5%，但实际上没有开始解析。

修复在知识入库仓储的统一 claim SQL 中完成：按各租户最后一次任务活动时间轮转租户，再在租户内按失败次数、领取次数和可用时间排序。该修复不改变知识权限边界，也不按指定租户写死优先级。

专用 Worker 角色采用列级最小权限。公平调度读取 `updated_at` 后，新增前向 migration，仅补充该列的 `SELECT` 权限，没有扩大为整表访问。

## 真实验证

- migration deploy 成功，共 121 条 migration。
- Worker 权限错误在授权应用后停止。
- 当前知识库已有 4 份 XLSX/PPTX 达到 `SUCCEEDED/READY`，合计生成 426 个切片。
- 后续两份 PPTX 已被公平调度领取并进入 `SECURITY_CHECK/PARSING`，证明队列持续推进。
- 3 份超过 100MB 的文件保留 `KNOWLEDGE_OBJECT_TOO_LARGE` 永久异常，不进行无效重试。
- Docling 处理复杂 PPT/PDF 时实测约占用 3GB 内存并可使用多核 CPU；本机继续使用 2 个并行任务，避免在 8GB Docker 内存限制下盲目增加并发造成解析器失稳。

## 尚需持续观察

580 份文档全部完成需要较长时间。后续应持续观察成功数、切片数、可重试解析异常和永久异常；不能用“任务已排队”代替完成验收。生产部署还需要基于独立解析 Worker、内存和真实文件复杂度进行容量压测。
