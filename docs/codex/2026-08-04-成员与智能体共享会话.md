# 成员与智能体共享会话实施与验收记录

## 背景与目标

员工不应在“联系成员”和“联系成员的智能体”之间维护两个割裂的聊天窗口。本次改造将新建会话收敛为成员共享频道：发起人、目标成员和目标成员的个人智能体使用同一条消息时间线，并通过“发给成员 / 询问某某的智能体”选择本条消息的主动回应方。

共享不等于让 AI 自动介入所有聊天。所有消息对会话中的真人成员可见，但只有明确选择智能体时才创建 Agent Run；选择成员本人时不会触发模型调用。

## 已实现设计

### 会话与参与者

- 从“联系本人”和“联系智能体”进入时，服务端使用相同的成员频道键，因此返回同一个会话 ID。
- 共享会话包含发起人、目标成员，以及目标成员当前可使用的个人智能体。
- 智能体参与者在员工界面统一显示为“某某的智能体”，不要求员工理解后台配置名称。
- 目标成员是正常的 USER 参与者，因此可从自己的消息列表读取会话、用户消息和智能体回复。
- 既有 `human:*`、`agent:*` 会话和旧请求仍可读取；本次没有迁移或删除历史消息。

### 消息回应方

- `CreateMessageRequest` 新增可选 `responseTarget`，支持受控选择真人成员或智能体。
- 该字段只决定主动回应方，不改变消息的共享可见范围。
- 选择真人时不创建 Agent Run；选择智能体时只为选中的、仍在会话中的智能体创建一次 Run。
- 服务端复核回应方是否是当前会话的活动参与者，并继续执行智能体运行就绪检查。
- 消息表保存回应方类型和 ID；同一幂等消息 ID 若换了回应方，会被视为冲突，不能静默改投。
- 未携带 `responseTarget` 的旧客户端继续按旧会话语义工作。

### 员工界面

- 通讯录成员详情只保留“打开共享会话”主操作。
- 新建会话弹窗每位成员只显示一个业务入口；“询问智能体”快捷入口会进入同一窗口并默认选中“某某的智能体”。
- 输入框上方展示“发给某某”和“询问某某的智能体”切换，旁边明确提示“消息对成员本人始终可见”。
- 会话列表和页头显示“成员与智能体共享”，消息气泡记录本条消息发给谁。
- 智能体流式状态、终态消息和普通消息均使用“某某的智能体”作为员工可识别身份。

## 数据与兼容性

新增前向迁移 `20260804000100_shared_member_agent_conversation`：

- `messages.response_target_type`
- `messages.response_target_id`
- 字段组合约束及会话内回应方索引

已有消息保持两个字段为空，不重写消息、Run、审计或 Outbox 历史。旧 URL 仍可访问；新的本人/智能体入口从改造后开始汇聚到共享频道。历史上已经分别创建的两个旧会话不会被破坏性合并，避免重写消息谱系和 Agent Run 外键。

## 实际验收证据

在本地 `enterprise_agent_vector` 数据库、API 3000、桌面开发服务 5173 和 AI Runtime 8100 上使用两个真实 seed 账号验收：

- “联系周睿”和“联系周睿的智能体”返回同一会话 ID。
- 会话参与者为两个 USER 和一个 AGENT，智能体展示名为“周睿的智能体”。
- 林晓发给周睿的真人消息可由周睿账号读取，且没有创建 Agent Run。
- 林晓选择“周睿的智能体”后创建且仅创建对应 Agent Run；同一输入消息也可由周睿账号读取。
- Agent Run 最终状态为 `SUCCEEDED`；周睿账号可在同一会话读取智能体输出消息。

## 风险与后续边界

- 历史上已经生成的独立真人会话和独立智能体会话没有自动合并。自动重写历史消息、Run 和审计外键风险较高，后续若需要统一历史，应先设计可回滚的数据迁移和冲突预览。
- 当前共享模式是“所有真人参与者可见，单一回应方主动响应”，尚未实现未读数、@提醒和人工接管状态按钮；真人可以直接发送消息完成接管。
- 桌面 Web 开发地址脱离 Electron preload 时会显示“桌面安全桥未加载”，这是预期安全边界；真实 Electron 开发进程和生产构建不受影响。
