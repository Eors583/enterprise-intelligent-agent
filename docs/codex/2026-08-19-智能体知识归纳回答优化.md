# 智能体知识归纳回答优化

日期：2026-08-19

## 问题与根因

员工智能体针对企业知识问题曾显示“模型暂未生成可完整核验的归纳回答”，随后直接回显召回片段。片段中包含文档标题符号、公式转义、`[IMAGE]` 占位符和乐享签名图片 URL，用户看到的是检索中间数据，而不是智能体完成理解和归纳后的回答。

根因不在乐享召回本身，而在 Agent Run 的生成后引用校验：旧规则要求同一段内每个独立句子分别以 `[SOURCE:<sourceId>]` 结尾。模型只要按常见写法在段尾统一引用，整条归纳回答就会被拒绝；开启证据兜底后，Worker 又把原始 excerpt 直接拼到聊天消息中。

## 本次决策

1. Runtime 提示明确要求先阅读相关证据、综合去重，再以结论优先的简洁中文回答；需要展开时使用 3–5 个清晰要点。
2. 禁止模型复制原始 chunk、URL、Markdown 图片语法、`[IMAGE]` 和文档解析噪声。
3. 引用校验采用段落级粒度：每个事实段落、列表项或表格行必须在末尾引用本次实际召回的一个或多个来源；同一段的多句归纳可以共享段尾来源。
4. 未引用、引用不存在来源、伪造来源、列表项漏引或来源数量异常的内容不作为企业知识答案发布；若仍有合法段落则只保留合法段落，否则正常返回无可靠依据，权限过滤和引用可信边界不变。
5. 引用校验不能发布模型原文或回显原始知识片段。知识无命中、候选无法支持结论和模型未形成合法引用属于正常无依据分支；乐享或模型供应商明确异常才显示失败步骤。

## 代码入口

- 生成提示：`apps/api/src/modules/agent-run/infrastructure/runtime/http-agent-runtime.client.ts`
- 输出引用校验与安全降级：`apps/api/src/modules/agent-run/application/agent-run.worker.ts`
- Worker 回归测试：`apps/api/src/modules/agent-run/application/agent-run.worker.spec.ts`
- Runtime 请求回归测试：`apps/api/src/modules/agent-run/infrastructure/runtime/http-agent-runtime.client.spec.ts`

## 验收重点

- 回答先给出可读的归纳结论，不展示召回原文堆叠。
- 每个事实段落或列表项显示稳定的 `[来源N]`，且来源可打开并对应本次授权召回证据。
- 回答正文不出现 `[SOURCE:...]`、签名资源 URL、`[IMAGE]`、公式转义或解析占位符。
- 故意去掉来源、使用伪造来源或让任一列表项漏引时，整条内容安全降级且不泄露原文。
- 使用真实乐享知识库与真实模型复测“你知道华为销售是如何进行管理的吗”，确认模型确实生成归纳回答，而不是仅凭单元测试判定完成。

## 2026-08-19 输入预算与错误状态修正

真实问题复测曾出现 `UNKNOWN / 等待供应商终态`。运行证据表明该请求没有进入 Manus：Runtime 在派发前以 `UNSUPPORTED_RUNTIME_INPUT` 拒绝了 16,049 字节的最终消息封装，原因是最终封装加安全余量超过 16,000 的保守输入预算。API 端又把合法的空 `model_attempts` 误判为响应损坏，导致确定失败被错误升级为 `UNKNOWN`。

修正内容：

- 将 API 上下文打包器为后续注入的身份、知识安全提示和协议封装预留量从 2 KiB 提高到 4 KiB，使较旧会话和低优先级可选上下文在派发前被裁剪；当前问题和系统提示仍为必需内容。
- Runtime 在供应商调用前失败时允许 `model_attempts=[]`，API 保留 `UNSUPPORTED_RUNTIME_INPUT` 确定失败语义，不再显示成远程结果待确认。
- 桌面端将输入预算失败解释为“上下文过长/输入超出范围”，引导用户缩小问题或新建会话，避免误导为供应商仍在生成。

## 2026-08-19 Manus 会话封装修正

真实复测中，Runtime 和 Manus 均成功，但模型把外层消息 JSON 当成普通说明数据，回复“没有明确的最新业务请求”。随后该回复因没有任何来源标记而被引用校验安全降级。根因是 Manus Task API 只接收一条文本消息，适配器需要在文本内重建 system/user/assistant 角色；旧封装同时强调“JSON 是数据”，却没有足够明确地要求执行最后一条 `role=user`。

适配器现已明确：`role=system` 是必须遵守的回答与安全规则，`role=assistant` 是历史回复，最后一个 `role=user` 是必须直接回答的当前请求；消息内容中嵌套的知识 JSON 仍只作为受控证据。模型不得讨论消息封装，只能返回助手答案，也不得使用 Manus 外部连接器、网站、文件、技能或工具。

## 2026-08-19 无效回答不再冒充知识答案

引用校验没有形成可交付、可核验的内容时，模型原文不能作为企业知识答案保存。最初实现曾将 Run 标记为 `FAILED / KNOWLEDGE_GROUNDING_VALIDATION_FAILED`；2026-08-20 根据真实空知识场景继续修正为正常无依据回复，同时仍不保存未核验的模型结论。桌面端保留旧错误码文案用于解释历史 Run，不代表新 Run 的知识空结果仍会失败。

## 2026-08-19 格式性校验放宽与等待时间调整

真实 Run `de909aac-84d0-4203-bfa7-383481c017c4` 的 Manus 调用在 31.8 秒后成功生成五个带合法来源的归纳要点，并非超时。失败是因为模型额外添加了无引用的开场引导段和末尾重复总结，旧校验将整篇答案拒绝。

现在校验器仅忽略位于答案首尾、长度受限且符合明确引导/总结措辞的无引用包装段，继续逐项校验并保留正文。位于中间的无引用事实、伪造来源、未知来源和越权来源仍然失败关闭。生成提示同时要求直接输出带引用的结论或要点，避免产生这类包装段。

单次 Agent Run 的模型等待预算由 60 秒提高到 300 秒；API Runtime HTTP 等待提高到 330 秒，Worker 事件租约提高到 360 秒，Manus 最大轮询等待提高到 300 秒。三个时间边界按顺序留出结算余量，避免长任务完成前被调用方或租约提前截断。

## 2026-08-19 引用协议的逐块恢复

Manus Task API 返回自由文本，不能由供应商接口强制执行 `[SOURCE:<sourceId>]` 结构；提示词能够提高遵循率，但无法保证每个生成段落都正确引用。Runtime 只判断供应商任务是否成功，API Worker 才掌握本次授权来源并负责最终引用校验，因此旧实现会在任意一个段落格式错误时拒绝整篇答案。

校验现改为逐块恢复：每个段落、列表项或表格行独立验证来源 ID，合法块转换为稳定的 `[来源N]` 并进入正式回答；无引用、伪造来源、未知来源或超过来源上限的块直接丢弃，不影响其他合法内容。仅当整篇没有任何合法块时才失败关闭，避免用错误引用包装未经证实的企业事实，也避免为格式修复额外创建未审计、可能重复计费的 Manus 任务。

## 2026-08-20 乐享检索空证据诊断

用户对 Run `ecfad616-c93a-42cf-a431-fcdea9a3362c` 重新生成后，界面显示“当前没有找到提问者可使用的可靠企业资料”。数据库和 Runtime 运行记录确认，该 Run 的输入安全决策为 `INTERNAL / ALLOW`，但最终传给 Runtime 的 `knowledgeSources` 为空；因此这句话只说明该次 Run 没有拿到证据，不能据此判断乐享中不存在内容。

按同一租户、同一用户、同一问题和正式 `KnowledgeRetrievalService` 入口重新执行只读检索，权限解析得到已启用的“咨询圈文库资料1”，乐享 AI 检索成功返回 8 条证据，包括《10-华为销售卓越之道：战略驱动与客户关系》《9-华为客户关系及销售管理》和《6-华为DSTE战略管理体系-DSTE、BLM、五看、三定、VDBD、BEM》。这证明乐享资料、当前用户权限、连接凭据和正式适配器当前均可用；截图中的空回答是一次历史检索阶段异常，不是知识缺失，也不是引用校验造成的。

该历史 Run 没有持久化检索响应的 `degradedReason`、`diagnostics`、已解析知识库 ID 或乐享调用回执，因此现有证据不能继续区分当时究竟是瞬时网络/令牌异常、适配器实例未装载，还是检索目标在该次执行中短暂为空。后续修复应把检索阶段摘要保存为不含凭据和原文的 Run 诊断回执，并区分“检索成功但无匹配”和“检索服务不可用”；后者不得再被表述成“知识库没有资料”。

## 2026-08-20 乐享等待与明确失败语义

乐享令牌与 AI 检索请求的单次等待预算从 5 秒提高到 20 秒；网络中断、超时、`429` 和服务端 `5xx` 最多自动尝试 3 次。乐享明确拒绝、返回不可识别响应，或等待重试后仍不可用时，知识检索边界抛出传输中立的不可用错误，Agent Run 以对应乐享错误码结束并在会话中显示可理解的失败原因。

远程知识源不可用不再降级为成功的空结果，也不会再触发“没有找到企业资料”的无依据回复。只有乐享请求成功完成且明确返回零条匹配时，系统才可按无结果处理；这样同时保证用户愿意等待时获得更长重试窗口，以及最终失败时能够看到确定原因而不是无限等待。

## 2026-08-20 Manus 无限等待与分阶段错误

截图中的 `PROVIDER_REQUEST_REJECTED` 不是乐享失败或等待超时。运行回执显示乐享知识和权限阶段已经完成，Manus 在 `task.create` 阶段不到一秒即拒绝请求；旧适配器把供应商的 `invalid_argument`、`not_found`、`failed_precondition` 和其他 4xx 全部压成同一错误码，导致界面无法指出实际出错步骤。失败请求还携带了多次重复问题和历史答复，输入明显大于此前成功请求，重复重试会继续放大上下文。

本次修正：

- 会话上下文按“最新优先”保留最多 6 条可选历史消息，并按发送者与规范化正文去重；当前问题、系统约束和授权知识来源仍为必需输入。
- Manus `task.create` 保留安全错误类别，客户端明确显示“Manus 模型任务创建”以及参数、目标或前置条件类别；乐享检索、模型创建、模型执行、Runtime 连接和回答来源校验使用不同步骤文案。
- Manus 一旦返回 `task_id`，取消任务总等待上限；单次轮询的网络超时、限流和临时不可用只对同一任务退避重试，直到 Manus 返回终态或用户取消。
- API 到 Runtime 的流式连接不再使用固定总时长计时器；Agent Run Worker 在等待期间按租约三分之一周期续租，避免长任务仍在执行时被其他 Worker 重复领取。

仍保留单次 HTTP 防护和明确错误终态：`task.create` 在没有返回 `task_id` 时若发生不确定网络中断，不能盲目创建第二个付费任务；Manus 明确返回任务 `error`、需要交互、无效响应、认证失败或创建参数错误时，系统应立即显示对应阶段，而不是无限等待或伪装成功。

## 2026-08-20 Manus 创建文本边界修正

新 Run `cc1e3dde-731b-4dbf-95c8-19b9f2750ae5` 证明乐享检索成功返回了 8 条授权证据，Runtime 也已把重复历史压缩到 6 条消息，但最终 Manus `task.create` 的单条文本仍有 12,896 UTF-8 字节，供应商在约 1.2 秒内返回 `invalid_argument`。同一路由、同一 `manus-1.6-lite` 模型和同一账号此前约 10,766 字节的请求可以成功；本地没有配置 `MANUS_PROJECT_ID`，消息也不含控制字符。Manus v2 官方文档仍确认该模型与当前字段合法，但没有公开 `message.content.text` 的长度上限。综合这些证据，本次拒绝最符合供应商未公开的创建文本边界，而不是乐享、超时、账号或项目错误。

API 上下文打包器现对包含 Manus 候选的路由使用 10,000 字节的保守预算，并继续预留 4 KiB 运行时与协议封装空间。按本次真实输入结构估算，8 条证据和 5 条会话会压缩为约 6 条排序靠前的证据加当前问题，最终供应商文本可降到已知成功区间以下。系统按既定优先级保留当前问题、系统安全规则和检索排序靠前的知识证据，再考虑记忆与旧会话；超出部分在调用 Manus 前裁掉，不再把一个必然被供应商拒绝的大请求发送出去。该限制只收紧 Manus 路由，不改变其他模型的已配置上下文预算，也不改变知识权限和引用校验。

## 2026-08-20 会话窗口记忆修正

用户在同一会话中先问“华为的 BLM 讲了什么？”，再追问“还是没懂，能用大白话解释吗？”。第二个 Run `16cded80-582b-403d-884a-9a447fc88c52` 虽然成功，但 Runtime 输入只有 system 和当前 user 两条消息，上一轮问题和 290 字的智能体回答均未进入模型；Memory Snapshot 也有 0 条上下文。原因是 Manus 10 KB 保护生效后，打包器先塞入知识证据，最后才尝试旧消息，知识较多时会把窗口历史全部挤掉。与此同时，乐享检索只使用当前一句追问，无法稳定知道“大白话解释”的对象是 BLM。

现在打包顺序调整为：当前问题与系统规则 → 最近两条窗口消息（通常是上一轮用户问题和智能体回答）→ 授权协作证据 → 乐享/RAG 证据 → 已激活持久记忆 → 更早历史。最近窗口消息单条最多保留 600 个 Unicode 字符，只有超长时才加截断标记，从而在 Manus 安全边界内同时保住对话主题和知识证据。相关追问还会把最近一个不同的用户问题补入乐享检索词；独立的新问题仍只按当前问题检索，避免旧主题污染新检索。

长期记忆方面，项目已有 `memory_records`、候选/激活状态、范围、授权、同意和保留策略，也会在 Agent Run 派发时按相关性载入可访问的 ACTIVE/SEALED Memory；但这几次真实 Run 的 Memory Snapshot 都是 0 条，目前没有自动把普通聊天静默提升为长期记忆。这个边界应继续保留：窗口记忆自动生效，跨会话长期记忆必须经过明确的候选提取、用户确认和权限治理，不能把模型回答或敏感聊天直接永久保存。

## 2026-08-20 知识无命中不再作为回复失败

会话记忆问题“你知道我刚刚问了什么问题吗”对应 Run `30783c11-fcc7-4c32-828e-03eabc168f16`。Manus 已成功生成内容，但系统把检索候选存在误判成这一轮必须形成企业知识引用，最终以 `KNOWLEDGE_GROUNDING_VALIDATION_FAILED` 显示红色失败卡；这不是乐享连接、鉴权或检索接口异常。

现在会话记忆类问题不再因为预取到知识候选而被强制转换为企业知识回答。需要企业依据的问题在检索无命中、候选无法支持结论或模型未形成合法引用时，系统丢弃未经核验的内容并以成功状态发布“当前没有找到你可使用的可靠依据”，不再把正常的知识空结果显示为系统故障。乐享连接失败、认证失败、目标不可用、接口异常和无法解析响应仍保持明确失败码及具体出错步骤，不会被空结果分支吞掉。

## 2026-08-20 消息富文本语义渲染

桌面端消息气泡此前直接用 React 文本节点展示消息正文，模型返回的 `**重点**`、列表、表格和代码块因此会把 Markdown 格式符原样暴露给用户。历史消息与流式回复现在共用同一个安全 Markdown 渲染组件：粗体、斜体、删除线、标题、列表、引用、代码、链接和表格按语义排版，格式符本身不再显示。

渲染层不启用原始 HTML；远程 Markdown 图片只显示替代说明，不直接请求外部资源。长链接和长代码允许断行或在自身区域横向滚动，表格使用独立横向滚动容器，避免消息气泡或会话页面被撑宽。该处理只改变展示，不改写数据库中保存的原始消息正文、知识引用或流式事件。
