# 知识语义服务“不可连接”诊断

## 结论

2026-08-10 本地管理端中 Embedding 与 Reranker 显示“不可连接”，直接原因是 NestJS API 配置的 AI Runtime 地址为 `http://127.0.0.1:8100`，但 8100 端口没有服务监听。API 与管理端分别仍在 3000、4173 端口运行，因此页面可以打开，知识能力则进入降级状态。

当前配置实际使用本地 `local_fastembed`：

- Embedding：`BAAI/bge-small-zh-v1.5`，索引维度 1536；
- Reranker：`BAAI/bge-reranker-base`；
- 项目虚拟环境已安装 `fastembed`、`fastapi` 与 `uvicorn`。

因此本次不是 OpenAI/Cohere 密钥错误，也没有证据表明本地模型损坏；AI Runtime 进程未启动或已经退出。能力探测异常时，后端当前使用固定的 OpenAI-compatible/Cohere-compatible 兜底 Provider 标签，导致页面显示与实际本地 FastEmbed 配置不一致。这是状态展示缺陷，不应据此判断真实供应商。

## 实际影响

在“企业知识库验收”知识库的真实管理页面中确认：

- 8 篇文档、65 个已发布切片均处于就绪状态；
- 当前模型历史向量为 `65 / 65`，语义覆盖显示 100%；
- 检索模式实际为 `LEXICAL`；
- 关系图谱包含 274 个实体、221 条关系，关系检索仍可用；
- 页面明确返回 `EMBEDDING_PROVIDER_UNAVAILABLE`。

历史向量仍保存在索引中，但新问题无法生成查询向量，所以当前不能使用这些向量做语义相似度召回。系统仍可使用关键词、模糊词法匹配、结构化查询和关系图谱增强，因此不会完全失去检索能力，但以下效果会下降：

- 同义词和近义表达的召回；
- 问句与原文措辞不一致时的命中；
- 长自然语言问题的语义相关性排序；
- Reranker 对候选切片的精排与去噪。

查询路径会捕获 Embedding/Reranker 调用失败并安全降级到词法排序。入库路径不同：知识库存在活动 Embedding 索引时，新文档或新版本在索引阶段需要调用 AI Runtime；Runtime 持续不可用会使任务失败并等待重试。因此该状态不仅影响检索质量，也可能影响后续上传和版本更新。

## 恢复与验收标准

本地恢复命令为：

```powershell
pnpm dev:ai
```

或者使用包含 API、AI Runtime、管理端和桌面端的完整启动命令：

```powershell
pnpm dev
```

不能只以端口监听作为完成标准。至少需要确认：

1. AI Runtime `GET /health/ready` 返回 200；
2. API `GET /health/ready` 返回 200；
3. 管理端 Embedding 与 Reranker 显示本地 FastEmbed/BGE 的真实 Provider 和模型名；
4. 知识库运行状态由 `LEXICAL` 恢复到语义模式；
5. 使用自然语言问题执行一次真实检索，结果中有向量候选和 Reranker 诊断；
6. 上传一份测试文档，确认解析、切片、Embedding、索引和自动可用完整成功。

## 2026-08-10 恢复结果

在用户明确要求启动后，已通过 `pnpm dev:ai` 在后台启动 AI Runtime。恢复验证结果：

- AI Runtime `GET /health/live`：200；
- AI Runtime `GET /health/ready`：200，Embedding 与 Reranker 均为 `ready`；
- API `GET /health/ready`：由 503 恢复为 200，`aiRuntime=up`；
- 管理端检索状态：由 `LEXICAL` 恢复为 `HYBRID`；
- Embedding：本地中文模型 `local-fastembed:BAAI/bge-small-zh-v1.5:pad-1536-v1`，65/65 当前切片覆盖；
- Reranker：本地中文模型 `local-fastembed:BAAI/bge-reranker-base:sigmoid-v1`；
- 真实检索诊断：执行了 8 个关键词候选、40 个向量候选和 32 个关系候选，证明查询向量和向量召回链路已实际运行。

实际问题“员工出差报销需要哪些材料？”返回了 3 条权限内证据，但首条来自《企业级知识库搭建指南》，不是预期的《差旅制度》。本次诊断显示 Reranker 未产生可靠分数，最终使用 `WEIGHTED_SCORE` 混合排序。因此本次可以确认服务和向量链路已经恢复，但不能把它描述为检索效果验收通过；仍需以标注问题集调整候选融合、文档权威性和 Reranker 阈值/模型效果。

为避免后续只启动页面而漏掉 AI Runtime 或知识基础设施，新增 `pnpm dev:all` 作为本地完整一键启动入口。它会根据 `.env` 选择普通 PostgreSQL 或 pgvector 开发数据库，启动 Redis、MinIO、Qdrant、Docling、ClamAV并等待就绪，再启动 API、AI Runtime、管理后台和桌面端；`pnpm dev:all:infra` 只启动并检查基础设施。该入口不自动执行 migration 或 seed，避免日常启动隐式修改业务数据。

管理端原先只在文档处理中自动刷新检索状态；如果页面在 AI Runtime 启动前已经读取到 `LEXICAL`，Runtime 恢复后旧状态会一直保留，直到用户手动点击“重新检查”或重新加载页面。现已为 Embedding/Reranker 的 `UNAVAILABLE`、`NOT_READY` 增加 5 秒恢复轮询；服务恢复后页面自动重新读取 readiness 并切换为 `HYBRID`，能力就绪后停止轮询，不对正常知识库持续发起状态请求。
