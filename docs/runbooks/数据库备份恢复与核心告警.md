# 数据库备份、恢复演练与核心告警

本基线把“有备份”和“备份确实可恢复”分开验证。脚本不会重启 API、AI Runtime、管理端或桌面端，也不会修改源数据库。恢复脚本只接受以 `_restore_rehearsal` 结尾的临时库名，并硬性拒绝 `enterprise_agent`、`enterprise_agent_acceptance` 和 PostgreSQL 系统库。默认还会拒绝在备份来源容器中恢复，目标库已存在时也不会终止连接或覆盖。

## 1. 创建可校验备份

备份目录必须先被显式声明为专用目录。初始化器拒绝卷根、符号链接和 reparse point；不会静默接管任意已有目录：

```powershell
.\infra\scripts\Initialize-EnterpriseBackupDirectory.ps1 `
  -Path .\.data\backups
```

```powershell
.\infra\scripts\Backup-EnterpriseDatabase.ps1 `
  -Container enterprise-agent-postgres-1 `
  -Database enterprise_agent `
  -DatabaseUser enterprise_agent `
  -RetentionDays 14
```

每次备份生成 PostgreSQL custom archive 和 JSON manifest。文件名包含 UTC 秒时间与随机标识；同一数据库、同一目录同时只能有一个进程持有独占锁，避免每日备份和恢复演练互相覆盖。Manifest 包含 SHA-256、已完成 migration 数、最新 migration、强制 RLS 表数量，以及少量关键表行数观察值；不写数据库密码或连接 URL。migration/RLS/行数在 `pg_dump` 快照结束后采集，只用于诊断，不作为恢复相等性门禁。备份只有在容器内临时归档确认删除后才会发布 `backup-created`；无法确认清理时直接失败。

Windows ACL 会收紧为当前用户、SYSTEM 和内置 Administrators；Linux 使用目录 `0700`、文件 `0600`，无法执行 `chmod` 时直接失败。仓库本地目录只用于开发和验收，生产仍必须复制到加密、不可变、异地的对象存储。

## 2. 在隔离临时库执行恢复演练

```powershell
.\infra\scripts\Test-EnterpriseDatabaseRestore.ps1 `
  -Container enterprise-agent-restore-postgres-1 `
  -DatabaseUser enterprise_agent `
  -ManifestPath .\.data\backups\enterprise_agent-20260721T010203Z-<random>.manifest.json `
  -TargetDatabase enterprise_agent_restore_rehearsal
```

恢复容器必须预建与生产一致的全局数据库角色。恢复门禁逐项精确验证：

- 由 PostgreSQL 目录自动发现全部公共 `tenant_id` 表；每张表都必须启用 `ENABLE/FORCE RLS`、不存在 PUBLIC 表级或列级 DML，并至少具有使用规范 `app.tenant_id` 谓词的 restrictive `FOR ALL` 策略。当前 schema 实测发现 215 张，但该数字只是观察值，不是需要人工更新的放行常量；未来新增表会自动进入门禁。具备 ACL 却未被 restrictive 策略覆盖的跨租户职责采用精确的“表 + 角色”审核清单，新增或删除例外都会失败；
- `auth_login_rate_limits` 预认证表的特殊 RLS 边界，以及 action token 的角色、策略数量和表达式；
- `agent_runs`、`auth_action_tokens`、`auth_login_rate_limits`、`outbox_events` 及四张知识图谱表的精确表级 ACL，Outbox 状态机字段、任职字段、Tool Gateway 父资源读取、SCIM 去开通和租户配额字段的精确列级 ACL，以及不存在 PUBLIC、职责外角色或图谱列级意外授权；图谱表只允许 `enterprise_agent_app` 读取，`enterprise_agent_admin` 执行 `SELECT/INSERT/UPDATE/DELETE`；
- 职责角色的精确能力边界，包含 `NOLOGIN/NOBYPASSRLS/NOSUPERUSER/NOINHERIT`，并拒绝除当前 migration 登录外的多能力 `LOGIN` 角色；
- action token 的 PK、token hash 唯一约束、三个 FK 的键顺序与删除行为、八个检查约束、active-token 部分唯一索引和两个支持索引，以及 Agent Run 用量约束的精确定义；投递目标证据还会校验不可变触发器、触发函数定义与函数 ACL，并通过删除证据约束、禁用触发器和向 `PUBLIC` 授予函数执行权三项事务内反向控制证明门禁能够失效可见。

正向检查之后，脚本会对基础 RLS 边界依次执行四个事务内反向控制，确认门禁确实能拒绝关闭 `agent_runs` FORCE RLS、把租户策略弱化为 `OR true`、创建未登记的公共 `tenant_id` 表，以及关闭 `auth_login_rate_limits` FORCE RLS；action token 投递目标等专项门禁还会执行各自的反向控制。每次验证后都会回滚并重新检查基线。

恢复目标必须是长度不超过 63 字符的 ASCII 数据库标识。脚本在创建后记录数据库 OID，并写入本次演练的随机 GUID comment；清理前必须同时匹配 OID 与 GUID，只会删除自身创建且身份未变化的目标。默认在校验后删除临时恢复库。只有容器临时归档和临时数据库均完成清理，脚本才会原子发布 `status=restore-verified`、`cleanupVerified=true` 的报告；操作、校验或清理失败会写入相应失败状态，绝不会留下可被探针接受的成功报告。排查时可显式加 `-KeepRestoredDatabase`，但不得把业务连接串切到演练库。

仅对已经与开发/生产完全隔离的验收容器，允许显式使用 `-AllowSharedCluster`。已存在的演练库只有同时传入 `-ReplaceExistingTarget` 才会被覆盖；生产自动化不得使用这两个开关规避隔离要求。

2026-07-22 的独立真实演练中，17/17 项恢复检查全部通过，报告为 `restore-verified`、`cleanupVerified=true`，临时恢复库在结束后不存在；归档 SHA-256 为 `e91c829b62438a33178ec2585ece4bd4e267b8e8f3bb8eba043755632c4e5707`。这证明该次归档和门禁可恢复，不代表加密异地存储、定时调度或生产灾备已经接线。

知识图谱迁移加入后，当前门禁新增 `knowledgeGraphTablesReadable`，会实际读取四张图谱表并将行数写入恢复报告；连同扩展后的精确 RLS 和 ACL 矩阵，当前恢复报告包含 18 项核心检查。上述 17/17 是 2026-07-22 旧基线的历史证据，不能替代应用最新迁移后的重新备份和恢复演练。

## 3. 核心告警探针

```powershell
.\infra\scripts\Test-EnterpriseCoreAlerts.ps1 `
  -Container enterprise-agent-postgres-1 `
  -Database enterprise_agent `
  -DatabaseUser enterprise_agent `
  -ExpectedEmbeddingModel text-embedding-model-immutable-version
```

当 Docker CLI 不可用时，可复用受控的 native 或 WSL PostgreSQL 客户端目录直接连接；密码、passfile 与 TLS 配置只通过 libpq 的进程环境变量传入，禁止放进命令参数：

```powershell
.\infra\scripts\Test-EnterpriseCoreAlerts.ps1 `
  -PgBinDirectory .\.data\pgclient16\root\usr\lib\postgresql\16\bin `
  -Host 127.0.0.1 `
  -Port 55435 `
  -Database enterprise_agent `
  -DatabaseUser enterprise_agent `
  -ExpectedEmbeddingModel text-embedding-model-immutable-version
```

Docker 仍是默认参数集，`-Container` 与 `-PgBinDirectory` 互斥。两种模式都使用 `psql --file=-`，探针 SQL 通过 UTF-8 标准输入传输，不进入进程参数。

探针输出结构化 JSON。顶层 `status=healthy` 时退出码为 `0`；存在基础运行告警时为 `alerting`，指定模型缺少可验收证据时为 `not_ready`，后二者退出码均为 `2`。`healthStatus` 只表示 Outbox、Agent Run、备份等基础运行信号是否健康，不能作为语义向量验收结论；指定 `ExpectedEmbeddingModel` 后必须同时看到 `semanticReadiness.status=ready` 和 `semanticReadiness.evidenceVerified=true` 才能证明当前非空知识切片已被该模型的 1536 维向量完整覆盖。

当当前知识切片数为 `0` 时，基础 `healthStatus` 仍可为 `healthy`，但语义状态会明确返回 `insufficient_evidence`，顶层状态为 `not_ready`，并在 `readinessBlockers` 中返回 `KNOWLEDGE_EMBEDDING_EVIDENCE_EMPTY`。这避免 SQL 空集合的“缺失数为 0”被误读为真实模型验收通过。省略 `ExpectedEmbeddingModel` 时语义状态为 `not_evaluated`，仅执行日常运行探针，不构成模型覆盖证明。

当前覆盖：

- Outbox `UNKNOWN` 与超时积压；
- Agent Run `UNKNOWN`、长时间排队和长时间执行；
- 最近 24 小时知识入库失败；
- 当前知识版本缺少指定不可变 Embedding 模型的 1536 维向量，以及指定模型但当前没有任何知识切片、无法形成非空验收证据的情况；
- 终态运行仍保留未核实 Token 占位、租户月配额逼近阈值、登录桶被阻断；
- 备份 manifest、来源或归档大小不匹配；高频探针只校验受保护的 manifest 元数据和文件大小，避免每个监控周期重读整个归档，完整 SHA-256 在备份创建、恢复演练和显式低频完整性检查时验证；
- 最新有效备份超过允许的新鲜度，或最近一次独立恢复演练报告失败/过期。每日新备份不会再使仍处于 SLA 内的周恢复报告失效。

部署环境应让任务调度器定时运行备份和探针，并把非零退出码接入企业现有告警通道。恢复演练至少每日或每周自动执行一次，且必须保存报告。脚本本身不包含短信、邮件或 IM 凭据，也不把凭据写入日志。

状态判定、任务参数、签名、目录安全和恢复 SQL 可在不连接数据库的情况下执行回归测试：

```powershell
Get-ChildItem .\infra\scripts\tests\Test-*.ps1 | ForEach-Object {
  powershell.exe -NoProfile -NonInteractive -File $_.FullName
  if ($LASTEXITCODE -ne 0) { throw "Offline test failed: $($_.Name)" }
}
```

当前离线回归基线为 12 个 suite、414 个断言通过；它验证脚本契约、反向场景、生产连续性配置、Prometheus 指标和灾备报告，不替代真实归档恢复、异地副本或 PITR。

## 4. 服务探针、告警投递与无人值守任务

数据库信号健康并不代表在线服务可用。服务探针会分别验证 API liveness、API readiness、管理端 HTTP 和 AI Runtime readiness；只记录状态码与归一化状态，不采集或转发上游正文，并拒绝 HTTP 重定向，避免把 3xx 登录页或跳转页误判为健康服务：

```powershell
.\infra\scripts\Test-EnterpriseServiceHealth.ps1 `
  -ApiBaseUrl https://api.example.com `
  -AdminBaseUrl https://admin.example.com `
  -AiRuntimeBaseUrl https://ai-runtime.example.com
```

`Invoke-EnterpriseMonitoringCycle.ps1` 会在隔离子进程中组合数据库核心探针与服务探针，原子写入 `.data/monitoring/latest-monitoring-result.json`；语义 `not_ready` 会保留为阻断信号。子进程异常、非预期退出码、无效 JSON、缺失字段以及状态/退出码矛盾都会归一为可投递的 `PROBE_*` 告警，不会因 StrictMode 中断而静默消失。若本地监控结果无法持久化，系统会生成结构化持久化失败告警，并在启用投递时直接以 JSON 发送到 webhook，避免本地磁盘故障同时吞掉告警。生产可通过环境变量配置通用 HTTPS webhook：

```powershell
$env:ENTERPRISE_ALERT_WEBHOOK_URL = 'https://alerts.example.com/hooks/enterprise-agent'
$env:ENTERPRISE_ALERT_WEBHOOK_BEARER_TOKEN = '<由 Secret Manager 注入，可省略>'
$env:ENTERPRISE_ALERT_WEBHOOK_SIGNING_KEY = '<由 Secret Manager 注入，可省略>'

.\infra\scripts\Invoke-EnterpriseMonitoringCycle.ps1 `
  -Container enterprise-agent-postgres-1 `
  -Database enterprise_agent `
  -DatabaseUser enterprise_agent `
  -ExpectedEmbeddingModel text-embedding-model-immutable-version `
  -ApiBaseUrl https://api.example.com `
  -AdminBaseUrl https://admin.example.com `
  -AiRuntimeBaseUrl https://ai-runtime.example.com `
  -Deliver
```

Webhook URL、Bearer Token 和签名密钥不会进入任务参数、结果 JSON 或日志。HMAC 实现兼容安装器使用的 Windows PowerShell 5.1；正文按 UTF-8 字节发送，Webhook 投递同样拒绝 HTTP 重定向，避免凭据或签名头被转发到其他目标。投递失败返回退出码 `3`，基础/语义/服务告警返回 `2`。`Invoke-EnterpriseBackupRehearsal.ps1` 串联备份和隔离恢复，并自动生成 `DATABASE_ISOLATED_REHEARSAL` 灾备报告；只有恢复报告为 `restore-verified` 且数据库 RPO/RTO 分别不超过 15 分钟和 240 分钟时成功。报告始终保留生产流量切换、异地恢复和 PITR 未验证边界。

Windows 部署可使用下面的安装器注册三个 SYSTEM 计划任务：每日备份、每周隔离恢复、周期监控。安装器要求生产 HTTPS 服务地址、不可变 Embedding 模型名、独立恢复容器，并默认要求机器级 webhook。安装时会显式初始化专用备份目录；每日备份和周恢复不能配置到同一小时。`-WhatIf` 会创建但不注册任务定义，并自检最终 argument line 已展开全部数组且包含必需开关：

```powershell
.\infra\scripts\Register-EnterpriseWindowsOperations.ps1 `
  -SourceContainer enterprise-agent-postgres-1 `
  -SourceDatabase enterprise_agent `
  -SourceDatabaseUser enterprise_agent_backup `
  -RestoreContainer enterprise-agent-restore-postgres-1 `
  -RestoreDatabaseUser enterprise_agent_restore `
  -ExpectedEmbeddingModel text-embedding-model-immutable-version `
  -ApiBaseUrl https://api.example.com `
  -AdminBaseUrl https://admin.example.com `
  -AiRuntimeBaseUrl https://ai-runtime.example.com `
  -WhatIf
```

Linux/Kubernetes 不运行 Windows 安装器，而由 cron/CronJob 调用相同的一次性脚本；必须先初始化备份目录，并使用具备最小 Docker/PostgreSQL 权限的服务账号。任务注册只是调度接线基线：生产仍需以真实 SYSTEM/服务账号启动一次任务，验证能够找到 Docker CLI、访问容器与目录；还必须向真实 webhook 发送签名测试告警并确认值班系统收到。

## 5. 生产门禁

- 连续备份任务成功不代表恢复可用；最近一次恢复报告必须为 `restore-verified`，最近一次数据库灾备报告必须为 `database-objectives-met`。
- 恢复演练使用与生产相同的 PostgreSQL/pgvector 主版本。
- 备份文件需进入加密对象存储并设置不可变保留策略；本地 `.data/backups` 仅用于开发和验收。
- `semanticReadiness=ready` 只证明非空切片拥有指定模型名和维度的记录，无法排除零向量或 mock 数据；真实 Embedding、Reranker 和企业问题集仍需单独验收。
- 告警通道、值班轮转、完整业务 RPO/RTO、跨区域副本和密钥托管仍属于部署环境责任；仓库只能验证隔离数据库恢复目标，不能替代生产流量切换。
