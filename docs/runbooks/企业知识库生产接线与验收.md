# 企业知识库生产接线、验收与故障恢复

本文对应当前仓库已经实现的知识入库链路：

`上传 → S3 对象账本 → ClamAV 扫描 → Docling 解析/OCR → 统一结构化 JSON → 切片 → 实体/关系/证据投影 → Embedding → Qdrant Dense/Sparse + PostgreSQL 关键词账本 → 混合融合/关系扩展 → Reranker → 证据充分性检查 → 发布`

它不替代数据库迁移、备份恢复、企业问题集或供应商合同审查。生产发布仍需同时执行：

- [数据库备份恢复与核心告警](./数据库备份恢复与核心告警.md)
- [真实语义检索与企业问题集验收](./真实语义检索与企业问题集验收.md)

## 1. 生产拓扑与责任边界

| 组件                       | 当前职责                                                       | 生产边界                                                |
| -------------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| NestJS API                 | 租户/RLS、文档版本、对象账本、任务租约、切片、发布、引用和审计 | 唯一可修改知识账本的服务                                |
| S3 兼容对象存储            | 保存上传原文件和统一结构化 JSON                                | 只保存对象，不决定租户权限和发布状态                    |
| ClamAV `clamd`             | 对上传字节执行恶意内容扫描                                     | 必须位于私网，扫描失败时入库失败关闭                    |
| Docling Serve              | PDF/DOCX/XLSX/PPTX/图片的 OCR、表格和版面解析                  | 视为不可信解析器；API 负责请求/响应大小、超时和结构校验 |
| Apache Tika                | 旧版 `.ppt`（OLE2）正文提取，底层由 Apache POI 解析            | 与 Docling 相同，限制源文件/响应大小和超时，不暴露公网  |
| AI Runtime                 | Embedding、Reranker 能力和供应商适配                           | 供应商密钥只进入 Runtime，不进入 API 或前端             |
| Qdrant                     | 已发布切片的 Dense、Sparse、RRF 和 Payload 初筛                | 不是业务事实账本；命中 ID 必须回 PostgreSQL 复核        |
| PostgreSQL/pgvector        | 文档、版本、任务、切片、回退向量、实体、关系、证据和审计账本   | 不通过人工 SQL 跳过状态机；Qdrant 不可用时可安全回退    |
| Knowledge Ingestion Worker | 持久队列消费、租约心跳、重试和终态落账                         | 至少一个实例启用；多实例通过 `SKIP LOCKED` 协作         |

生产网络只应允许：

- API/Worker 通过 HTTPS 访问对象存储、Docling 和 AI Runtime；
- API/Worker 通过私网 TCP 访问 `clamd`；
- AI Runtime 通过 HTTPS 访问已批准的 Embedding/Reranker 供应商；
- `clamd` 3310、Docling 原始服务端口和数据库不得直接暴露公网。

## 2. API/Worker 配置

下面是变量清单，不是可直接部署的 Secret 文件。所有 URL、桶名、账号和密钥必须由部署系统注入；不得提交真实值。

```dotenv
NODE_ENV=production
REPOSITORY_DRIVER=prisma

# 使用职责分离的数据库账号。启用生产 Worker 时 OUTBOX_DATABASE_URL 必填，
# 且用户名必须与 DATABASE_URL 不同。
DATABASE_URL=<由 Secret Manager 注入>
ADMIN_DATABASE_URL=<由 Secret Manager 注入>
AUTH_DATABASE_URL=<由 Secret Manager 注入>
LIFECYCLE_DATABASE_URL=<由 Secret Manager 注入，必须使用独立用户名>
OUTBOX_DATABASE_URL=<由 Secret Manager 注入>

# API 到独立 AI Runtime。
AI_RUNTIME_URL=https://ai-runtime.internal.example
KNOWLEDGE_SEMANTIC_SEARCH_ENABLED=true
KNOWLEDGE_RERANK_ENABLED=true
KNOWLEDGE_AI_TIMEOUT_MS=30000
KNOWLEDGE_EMBEDDING_DIMENSIONS=1536
KNOWLEDGE_VECTOR_SEARCH_MODE=hnsw

# 大规模向量与稀疏检索。Qdrant 在事务外执行，PostgreSQL 对命中切片再次做
# 租户、知识库、当前发布版本、文档状态和资源策略校验。
KNOWLEDGE_SEARCH_INDEX_DRIVER=qdrant
KNOWLEDGE_QDRANT_URL=https://qdrant.internal.example
KNOWLEDGE_QDRANT_API_KEY=<由 Secret Manager 注入>

KNOWLEDGE_INGESTION_MAX_ATTEMPTS=5

```

配置约束：

- 生产环境拒绝 `KNOWLEDGE_OBJECT_STORE_DRIVER=local`、`KNOWLEDGE_FILE_SCANNER_DRIVER=disabled` 和非 `docling` 解析器。
- S3 `default_chain` 模式不得同时填写静态 Access Key；优先使用工作负载身份/IAM Role。只有无法使用工作负载身份时才选择 `static` 并通过 Secret 注入两项凭据。
- 生产 S3 必须填写与部署区域、AWS partition 一致的客户管理 KMS Key 完整 ARN；alias、裸 Key ID 和依赖桶默认加密都会在生产配置校验时被拒绝。开发环境可留空以兼容本地 MinIO。
- 自定义 S3 endpoint 和 Docling URL 在生产环境必须是无凭据、无 query/fragment 的 HTTPS origin。
- 文档源 Manifest 和文件下载只允许 `KNOWLEDGE_SOURCE_SYNC_ALLOWED_HOSTS` 中的精确主机名；不支持通配符。生产必须关闭 `KNOWLEDGE_SOURCE_SYNC_ALLOW_LOCAL_FIXTURE`。
- 当前受控取数器只接受 HTTPS、默认 443 端口、无 URL 用户名/密码、无 fragment、解析结果全部为公网地址的目标；拒绝跳转和压缩响应，并固定 DNS 解析结果用于实际连接。生产网盘适配器应经专用出站网关暴露，不要把 API 配置为直连 RFC1918 私网或任意用户 URL。
- `KNOWLEDGE_FILE_SCANNER_TIMEOUT_MS` 必须小于 `KNOWLEDGE_INGESTION_CLAIM_TTL_MS`。
- `KNOWLEDGE_INGESTION_CLAIM_TTL_MS` 必须比 `KNOWLEDGE_AI_TIMEOUT_MS` 至少多 15 秒。Worker 在长任务执行期间每约三分之一租约周期续租。
- `KNOWLEDGE_INGESTION_RETRY_BASE_MS` 不得大于 `KNOWLEDGE_INGESTION_RETRY_MAX_MS`。
- HTTP 上传控制器当前最多接收 20 MB；即使对象存储上限更高，单次管理端上传仍以 20 MB 为准。
- 生产环境默认 `KNOWLEDGE_PERSISTENT_WRITES_ENABLED=false`，此时上传、网页导入、重试、重建向量和重建图谱命令会返回 HTTP 503，错误码为 `KNOWLEDGE_PERSISTENT_WRITES_DISABLED`。
- 生产环境若设置 `KNOWLEDGE_PERSISTENT_WRITES_ENABLED=true`，必须同时设置 `KNOWLEDGE_INGESTION_WORKER_ENABLED=true`，否则 API 在配置校验阶段直接拒绝启动。启用 Worker 的生产进程还必须提供独立最小权限的 `OUTBOX_DATABASE_URL`。
- Worker 启动后必须先成功轮询一次持久化队列，`GET /health/ready` 才会报告 `checks.knowledgeIngestion=up`；启动中、队列账号失效或轮询失败时 readiness 为 503，所有入库写命令返回 `KNOWLEDGE_INGESTION_CONSUMER_UNAVAILABLE`，不会先接受任务再永久积压。

`KNOWLEDGE_VECTOR_SEARCH_MODE=exact` 适合小数据量基线和结果对照；切换 `hnsw` 前应确认目标数据库已有匹配索引、查询计划和企业问题集回归结果，不能只改变量。

## 3. S3 兼容对象存储

当前适配器实际调用 `PutObject`、`GetObject`、`HeadObject` 和 `DeleteObject`。同一版本至少有两类对象：

`<KNOWLEDGE_OBJECT_STORE_S3_PREFIX>/<tenant UUID>/<document UUID>/<version UUID>.bin`

`<KNOWLEDGE_OBJECT_STORE_S3_PREFIX>/<tenant UUID>/<document UUID>/<version UUID>.structured.json`

原件用于下载、审计和重解析；结构化对象保存解析器原始表示、规范化正文、页/表格元素和 parser provenance。两者均有独立的对象长度和 SHA-256 账本，不能用结构化结果替代原件。

生产权限应限制在专用桶和上述前缀，不授予桶管理权限。对象写入会显式发送
`ServerSideEncryption=aws:kms` 和 `SSEKMSKeyId=<配置的 Key ARN>`，不依赖桶默认加密。
IAM Role 除前缀级 `s3:PutObject`、`s3:GetObject`、`s3:DeleteObject` 外，只能对该客户管理
Key 使用必要的 `kms:Encrypt`、`kms:Decrypt`、`kms:GenerateDataKey`；Key policy 还应通过
`kms:ViaService` 和加密上下文把使用范围约束到目标 S3 区域及专用桶。

建议同时启用：

- Bucket policy 拒绝未携带 `aws:kms`、错误 KMS Key ARN 或非 TLS 的写入；
- Bucket Versioning、访问日志、生命周期和删除保护；
- 跨区域复制或独立备份，并把原文件恢复纳入数据库恢复演练；
- 私网 endpoint、TLS 校验和出站 allowlist；
- 对象写入、读取错误率与延迟告警。

代码写入时携带 SHA-256 provider checksum 和 `sha256` metadata，并用 `If-None-Match: *`
防止覆盖同一逻辑对象。`HeadObject`（条件写冲突）与 `GetObject`（读取）都必须由 AWS 响应
返回 `ServerSideEncryption=aws:kms` 及与配置完全一致的 `SSEKMSKeyId`；缺失、SSE-S3、
错误 Key 或别名/ARN 漂移一律按完整性故障 fail closed。随后还会核对对象长度、provider
checksum、metadata 和数据库账本。

上线 canary 必须用生产身份完成一次写入、Head、Get，并在 CloudTrail/KMS 审计中确认目标
Key；再分别使用错误 Key、缺失加密头和被撤销 KMS 权限做负向验证。注意 S3 SDK 的可信响应
字段是 `ServerSideEncryption` 与 `SSEKMSKeyId`，不要把自定义 metadata 当作加密证明。

`KNOWLEDGE_OBJECT_INTEGRITY_FAILED` 是非自动重试故障：不要覆盖原对象或直接修改数据库
checksum，应隔离该版本、调查对象/账本漂移和 KMS 配置，再上传一个新版本。

## 4. ClamAV `clamd`

API 使用 `INSTREAM` 协议把内存中的受限字节流发送给 `clamd`，不会调用 shell，也不会把文件写入扫描机临时路径。

生产要求：

- 使用固定版本镜像/软件包并持续运行官方签名更新任务；
- `clamd` 与 API/Worker 使用私网和网络策略隔离，3310 不对公网开放；
- 配置资源上限，保证最大扫描流不低于 `KNOWLEDGE_OBJECT_STORE_MAX_BYTES`；
- 为进程、签名新鲜度、TCP 可达性、超时率和感染命中建立告警；
- 发布前使用无害文件、组织批准的 EICAR 测试流程和超时/断网故障注入分别验证 `clean`、`infected` 和 fail-closed。

处理语义：

| 扫描结果               | 入库结果                                               |
| ---------------------- | ------------------------------------------------------ |
| `clean`                | 继续解析，并在审计事件记录 `securityScanVerdict=clean` |
| `infected`             | `KNOWLEDGE_FILE_INFECTED`，非自动重试                  |
| 超时、不可达、协议错误 | `KNOWLEDGE_FILE_SCAN_UNAVAILABLE`，按任务退避重试      |
| `disabled`             | 仅开发可得到 `not_scanned`；生产配置会在启动时被拒绝   |

感染文件不得通过“重试”放行。应隔离对象、按安全事件流程调查，再由授权人员上传经过处置的新版本。

## 5. Docling Serve

生产应部署固定版本或固定镜像 digest 的 Docling Serve，并在私网入口设置 `DOCLING_SERVE_API_KEY`。API 通过 `X-Api-Key` 调用同步 `POST /v1/convert/file`；官方 REST 契约见 [Docling REST API](https://docling-project.github.io/docling/usage/api_server/rest_api/)。

当前集成边界：

- PDF、DOCX、XLSX、PPTX 和常见图片交给 Docling；旧版 OLE2 `.ppt` 交给 Apache Tika/POI；纯文本与 Markdown 仍由 API 本地解析器处理；
- Tika 通过 `PUT /tika` 接收 `application/vnd.ms-powerpoint`，API 会先验证 OLE2 文件头，且只接收受限大小的 UTF-8 纯文本响应；
- 请求启用 OCR、`accurate` 表格模式、图片占位符和页分隔标记；
- 只接受 `status=success` 且存在 Markdown 正文的 JSON；
- API 校验文件签名、源文件大小、响应大小、UTF-8、控制字符、页序和非空文本；
- 解析器返回规范化文本、页码、表格/版面结构和 parser provenance，不接管租户权限、版本或发布；
- API 将通过边界校验的结构化表示另存为不可覆盖对象，并在管理端提供只读预览。

部署探针应至少包括：

- 进程/容器存活；
- Docling 版本对应的 HTTP health endpoint；
- 带 `X-Api-Key` 的小型 PDF、扫描 PDF 和含表格 DOCX 转换 canary；
- OCR 模型缓存、CPU/GPU、内存、队列长度、转换耗时和失败率。

不要用 `/docs` 返回 200 代替转换 canary。当前 API 使用同步转换端点，Docling 扩容、超时和 API 的 Worker 并发必须一起压测。对大型扫描件，应先测出 P95/P99 再调整 `KNOWLEDGE_DOCLING_TIMEOUT_MS` 和 Worker 容量。

### 5.1 Qdrant 索引同步与回退

Qdrant collection 使用 1536 维 Dense 向量和文本生成的 Sparse 词项向量，查询侧由 Qdrant 执行融合。Payload 至少携带 tenant、knowledge base、document、version、classification、发布状态和内容哈希。生命周期规则如下：

- 版本发布或重建索引时，对该版本执行幂等 upsert；
- 版本归档时删除该版本全部 point；
- 查询 Qdrant 必须在 Prisma 交互事务外完成，避免外部 HTTP 延迟占用数据库事务；
- Qdrant 返回的 chunk ID 只作为候选，PostgreSQL 必须再次校验当前版本、文档状态和资源策略；
- Qdrant 超时或不可用时记录 `KNOWLEDGE_QDRANT_UNAVAILABLE`，并回退到 PostgreSQL/pgvector，不得返回未经账本校验的 payload 文本。

### 5.2 企业网盘/文档源增量同步

当前 API 使用通用 `HTTPS_MANIFEST` 协议，把飞书、SharePoint、企业微信、Box 或自建网盘的厂商差异隔离在受控网关。连接器在 PostgreSQL 保存名称、Manifest URL、状态、成功游标和运行统计；远端条目保存稳定 `externalId`、`sourceRevision`、SHA-256/ETag 等来源证据。原文件仍由统一入库链写入 S3，正文和大文件不会放进 PostgreSQL。

Manifest 必须以 `application/json` 返回，结构如下：

```json
{
  "schemaVersion": 1,
  "nextCursor": "opaque-cursor-2026-08-05T12:00:00Z",
  "hasMore": false,
  "items": [
    {
      "externalId": "drive-file-stable-id",
      "title": "国内差旅制度",
      "fileName": "国内差旅制度.docx",
      "mimeType": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
      "downloadUrl": "https://knowledge-source-gateway.example.com/files/temporary-token",
      "sourceUri": "https://drive.example.com/docs/drive-file-stable-id",
      "sourceRevision": "revision-42",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "modifiedAt": "2026-08-05T12:00:00+08:00",
      "deleted": false
    }
  ]
}
```

删除条目使用相同 `externalId`，设置 `deleted=true` 且 `downloadUrl=null`。同步语义和安全边界如下：

- `externalId` 必须在连接器内稳定；标题或文件名不能作为主身份。`sourceRevision`、SHA-256 或 ETag 用于识别无需处理、更新和可追溯版本；服务端仍会核对实际下载文件 SHA-256。
- 一页最多 1,000 条、一次同步最多处理 1,000 条，并受 `KNOWLEDGE_SOURCE_SYNC_MAX_PAGES`、Manifest 字节上限、单文件对象上限和 HTTP timeout 共同约束。
- 所有页和条目都成功时才提交新游标；任一条失败时运行标记为失败并保留旧游标，重试从旧游标开始。远端写接口必须保证相同 revision 的重复拉取幂等。
- 更新创建新的文档版本并走扫描、解析、切片、Embedding、Qdrant 和关系投影；删除归档当前文档并使其版本 point 退出当前检索，但保留版本、来源和审计账本。
- Manifest 入口不携带长期 OAuth/Access Token。厂商 OAuth、服务账号、续期和限流由网关或 Secret Manager 管理；短期预签下载 URL 只能授予单文件读取并应在同步窗口后失效。不得在 Manifest、数据库、日志或失败消息中返回厂商密钥。
- 当前连接器由管理员在知识库界面手动触发；生产周期调度、Webhook 去抖、断点续传、厂商 429 退避和原始 ACL 到 `resourceScopeId` 的投影仍需在厂商适配层完成并单独验收。

开发环境可用以下命令启动或停止 MinIO、Qdrant、Docling、Apache Tika 和 ClamAV：

```powershell
pnpm dev:knowledge-infra
pnpm dev:knowledge-infra:down
```

已有验收知识库可直接执行完整复验：

```powershell
$env:KNOWLEDGE_SMOKE_KB_ID='<knowledge-base-uuid>'
node tools/knowledge-smoke/run-e2e.mjs
```

脚本会验证六种格式的 READY/发布状态、结构化对象读取、四个正向问题首条来源、一个无答案问题和 Qdrant point/vector 数量，并把证据写入 `.data/knowledge-smoke/e2e-report.json`。

## 6. Embedding 与 Reranker

Embedding/Reranker 密钥只配置在 AI Runtime：

```dotenv
AI_RUNTIME_EMBEDDING_DRIVER=openai_compatible
AI_RUNTIME_EMBEDDING_BASE_URL=https://<approved-provider>/v1
AI_RUNTIME_EMBEDDING_API_KEY=<由 Secret Manager 注入>
AI_RUNTIME_EMBEDDING_MODEL=<不可变部署/版本名>
AI_RUNTIME_EMBEDDING_DIMENSIONS=1536
AI_RUNTIME_EMBEDDING_TIMEOUT_SECONDS=30

AI_RUNTIME_RERANK_DRIVER=cohere_compatible
AI_RUNTIME_RERANK_BASE_URL=https://<approved-provider>/v2
AI_RUNTIME_RERANK_API_KEY=<由 Secret Manager 注入>
AI_RUNTIME_RERANK_MODEL=<不可变部署/版本名>
AI_RUNTIME_RERANK_TIMEOUT_SECONDS=30
```

API 与 Runtime 必须同时满足：

- API：`KNOWLEDGE_SEMANTIC_SEARCH_ENABLED=true`、`KNOWLEDGE_RERANK_ENABLED=true`；
- Runtime：两个 provider 均不是 `disabled`，模型名固定，Embedding 维度恰为 1536；
- 新入库切片由当前 Embedding 模型完整生成非零有限向量；
- Reranker 返回请求内唯一候选、0～1 分数和确定的模型名；
- 模型升级采用“新模型生成全量向量 → 企业问题集验收 → 切换 → 保留回滚窗口”，不得让同一发布批次静默漂移模型别名。

`GET /health/ready` 和 capability 只证明配置/本地生命周期就绪，不会发起可能计费的供应商 smoke。真实供应商、非零向量、Reranker 排序和 ACL 必须通过“真实语义检索与企业问题集验收”。

AI Runtime 自身的生产门禁仍然有效。若部署版本尚未提供持久化 `RunStore`，不得通过保留 development/memory 配置来冒充完整生产 Runtime；知识 Provider 验收通过也不能替代对话 Run 的生产持久化验收。

## 7. 异步 Worker、租约和重试

上传接口只负责持久化版本、原文件和 `PENDING` 任务，随后立即返回。Worker 的正常阶段为：

`UPLOADED → SECURITY_CHECK → PARSING → CHUNKING → INDEXING → READY`

任务状态为 `PENDING → RUNNING → SUCCEEDED | FAILED`。多个实例使用 `FOR UPDATE SKIP LOCKED` 领取任务；`RUNNING` 租约过期后可被其他实例重新领取。执行中的 Worker 定期续租，失去租约的旧实例不能覆盖新实例结果。

自动重试使用指数退避和抖动，最多 `KNOWLEDGE_INGESTION_MAX_ATTEMPTS` 次。可重试场景包括扫描服务不可用、Docling 超时/不可用、AI Runtime/供应商暂时不可用和未分类的瞬时入库错误。恶意文件、格式/签名错误、无文本、对象冲突或完整性失败不会盲目重试。

容量规划：

- 每个 API 进程当前可同时领取 `KNOWLEDGE_INGESTION_BATCH_SIZE` 个任务；
- 总并发约为启用 Worker 的实例数乘以 batch size；
- 先根据 Docling、ClamAV、Embedding 的最低稳定并发设上限，再扩 API/Worker；
- 监控 `PENDING` 最老年龄、`RUNNING` 租约过期数、attempts、各 stage 耗时、24 小时失败数和供应商 429；
- 滚动发布应先停止新领取并等待活动批次结束；即使实例异常退出，过期租约也会恢复任务，但会增加一次 attempt。

不要通过 SQL 把任务强制改成 `SUCCEEDED`、把版本改成 `READY` 或手工绑定 `currentVersionId`。

当前生产部署单元使用 API 内嵌 Worker。只有同时满足
`KNOWLEDGE_PERSISTENT_WRITES_ENABLED=true`、
`KNOWLEDGE_INGESTION_WORKER_ENABLED=true` 且 Worker 已成功轮询持久化队列的实例，才能接收知识写入流量。若需拆成独立 Worker Deployment，必须先增加跨进程消费者心跳/租约探针，不能仅用“外部 Worker 理论上存在”绕过此门禁。

## 8. 三层健康与上线验收

### 8.1 进程/依赖健康

| 探针                        | 成功条件                                                                | 不能证明                                                                     |
| --------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| API `GET /health/live`      | HTTP 200、`status=ok`                                                   | 数据库、Worker、S3、ClamAV、Docling、模型可用                                |
| API `GET /health/ready`     | HTTP 200、`status=ready`；生产写入启用时 `checks.knowledgeIngestion=up` | S3/ClamAV/Docling 的真实处理能力；仅当 Agent Worker 启用时才连带检查 Runtime |
| Runtime `GET /health/live`  | HTTP 200、`status=ok`                                                   | Provider 可计费调用成功                                                      |
| Runtime `GET /health/ready` | HTTP 200、`status=ready`                                                | 非零真实向量、排序质量和企业 ACL                                             |
| 核心告警脚本                | `status=healthy` 且退出码 0                                             | 单个知识库的发布资格                                                         |

API/Runtime 健康检查可使用现有脚本：

.\infra\scripts\Test-EnterpriseServiceHealth.ps1 `
  -ApiBaseUrl https://api.example.com `
  -AdminBaseUrl https://admin.example.com `
  -AiRuntimeBaseUrl https://ai-runtime.example.com
```

核心数据库/语义证据探针：

  -Container <生产 PostgreSQL 容器或受控执行目标> `
  -Database <生产数据库名> `

  -ExpectedEmbeddingModel <不可变 Embedding 模型名>
```

需要重点告警：

- `KNOWLEDGE_INGESTION_FAILED`
- `KNOWLEDGE_EMBEDDING_GAP`
- `KNOWLEDGE_EMBEDDING_EVIDENCE_EMPTY`（readiness blocker）
- `SEMANTIC_SCHEMA_MISSING`

### 8.2 知识库检索诊断

管理员身份读取：

`GET /api/v1/admin/knowledge-bases/{knowledgeBaseId}/readiness`

该接口返回运行状态，不再决定知识库能否设为 `ACTIVE`。重点检查：

- 没有处理中或失败的文档；
- 至少有一个已发布的非空切片；
- Embedding capability 为 `READY` 且有模型名；
- 当前模型覆盖全部已发布切片，即 `semanticCoverage=1`；
- Reranker capability 为 `READY` 且有模型名。
- 当前 READY 版本已建立实体、关系和切片级证据，关系证据覆盖率达到门槛；
- 图谱 `status`、`diagnostics`、孤儿实体、无证据关系和图谱构建失败。

响应中的 `retrievalMode=LEXICAL` 表示关键词降级，但不阻止初版使用。管理员可以直接启用空知识库；文档只要完成解析和分块即可发布。Embedding、Reranker、评测和图谱诊断用于质量判断，不再由服务端作为启用或发布硬门禁。

### 8.3 端到端 canary

每次首次接线、解析器升级、模型升级或存储迁移后，在隔离验收租户完成：

1. 上传一份可搜索 PDF、一份扫描 PDF 和一份含表格的 DOCX；
2. 观察任务从 `PENDING/RUNNING` 到 `SUCCEEDED`，确认扫描、parser 名、页码和审计事件；
3. 在版本切片预览中核对标题层级、页码、表格文本、切片数量和当前模型名；
4. 确认 readiness 的 `publishedChunkCount > 0`、`embeddedChunkCount = publishedChunkCount`、`semanticCoverage=1`、`retrievalMode=HYBRID`；
5. 在“实体关系”页确认实体、关系、方向、当前版本证据和来源切片均可追溯，同名文档不会合并为同一个源实体；
6. 使用管理员检索测试台分别验证实体名称、实体别名、一跳关系和两跳关系，确认关系候选数、扩展数、完整路径和来源证据；
7. 以普通员工身份模拟有权、无权、父子部门和无答案问题，确认关系扩展不会越过知识库 ACL；
8. 执行供应商 smoke 与不少于门槛数量的脱敏企业问题集；
9. 对每个生产文档源执行两阶段 canary：先新增，再验证更新、删除归档、重复跳过、失败时游标不推进和重试幂等；核对原文件、版本、Qdrant point 和来源链接联动；
10. 初版可直接将知识库设为 `ACTIVE`；正式扩大生产流量前，仍应要求 ACL 泄漏为 0、质量与延迟阈值通过，并记录诊断项处置结论。

空知识库、只有词法候选、只返回 capability `ready` 或只看到 HTTP 200 都不能通过。

## 9. 故障恢复决策

| 现象/错误                                                    | 处置                                                                                                       |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `PENDING` 持续堆积                                           | 检查是否至少一个 Worker 启用、数据库 Worker 账号、最老任务年龄和 poll 日志；恢复消费者后由持久队列继续处理 |
| `RUNNING` 但 Worker 已退出                                   | 不手改状态；等待 claim TTL 到期，由其他实例重新领取                                                        |
| `KNOWLEDGE_FILE_SCAN_UNAVAILABLE`                            | 恢复 `clamd`/网络/签名后等待自动退避；耗尽后在管理端重试该失败版本                                         |
| `KNOWLEDGE_FILE_INFECTED`                                    | 安全隔离和事件响应；不得重试放行，处置后上传新版本                                                         |
| `DOCUMENT_PARSER_TIMEOUT` / `DOCUMENT_PARSER_UNAVAILABLE`    | 恢复 Docling 容量/网络后等待自动重试；检查转换 P95 再调整超时                                              |
| `DOCUMENT_PARSE_FAILED` / `DOCUMENT_PARSER_INVALID_RESPONSE` | 在隔离环境复现并检查文件与 Docling 版本；修复后上传新版本或由管理员显式重试                                |
| `KNOWLEDGE_OBJECT_INTEGRITY_FAILED`                          | 冻结对象和账本证据，核对 S3 version/checksum；恢复可信对象后上传新版本，不能直接改 checksum                |
| Embedding/Reranker 不可用                                    | 修复 Runtime/provider；确认模型名与 1536 维契约，再重试失败版本                                            |
| 文档 `READY` 但当前模型覆盖不足                              | 使用“重建向量”操作，再检查 `semanticCoverage=1`；不必重新解析原文件                                        |
| 文档 `READY` 但实体/关系/证据缺失                            | 使用“重建关系”操作；普通文档检索继续可用，图谱诊断按实际关系检索需求处理                                   |
| 出现 `DOCUMENTS_FAILED`                                      | 查看版本的 `ingestionJob.errorCode/errorMessage`，按根因处置，再调用管理端“重试”；不影响其他已发布文档     |
| 模型切换后质量下降                                           | 停止激活新知识库，切回批准模型；按版本重建向量并重新运行企业问题集                                         |

失败版本的受支持恢复入口为：

- `POST /api/v1/admin/knowledge-bases/{kb}/documents/{document}/versions/{version}/retry`
- `POST /api/v1/admin/knowledge-bases/{kb}/documents/{document}/versions/{version}/rebuild-embeddings`
- `POST /api/v1/admin/knowledge-bases/{kb}/documents/{document}/versions/{version}/rebuild-graph`

两个接口都要求租户内知识写权限；重建操作立即写审计，重试任务在成功或失败终态写审计。优先使用管理后台，避免把短期管理员凭据留在命令历史。
