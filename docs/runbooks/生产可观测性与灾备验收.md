# 生产可观测性与灾备验收

本基线补齐关联标识、结构化访问日志、AI 依赖降级状态、Run/Outbox/Process/Tool/RAG 指标、Prometheus 告警规则、生产连续性配置门禁和 RPO/RTO 演练报告契约。它不会启动、停止或重启开发服务，也不会上传任何真实云备份。

## 1. 关联 ID 与 Trace 边界

API 和 AI Runtime 接受并返回以下头：

- `X-Request-ID`：单次 HTTP 请求标识；
- `X-Correlation-ID`：消息、任务、Agent Run、流程、工具调用跨请求关联标识；
- `traceparent`：合法的 W3C Trace Context；非法、全零或不安全输入会被替换。

API 与 AI Runtime 的访问日志输出单行 JSON，字段为 `event`、`occurredAtUtc`、`requestId`、`correlationId`、`traceId`、`method`、`path`、`statusCode` 和 `durationMs`。`path` 不包含 query，日志也不包含正文、Prompt、工具参数、Token、Secret 或上游响应。

API 与 AI Runtime 均已接入 OpenTelemetry SDK、OTLP/HTTP Trace/Metric Exporter 和 HTTP 客户端/服务端自动埋点；AI Runtime 还覆盖 asyncpg。生产环境默认把遥测设为 readiness 必需能力，未配置 Collector 或 SDK 启动失败时不得宣称就绪。仓库只提供安全配置与导出链路，不伪造 Collector、Trace 后端或供应商 APM 的在线证据；正式验收仍需证明同一 `trace_id` 能跨 API、AI Runtime、检索、工具和业务系统查询，并完成采样、脱敏、留存和告警演练。

共享开发 `.env` 中，Nest API 使用标准 `OTEL_*`，AI Runtime 优先使用 `AI_RUNTIME_OTEL_*` 隔离别名；生产进程仍可给 AI Runtime 直接注入标准变量。远程 Collector 必须使用 HTTPS，Header 只允许由服务端 Secret 注入且不会进入状态接口或日志。

## 2. AI 依赖的独立降级状态

AI Runtime 提供 `GET /health/dependencies`，独立返回：

- `run_store`；
- `model`；
- `embedding`；
- `reranker`。

每项状态是 `ready`、`degraded` 或 `disabled`，并携带明确的 `fallback_mode`。模型降级时进入“知识检索后人工接管”；Embedding 降级时暂停无依据生成并保留结构化业务能力；Reranker 降级时保留不经过重排的混合检索。

依赖状态中的 `evidence=lifecycle_probe` 和 `external_connectivity_verified=false` 是重要边界：当前轻量探针验证配置和适配器生命周期，不主动调用收费或限流的供应商接口，不能替代合成请求、企业问题集或供应商 SLA 验收。`/health/ready` 继续承担实例能否接收完整流量的门禁，`/health/dependencies` 用于展示和监控单项降级。

## 3. 指标与告警

数据库核心探针现在覆盖：

- Outbox：待发送、超时待发送、UNKNOWN；
- Agent Run：排队、执行、长时间排队/执行、UNKNOWN、未核实用量；
- Process Runtime：Schema、停滞实例、逾期步骤、24 小时异常步骤；
- Tool Gateway：Schema、UNKNOWN 外部效果、停滞执行、24 小时失败、24 小时 P95 执行延迟；
- RAG：24 小时入库失败、当前切片、指定模型向量覆盖和缺口；
- 备份新鲜度与隔离恢复演练；
- 模型、Embedding、Reranker 与 Run Store 独立状态。

一次监控周期原子生成 `.data/monitoring/latest-monitoring-result.json`。若使用 node_exporter textfile collector，可导出 Prometheus 文本：

```powershell
.\infra\scripts\Export-EnterprisePrometheusMetrics.ps1 `
  -MonitoringResultPath .\.data\monitoring\latest-monitoring-result.json `
  -OutputPath C:\ProgramData\node_exporter\textfile\enterprise_agent.prom
```

核心告警规则位于 `infra/observability/prometheus/enterprise-agent-alerts.yml`，包括监控快照中断、Run/Outbox UNKNOWN、流程逾期、工具外部效果不确定、RAG 入库/向量缺口、AI 依赖降级、备份过期和恢复演练过期。SLO 记录与告警规则位于 `infra/observability/prometheus/enterprise-agent-slo.yml`，覆盖：

- 99.9% / 30 天可用性目标以及 1 小时/5 分钟、6 小时/30 分钟、3 天/6 小时多窗口燃烧率；
- 普通 Agent Run 成功回复 P95 不超过 8 秒；
- 结构化工作台/财务看板/知识引用查询 P95 不超过 3 秒；
- Agent Run 首 Token P95 降级；
- Outbox 最老待处理事件不超过 60 秒。

规则不使用 tenant、run、task 或 tool ID 作为标签，避免高基数。低流量时错误率容易被单次失败放大，因此数据库核心探针、依赖就绪和队列停滞告警仍作为独立兜底，不能只依赖燃烧率。

`enterprise_agent_outbox_oldest_pending_age_seconds` 是“业务事件尚未离开事务 Outbox”的内部代理 SLI，能发现最早一段积压，但不能替代“业务系统事件产生→规则完成检测”的端到端 P95。正式验收还必须以 Correlation ID 在事件生产、Outbox 发布、消费者接收和规则判定四个时间点形成同一条 Trace，并用真实事件峰值计算端到端分位数。

生产 Collector 示例位于 `infra/observability/otel-collector.production.example.yaml`。它启用 TLS OTLP Receiver、从挂载 Secret 文件轮换的 Bearer 入口认证、内存保护、批处理、敏感属性删除、Trace 后端导出、Prometheus 指标导出以及 Collector 自监控。API 与 AI Runtime 必须通过服务端 `OTEL_EXPORTER_OTLP_HEADERS` / `AI_RUNTIME_OTEL_EXPORTER_OTLP_HEADERS` 注入同一受控认证头，不能把 Token 放入镜像、前端或仓库；需要 mTLS 时可在部署覆盖层增加客户端 CA，并同步配置两个 Exporter 的客户端证书。

示例固定 `UnderscoreEscapingWithSuffixes`，Prometheus 规则依赖该名称转换策略；升级 Collector 或自动埋点库后必须先比对 `/metrics`，再执行 `promtool check rules`。所有证书、Token 文件路径、CA 和后端授权值都必须由部署 Secret/环境提供，不得写入仓库。

指标文本来自周期性快照，不是请求路径上的实时计数器；它适合可靠性门禁和核心告警，不替代直方图、每租户 FinOps、AI 质量评测或完整业务 SLI。实际阈值必须经过负载测试和试点基线调整。

## 4. 无人值守调度

Windows 使用现有安装器注册每日备份、每周隔离恢复和周期监控：

```powershell
.\infra\scripts\Register-EnterpriseWindowsOperations.ps1 `
  -SourceContainer enterprise-agent-postgres-1 `
  -SourceDatabase enterprise_agent `
  -SourceDatabaseUser enterprise_agent_backup `
  -RestoreContainer enterprise-agent-restore-postgres-1 `
  -RestoreDatabaseUser enterprise_agent_restore `
  -ExpectedEmbeddingModel text-embedding-model-immutable-version `
  -ApiBaseUrl https://api.example.com `
  -AdminBaseUrl https://admin.example.com `
  -AiRuntimeBaseUrl https://ai-runtime.example.com `
  -WhatIf
```

`-WhatIf` 只验证最终任务定义；正式注册后仍需用真实服务账号触发一次并检查 Docker、目录、网络和 webhook 权限。Linux 参考 `infra/operations/enterprise-agent.crontab.example`。示例不包含凭据，不会自动安装。Kubernetes 不应挂载宿主 Docker Socket；应把一次性操作封装为固定 digest、签名镜像，并直接使用托管数据库和对象存储 API。

## 5. 加密异地备份与 PITR 配置门禁

复制示例配置后替换所有占位值：

```powershell
Copy-Item .\infra\config\enterprise-continuity.production.example.json `
  C:\ProgramData\enterprise-agent\continuity.production.json

.\infra\scripts\Test-EnterpriseProductionContinuityConfiguration.ps1 `
  -Path C:\ProgramData\enterprise-agent\continuity.production.json
```

门禁要求：

- KMS envelope encryption，密钥只允许 `secret://`、`vault://` 或 `kms://` 引用；
- 独立故障域的异地对象存储；
- Object Lock Compliance 或 WORM，不可变保留至少 14 天；
- WAL 归档、timeline history、restore command 和不超过 15 分钟的 PITR 恢复窗口；
- RPO 不超过 15 分钟、RTO 不超过 240 分钟；
- 禁止配置内出现明文 password、access key、secret key、bearer token 或 API key。

配置通过只证明“生产参数满足门禁”，输出会保留 `CONFIGURATION_ONLY_REQUIRES_RUNTIME_EVIDENCE`。仓库没有伪造某个云厂商的 KMS、Object Lock、跨区域复制或 WAL archive 上传结果；这些必须由所选基础设施适配器、对象版本/保留策略、复制状态和真实恢复证据关闭。

## 6. RPO/RTO 演练报告

完成备份和隔离恢复后，用事故时点生成受保护报告：

```powershell
.\infra\scripts\Publish-EnterpriseDisasterRecoveryReport.ps1 `
  -ManifestPath .\.data\backups\enterprise_agent-<id>.manifest.json `
  -RestoreReportPath .\.data\backups\enterprise_agent-<id>.manifest.restore-report.json `
  -IncidentDeclaredAtUtc '2026-07-28T03:00:00Z' `
  -RpoObjectiveMinutes 15 `
  -RtoObjectiveMinutes 240
```

报告契约固定为 `contractVersion=1`、`scope=DATABASE_ISOLATED_REHEARSAL`，从 manifest 的恢复点、事故时点、恢复开始和数据库验证完成时间计算 RPO/RTO。报告只有在源库、SHA-256、`restore-verified` 和 `cleanupVerified=true` 一致时才可能成为 `database-objectives-met`。

隔离数据库恢复报告永远令 `productionTrafficFailoverVerified=false`、`offsiteRestoreVerified=false` 和 `pitrReplayVerified=false`，并明确输出 `OFFSITE_RESTORE_NOT_TESTED` 与 `PITR_REPLAY_NOT_TESTED`。可以附带外部证据引用用于后续审查，但“记录了引用”不会自动变成“已验证”。因此该报告不能被当作区域切换、DNS/流量切换、应用恢复、对象存储恢复或完整业务 RTO 已通过。

## 7. 离线回归

不连接数据库、不访问模型和云服务即可验证契约：

```powershell
Get-ChildItem .\infra\scripts\tests\Test-*.ps1 | ForEach-Object {
  powershell.exe -NoProfile -NonInteractive -File $_.FullName
  if ($LASTEXITCODE -ne 0) { throw "Offline test failed: $($_.Name)" }
}
```

此外应运行 API TypeScript 测试、AI Runtime 测试、Collector `validate`、Prometheus `promtool check rules` 和生产镜像配置检查：

```powershell
otelcol-contrib validate --config=.\infra\observability\otel-collector.production.example.yaml
promtool check rules `
  .\infra\observability\prometheus\enterprise-agent-alerts.yml `
  .\infra\observability\prometheus\enterprise-agent-slo.yml
```

仓库内静态规则检查不能替代生产 Collector/Prometheus 加载、真实指标名称比对、告警路由、值班通知和演练确认。

## 8. 上线证据清单

正式 Go-Live 前仍必须提供仓库外证据：

1. 真实供应商模型、Embedding、Reranker 合成调用和企业问题集结果；
2. 生产 Prometheus/日志/Trace 后端成功采集，并完成一次告警送达与确认；
3. KMS Key ID、对象不可变保留、跨故障域复制、PITR WAL 连续性证据；
4. 从异地副本和指定时间点恢复，随后完成 API、Agent、RAG 和工具只读 smoke test；
5. 区域或集群故障下的生产流量切换与回切；
6. RPO/RTO 达标报告、问题复盘、负责人和整改期限。
