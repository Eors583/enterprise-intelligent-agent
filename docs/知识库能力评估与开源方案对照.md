# 企业知识库能力评估与开源方案对照

更新日期：2026-08-12

## 1. 结论

当前知识库已经跑通企业试点所需的基础文档 RAG：文件入库、版本、可配置分块、中文关键词与向量混合召回、BGE Cross Encoder 重排、Agent Run 回答和切片级可信引用均已在当前开发实例实测。同时保留原有租户隔离、部门范围和引用二次校验。本轮没有继续扩展权限模型。

- 当前实例已有 1 个活动知识库、2 个 READY 文档和 2/2 个当前模型向量切片，语义覆盖率为 100%；
- AI Runtime 的本地 `BAAI/bge-small-zh-v1.5` Embedding 与 `BAAI/bge-reranker-base` 均为 `ready`，自然中文问句已通过混合召回和重排实测；
- 当前活动知识库的图谱状态为 `NOT_BUILT`，实体、关系、提及和证据均为 0，现有两跳关系扩展尚无真实图数据可用；
- PDF/DOCX 已能解析，但还没有 OCR、版面、表格和图片语义解析；
- 本地磁盘、同步解析模式适合开发或小规模试点，不满足多副本生产部署；
- 文档预览、切片质检、数据源连接器和知识效果运营仍需持续完善；这些能力在初版作为可选增强，不阻塞功能验证。

因此当前判断为：

| 使用阶段     | 结论     | 前提                                                        |
| ------------ | -------- | ----------------------------------------------------------- |
| 技术验证     | 可用     | 当前本地中文 Embedding、混合检索、重排和可信引用链路已跑通  |
| 小范围试点   | 条件可用 | 完成真实企业问题集验收、切换对象存储与持久异步任务          |
| 企业正式生产 | 暂不建议 | 还需 OCR/复杂文档、连接器、治理、监控、高可用与安全运营闭环 |

## 2. 已有能力

### 安全与权限

- PostgreSQL RLS 租户隔离；
- 知识库部门范围与子部门继承；
- 检索前权限过滤，禁止候选不会发送给 Reranker；
- 引用绑定文档版本与切片，并在查看原文时再次鉴权；
- 仅检索当前已发布且处理成功的版本。

### 文档与版本

- PDF、DOCX、TXT、Markdown 上传；
- 文档解析、确定性切片、内容哈希和 Token 估算；
- 草稿、发布、历史版本、回滚和向量重建；
- 解析或向量失败不会生成部分可用版本；
- 管理员可查看检索分数、检索模式、降级原因和语义覆盖率。

### 检索与回答

- 中文完整词、trigram、bigram 与模糊匹配；
- pgvector 精确/HNSW 向量召回；
- 知识库级全文、向量、混合模式与可配置语义/关键词加权融合；
- 可配置 TopK、最低相关度、单篇文档最多切片和 Cross-Encoder Reranker；
- 相关性阈值和无依据回答策略；
- Agent Run 对知识引用做可信校验。

## 4. 推荐架构

```mermaid
flowchart LR
  A["文件/飞书/网盘/网页"] --> B["对象存储 S3/MinIO"]
  B --> C["异步解析队列"]
  C --> D["Docling/OCR/版面与表格解析"]
  D --> E["页码、标题、版面元数据"]
  E --> F["切片与质检"]
  F --> G["Embedding + pgvector"]
  G --> H["问题分类与检索路由"]
  H --> I["权限内关键词/向量混合召回"]
  H --> L["业务事实 SQL / API"]
  H --> M["实体链接 + 受控图遍历"]
  I --> N["Reranker"]
  L --> O["证据合并"]
  M --> O
  N --> O
  O --> J["Agent Run"]
  J --> K["答案 + 可点击可信引用"]
```

建议采用：

- **Docling**：作为 PDF、Office、OCR、版面和表格解析层；
- **pgvector**：继续作为租户数据边界内的向量存储；
- **BGE-M3 / Qwen Embedding**：中文与多语语义向量；
- **BGE Reranker / Qwen Reranker**：候选精排；
- **MinIO 或 S3**：原始文件、解析产物和版本快照；
- **现有 API/RLS**：继续作为唯一权限、发布、引用和审计入口。

RAGFlow 可以作为完整能力参考或独立解析/检索服务，但若直接替换本项目知识层，会引入第二套用户、租户、权限和索引生命周期，必须做严格的 ACL 映射与引用二次鉴权。Dify 和 FastGPT 更适合工作流/应用编排参考，采用前还需单独评估其许可证与多租户限制。

## 5. 初版运行约束与生产验收

### 初版运行约束

- 知识库可以空库启用，文档完成解析和分块后即可直接发布；
- 解析复核、治理审核、评测 Run、Embedding 覆盖和关系图谱状态不再作为知识库启用或文档发布的硬门禁；
- 文件必须通过 MIME/扩展名/大小校验和恶意文件扫描；
- 解析或切片失败必须可见、可重试，失败版本不能发布；Embedding 不可用时允许降级为关键词检索；
- 管理员能查看原文、页码、切片和各模型向量覆盖。

### 检索质量验收（非阻塞）

- 当前 Embedding 模型的向量覆盖率达到 100%，或管理员明确接受降级；
- 企业问题集达到约定的 Recall@5、MRR、nDCG 和无答案准确率；
- 任意越权命中或越权引用数量必须为 0；
- 供应商不可用时显示“仅词法检索”，不得标记为语义检索正常。

### 生产上线验收

- 原文件迁移至对象存储，解析和向量化迁移至持久化异步任务；
- 建立解析积压、失败率、检索 P95、无答案率和模型异常告警；
- 完成备份恢复、索引重建、模型切换和权限回归演练；
- 用真实企业文档和脱敏问题集验收，不能以空知识库或合成数据代替。

## 6. 本轮已补齐的管理闭环

- 草稿知识库可以由管理员在不对员工开放的前提下预览真实检索结果；
- 文档列表支持标题/文件名搜索，以及来源和处理状态筛选；
- 每个文档版本可以分页查看完整切片、章节、页码、Token、哈希和已生成的 Embedding 模型；
- PDF 新入库时保留页级正文，并在切片元数据中记录页码和解析器来源；
- 知识库状态可直接设为 `ACTIVE`；页面同时展示文档、向量和图谱诊断，但不再用诊断结果禁用保存；
- 可见范围改为显式选择“全企业”或“指定部门”，组织树加载失败时不会把空选择误保存为全企业；
- 同名部门显示层级路径，降低管理员选错范围的风险；
- 草稿预览、仅词法降级和 0% 向量覆盖均以明确文案呈现，不再产生“语义 RAG 已可用”的错误预期。

## 7. 本轮参考 Dify 的范围与差异

本轮参考 Dify 已公开的知识库体验，但没有复制 Dify 的完整平台：

- 已参考并实现：知识库级检索模式、向量/全文混合权重、TopK、Score Threshold、模型重排、分块目标与重叠、独立检索测试，以及工作流/Agent 中使用知识检索结果。
- 本项目的不同点：RAG 直接嵌入企业 `Agent Run`，文档版本、切片和回答引用形成同一条可验证血缘；PostgreSQL 仍是企业业务事实账本，不另建一套 Dify 应用、用户和知识生命周期。
- 尚未对齐 Dify：父子分块、通用元数据字段与过滤器、数据源插件生态、网页/云盘定时同步、批量索引运营、可视化评测数据集、应用编排画布和知识流水线。
- 关系检索不应照搬普通向量 RAG。项目、任务、负责人和交付状态优先查询 NestJS 业务 API/参数化 SQL；文档实体关系再走 PostgreSQL 受控图遍历；只有出现跨全库总结需求时才增加 Global GraphRAG。

Dify 参考资料：[分块和清洗](https://docs.dify.ai/en/cloud/use-dify/knowledge/create-knowledge/chunking-and-cleaning-text)、[索引与检索设置](https://docs.dify.ai/en/cloud/use-dify/knowledge/create-knowledge/setting-indexing-methods)、[元数据](https://docs.dify.ai/en/cloud/use-dify/knowledge/metadata)、[检索测试](https://docs.dify.ai/en/cloud/use-dify/knowledge/test-retrieval) 与 [Knowledge Retrieval 节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)。

## 8. 完整 RAG 与关系型检索方案

### 8.1 结论

本项目应实现“问题路由 + 多检索器 + 证据融合”，而不是把所有问题都发送到向量检索或自由生成 SQL：

| 问题类型 | 示例                                   | 权威检索路径                               | 原因                                                               |
| -------- | -------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------ |
| 文档事实 | “差旅报销需要什么材料？”               | BM25/中文词法 + 向量 + RRF + Cross Encoder | 语义表达多样，答案来自文档片段                                     |
| 业务关系 | “哪个项目依赖供应商审批，负责人是谁？” | NestJS 受控业务 API / 参数化 SQL           | 项目、任务、负责人和状态已经是 PostgreSQL 权威事实，不应从文档猜测 |
| 文档关系 | “制度 A 与流程 B 有什么依赖？”         | 实体链接 + 1～2 跳受控图遍历 + 原文证据    | 需要跨片段关系，但每条边仍须有来源                                 |
| 全局分析 | “全部项目风险的共同主题是什么？”       | 结构化聚合 + GraphRAG 社区摘要/分层总结    | 属于全局综合问题，普通 top-k RAG 容易漏掉长尾事实                  |

Microsoft GraphRAG 也明确区分 Local、Global 和 DRIFT Search：Local 将实体图与原始文本片段结合，Global 对社区报告做 map-reduce，DRIFT 用全局信息扩展局部检索。因此 GraphRAG 应作为特定问题类型的检索器，而不是替代全部业务查询。参考：[Microsoft GraphRAG Query Overview](https://microsoft.github.io/graphrag/query/overview/) 和论文 [From Local to Global](https://arxiv.org/abs/2404.16130)。

### 8.2 PostgreSQL 优先的关系检索

当前仓库已经有知识实体、提及、关系、关系证据、本体、冲突治理、时态有效期和最多两跳的递归查询，并且这些表继承租户 RLS。第一阶段应继续使用 PostgreSQL：

1. 将 `Organization`、`User`、`AgentInstance`、`Strategy`、`Objective`、`Project`、`Task`、`Deliverable`、`Evidence` 映射为稳定业务实体，使用业务 UUID 作为 `externalKey`，不靠名称猜测同一实体。
2. 文档入库时用结构化抽取产生候选实体/关系；初版允许有来源证据的活动关系直接参与 1～2 跳检索，本体、谓词、类型、置信度和人工治理作为后续质量诊断与校正能力。
3. 查询规划器只输出受控意图、实体、谓词、方向、时间和组织范围；业务事实查询使用白名单模板/AST 构造器，不让模型直接执行任意 SQL。
4. 图遍历限制为最多两跳，路径上每条边必须有当前版本的可访问证据；租户、知识库和文档证据过滤继续执行，开放冲突和未发布本体仅作为诊断，不阻塞初版关系检索。
5. 最终排序融合实体匹配、路径置信度、来源权威性、时效、词法/向量分数和 Reranker 分数；答案同时返回业务记录引用和文档切片引用。

PostgreSQL 原生递归 CTE 可以处理直接与间接关系；pgvector 继续承担相似度检索，并且现有 exact 模式可作为小规模正确性基线。pgvector 官方说明 exact nearest-neighbor 提供完整召回，而 HNSW/IVFFlat 用召回率换速度；多租户共享近似索引还可能相互影响召回，因此切换 HNSW 前必须完成租户过滤与召回回归。参考：[PostgreSQL Recursive Queries](https://www.postgresql.org/docs/current/queries-with.html) 和 [pgvector](https://github.com/pgvector/pgvector)。

### 8.3 何时引入 Neo4j

Neo4j 官方 GraphRAG 已提供 Vector/Hybrid、VectorCypher/HybridCypher 和 Text2Cypher 等不同 Retriever，证明“语义命中后图遍历”和“结构化关系查询”应是独立路径。参考：[Neo4j GraphRAG User Guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)。

当前阶段不建议让 Neo4j 成为第二个权威账本，因为这会复制租户、ACL、版本和审计状态。满足以下条件时，可以把 Neo4j作为由 Outbox 驱动的只读派生图：

- 大量查询需要三跳以上遍历、路径模式匹配、社区检测或图算法；
- PostgreSQL 递归查询在真实规模和 P95 门禁下已成为明确瓶颈；
- 已完成增量同步、删除传播、版本水位、ACL 投影、重建与灾备演练；
- 所有 Neo4j 结果仍回到 NestJS API 做最终授权和来源校验。

### 8.4 推荐实施顺序

1. 用真实部门资料和问题集完成混合检索、无答案和回归门禁，并按需要从当前中文 n-gram 基线升级为中文 BM25。
2. 增加父子分块、切片预览/重建和自定义元数据过滤，覆盖长制度、长报告与多版本资料。
3. 发布最小企业本体，把组织、战略、项目、任务、交付物和证据的业务 UUID 接入知识实体。
4. 用 1～2 跳关系问题集验收路径准确率和证据完整率，再按需要补齐本体发布、冲突校正和时态治理。
5. 增加问题分类器和白名单查询规划器，融合文档检索、业务 API/SQL 和图检索结果。
6. 只有出现全库综合问题的明确需求后，再增加社区摘要/Global GraphRAG；只有 PostgreSQL 图遍历达到性能边界后，再评估 Neo4j 派生读模型。

关系检索的生产质量验收至少包括：关系问题准确率、路径精确率、证据覆盖率、实体消歧准确率、过期关系拒绝率、无答案准确率、越权命中为 0，以及按问题类型统计的 P95 延迟与成本；初版不把这些指标做成运行时硬门禁。

## 9. 千万级多类型知识库方案（2026-08-12 增补）

本节取代本文早期“继续以 pgvector 为主要向量热路径”和“复杂文档能力尚未接入”的规模判断。当前开发实例已经接入 Docling、MinIO、Qdrant 稠密/稀疏混合索引、父子块、页码/工作表定位和结构化工作簿查询。PostgreSQL 仍是租户、ACL、发布版本与引用证据的权威账本，但千万级向量和词法候选必须由专用检索索引先行缩小到有界 Top-K，PostgreSQL 只核验和回填这些候选。

### 9.1 当前 10 万切片的实测结论

2026-08-12 开发实例有两个主要活动知识库，PostgreSQL 当前版本分别为 51,691 和 47,607 个切片，对应 Qdrant 活动点数完全一致。Qdrant 单个约 5 万点 collection 的稠密 Top-40 检索，20 次本机调用中中位约 16 ms、P95 约 20 ms；同一中文查询跨两个 collection 并行执行稠密 + 中文稀疏向量 + RRF，可返回 80 个粗排候选，预热后 Qdrant 服务端合计约为个位数毫秒。以上结果只证明当前 10 万级索引没有性能瓶颈，不能冒充千万级验收。

此前 17～53 秒的慢查询来自检索编排而不是向量库：

1. 两个知识库使用相同模型和 1536 维向量，但各自拥有不同 collection；旧代码把 collection 名也当作模型兼容条件，导致跨库查询直接放弃 Qdrant。
2. 即使 Qdrant 已返回候选，旧代码仍对 PostgreSQL 近 10 万条正文无条件执行 `LIKE + similarity + word_similarity` 后再排序，现有 `knowledge_chunks_content_trgm_idx` 的累计扫描次数为 0。
3. PostgreSQL 事务因此长时间读取数据文件并触发事务超时，Agent Run 一直停留在 `QUEUED`，模型实际调用次数为 0。

当前修复策略是：兼容模型的多个 collection 并行召回并合并；Qdrant 健康且不是“仅全文”模式时跳过 PostgreSQL 正文扫描；Qdrant 故障降级只使用可命中 GIN trigram 索引的三字符以上词项预筛，再对小候选集评分。开发库上该索引预筛约 182 ms，避免故障时重新拖垮业务数据库。

本轮继续在真实两库链路发现并修复了三项热路径问题：

1. 普通 `DOCUMENT` 问题曾无条件执行十几万行关系表上的递归 CTE；现在只有显式关系意图或基础召回为空时才启用图扩展，普通文档问答不再为未使用的图候选付出延迟。
2. Qdrant 混合查询返回的是 RRF 排名分数，不是余弦相似度；现在由 Qdrant 适配层先把双路 RRF 分数归一化到统一 `[0,1]` 范围，再进入已有质量阈值，避免 40 个有效候选被错误当作低相似度全部过滤。
3. 本地 CPU Cross Encoder 曾可占用约 25 秒；现在交互检索的重排预算固定为 3 秒，超时或无有效结果时保留已经通过权限核验和质量门禁的混合召回结果，不以“降级”为由返回空证据。

以用户实际问题“我想知道华为铁三角是什么”复测两个约 5 万切片的知识库：关闭重排时冷请求约 370 ms、预热后约 47 ms；启用重排时完整检索约 3.5 秒，CPU 重排超出 3 秒后按设计回退，仍返回 8 条证据，8 条正文均包含“铁三角”，Top 1 可直接支撑客户经理（AR）、方案经理（SR）、交付经理（FR）组成的答案。以上是当前约 10 万切片的功能与延迟证据，不外推为 10M 性能承诺。

同日用仓库既有的 200 题来源绑定数据集做单并发回归，覆盖 175 道可回答问题、25 道无答案问题，以及 PDF、PPT、XLSX、OCR 图片和英文接口文档等证据形态。最终 Recall@5、MRR、nDCG@10、无答案准确率均为 100%，ACL 泄漏为 0，错误为 0；P50 为 88.36 ms、P95 为 161.94 ms、P99 为 2.24 s，最慢为 3.78 s。该数据集证明本轮热路径修改没有降低已有来源绑定检索质量，但其知识库规模远小于 10 万，延迟数据不能替代 1M/10M 容量压测。回归中本机 CPU Cross Encoder 首次超过 3 秒后打开 60 秒熔断，后续请求使用已经通过权限、混合召回和直接证据门禁的加权融合结果；生产 10M 验收仍须单独验证 GPU 或隔离式 Reranker 的吞吐、排队和取消能力。

为避免提速后误伤精确引用，证据门禁还会识别“请根据某文档说明这段原文”一类包装语，优先用冒号后的正文或引号内的章节名与原文做证据覆盖判断；相同混合分数时以直接证据覆盖率打破平局。这一调整恢复了表格、PPT、OCR 和英文片段的 Top 1，同时 25 道无答案问题仍全部拒答。

### 9.2 “30 秒”必须拆成分层 SLO

千万级目标定义为“高质量、权限正确的最终回答在 30 秒内完成”，不能把 30 秒都留给召回。生产门禁按热/冷请求、P95/P99 和并发分别报告：

| 阶段                              |  P95 预算 |   P99 预算 | 说明                                 |
| --------------------------------- | --------: | ---------: | ------------------------------------ |
| 权限范围、查询路由                |    200 ms |     500 ms | 只读取业务元数据，不扫描切片正文     |
| 查询 Embedding                    |    800 ms |      1.5 s | 服务预热、批处理与超时隔离           |
| 稠密 + 稀疏/词法粗排              |     1.5 s |        3 s | 10M 有效点、过滤和并发条件下验收     |
| PostgreSQL ACL/版本核验与正文回填 |    500 ms |        1 s | 只处理有界 chunk ID                  |
| Rerank、父块回溯和上下文压缩      |       2 s |        4 s | 候选量必须受限；CPU/GPU 分别验收     |
| 完整知识检索                      |   **5 s** |   **10 s** | 超时返回可解释降级，不允许全库扫描   |
| 首个可见进度 / 首 Token           | 1 s / 8 s | 2 s / 12 s | 员工端持续显示所处阶段               |
| 最终回答                          |  **30 s** |       45 s | 30 秒是 P95 业务目标，不是单次演示值 |

### 9.3 多类型文件采用自动路由，不增加用户配置负担

用户继续只上传文件；系统根据 MIME、解析结果、版面结构与内容密度自动选择策略。管理员默认只看到“解析质量、索引状态、检索质量、是否需要处理”四类业务信息，不要求普通用户理解 token、HNSW、collection 或 rerank 参数。

| 文档类型             | 权威父块                     | 检索子块起点                              | 必须保留的结构                                     | 特殊召回路径                                                   |
| -------------------- | ---------------------------- | ----------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------- |
| 原生/扫描 PDF、报表  | 页或跨页章节                 | 400～700 token，10%～15% 重叠作为评测起点 | 页码、标题层级、表格/图表、版面坐标、OCR 置信度    | 文本混合检索；表格/图表作为完整单元并可回溯原页                |
| DOCX/制度/合同       | 标题章节、条款               | 450～800 token；条款边界优先              | 标题路径、编号、列表、脚注、表格、修订版本         | 精确条款号词法召回 + 语义召回；命中子块后回溯章节              |
| PPT/PPTX             | 单页幻灯片                   | 短页整页；超长页按标题/文本框分子块       | 页码、标题、正文、备注、图表与阅读顺序             | 页标题/业务术语稀疏召回 + 稠密召回；引用定位到页               |
| XLSX/CSV             | 工作表、命名表、连续表格区域 | 表头 + 有界行组；表头在每块重复           | 工作表名、单元格地址、表头、公式与显示值、数据类型 | 聚合/筛选/计算优先走受控结构化查询；文本检索只负责定位表和字段 |
| HTML/Markdown/纯文本 | 标题章节或正文区             | 400～700 token                            | 标题、代码块、列表、来源 URL、抓取时间             | 去导航、页脚和模板噪声；代码/日志按行边界切分                  |
| 图片/OCR             | 单图或版面区域               | OCR 段落/表格/说明文字                    | 坐标、OCR 置信度、图像哈希、说明文字               | 低置信度进入人工复核；有视觉模型时可增加独立图片向量           |

所有格式共同执行：页眉页脚和模板去重、规范化内容哈希、父子/前后块血缘、来源版本与密级、解析器和切片策略版本、表格/代码/公式不在任意字符位置截断。上下文前缀先使用确定性的“文档标题 + 标题路径 + 页/工作表定位”；只有离线评测证明有收益时，才为难例异步生成 LLM 上下文说明，避免对千万切片默认增加成本和噪声。

### 9.4 千万级检索拓扑

```mermaid
flowchart LR
  A["员工问题"] --> B["权限范围与查询路由"]
  B --> C["一次查询 Embedding"]
  B --> D["结构化 SQL/API 分支"]
  C --> E["Qdrant 稠密 + 稀疏并行预取"]
  E --> F["RRF/DBSF 有界融合"]
  F --> G["PostgreSQL ACL、当前版本和证据核验"]
  G --> H["Cross Encoder 小候选精排"]
  H --> I["父块回溯与上下文压缩"]
  D --> J["证据融合"]
  I --> J
  J --> K["流式回答 + 可点击引用"]
```

目标形态按“同一 Embedding 模型/维度使用共享 collection，tenant、knowledge base、版本、active、分类作为 payload 索引”组织，避免每个知识库建立独立 collection。现有独立 collection 在迁移期间允许有限并行扇出；新索引通过双写、点数/版本水位校验、影子查询和回滚完成合并，不能直接修改 collection 名而丢失数据。Qdrant 官方也建议多租户场景优先共享 collection 并使用 payload 分区，而不是为每个租户创建大量 collection。

PostgreSQL 不再承担千万正文的每次模糊粗排。Qdrant 返回的 ID 仍不可信，必须回到 PostgreSQL 以当前租户、知识库、文档版本、发布状态、资源策略和治理哈希核验；因此性能优化不会绕开现有企业权限边界。

### 9.5 Qdrant 与 Milvus 的决策门禁

Manus 参考文档提出“千万级默认 Milvus”过于绝对。当前 Qdrant 已提供命名稠密/稀疏向量、payload 索引、过滤 HNSW、RRF/DBSF、多分片、多副本、量化和磁盘向量；现有项目也已经完成 Qdrant 适配、索引版本和 ACL 回查。现在迁移数据库会增加双写、回填、灾备和运维风险，却不会修复上层全表扫描。

因此先用 Qdrant 完成 100k → 1M → 10M 阶段压测。只有出现以下任一经复现的证据才启动 Milvus/其他引擎 PoC：

- 10M、目标过滤选择性和目标并发下，Qdrant 无法同时通过召回率与 P99 门禁；
- 持续写入导致可服务时间、索引新鲜度或尾延迟不达标；
- 单集群增长目标明显超过当前 Qdrant 容量边界，且分片/量化后仍不满足成本目标；
- 业务确实需要当前 Qdrant 无法满足的内置 BM25、GPU 索引或冷热分层能力。

10M × 1536 × float32 的裸向量约 61.44 GB（约 57.2 GiB）。按 Qdrant 容量规划的约 1.5 倍基础系数，再计 HNSW、payload、操作余量和副本，生产不能按“单机 64 GB”估算。基准候选拓扑为 3 个检索节点、6 或 12 个初始分片、复制因子 2、向量与 payload 落盘、热 HNSW/量化驻内存；最终节点内存、磁盘和分片数以 10M 压测结果确定，而不是把这组数值直接当生产承诺。

### 9.6 不降质量的验收门禁

每次索引、切片、模型、量化或 Top-K 变化都必须与冻结的 exact/旧版本基线配对比较：

- 200～500 条首批真实员工问题，逐步扩到覆盖 PDF、Word、PPT、Excel、扫描件、精确编号、无答案和跨文档问题；
- Recall@20 相对基线下降不超过 2 个百分点，nDCG@10 不下降；若业务确定绝对门槛，再同时要求绝对 Recall；
- 无答案准确率不能因扩大候选而下降，引用来源/版本/定位可验证率为 100%；
- ACL、跨租户、已归档/过期版本误召回为 0；
- 延迟必须与 Recall 同表报告，禁止用降低 `ef`、Top-K 或关闭重排制造“快但找错”的结果；
- 分别覆盖热缓存、冷缓存、50%/99%/99.9% 过滤、并发 1/20/100、持续写入和单节点故障。

仓库已经有持久化的 200 题检索 Benchmark 与离线 `tools/semantic_acceptance` 验收器，应直接扩展而不是再造第二套评测框架。容量档位为额外维度：每个 100k、1M、10M 报告都必须记录有效点数、collection/分片/副本、量化、数据类型分布、并发、冷热状态、写入速率、P50/P95/P99、Recall@5/20、MRR、nDCG@10、无答案准确率、引用正确率和 ACL 泄漏数。报告不得包含原始查询、文档正文、向量或凭据；只保留数据集哈希、稳定用例 ID、结果 chunk ID 和聚合指标。

规模验收分三关：100k 用真实数据修正链路；1M 用真实数据加经过分布校准的合成数据验证索引与并发；10M 在生产同规格集群实际装载并运行完整质量/性能矩阵。只有第三关真实通过，才能宣布“千万级 30 秒内高质量回答已完成”。

### 9.7 参考资料校正

- Docling 官方提供统一 `DoclingDocument`、多格式输入、结构化 JSON 与原生 `HybridChunker`；后者会先按文档结构切，再按目标 tokenizer 拆分/合并，并支持表格重复表头。当前项目应逐步消费结构化对象，而不是长期只消费 Markdown 导出。
- NVIDIA 的公开实验说明页级切片在其 PDF 数据集上平均表现最好，且表格/图表保持完整；这支持 PDF/演示文稿优先按页，但不能推导出 Excel、代码和网页也都按页。
- Qdrant Query API 原生支持稠密与稀疏预取后 RRF/DBSF 融合；没有可靠训练集和分数先验时，RRF 是安全默认。当前项目已经走这条路径，不需要额外部署 Elasticsearch 才能先解决 10M 目标。
- Dify 的检索层同样依赖 Qdrant、Milvus、pgvector 等可替换向量库并执行有界 Top-K/重排；它的优势主要是平台化和配置体验，不是拥有一种能让 SQL 全表扫描自动变快的专有算法。
